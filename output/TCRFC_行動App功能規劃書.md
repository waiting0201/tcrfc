> **v3.0 修訂摘要——雙會籍，且藍鯨官網確定建置**
> 本版是**資料模型層級的變更**，因此跳大版號。變更來自客戶決策：藍鯨將有自己的會員。

> 2. **會員卡為「每份會籍一張」**（§3.6）：持有兩隊會籍者有兩張卡，各自帶該俱樂部的標誌與品牌色，以左右滑動切換。

> 6. **俱樂部品牌資料與後台帳號授權由主站 `J4 俱樂部與授權管理` 承載**：該範疇屬系統管理，且已成為主站型別。`M` 模組為 M1–M5。
> 7. **§16.2 阻塞級第 5、6 項已解除**：
>    - 第 5 項「官網是否同步為雙隊」——**客戶已決定建置台中藍鯨官網**（獨立網域、雙語，見 [`TCRFC_台中藍鯨官網功能規劃書.md`](TCRFC_台中藍鯨官網功能規劃書.md)）。這正是 §2.3 的**解法 A**，藍鯨的賽程、名單、新聞三類頁面都會有回退目標。
>    - 第 6 項「主站 `J` 模組資料範圍權限」——**主站規劃書 v3.0 已補**（`AdminUserClub`／`AdminUserTeam`、`scope_mode`、資料存取層強制）。
>    ⚠️ **但新增一個技術條件**：藍鯨官網是**獨立網域**，而 Universal Link 只能綁自己持有的網域。該網域**必須由可控方持有**並能放置 `.well-known/apple-app-site-association` 與 `assetlinks.json`，否則藍鯨深連結仍然無法回退（§2.3）。
> 8. **§11「合作球隊帳號」的會員權限**：藍鯨的客服需要看得到自家會員。規則為「**只能存取自家的 `Membership`／`Order`／`Registration`；`Member` 主檔欄位一律遮罩；絕對看不到對方俱樂部的任何會籍列**」。
> 9. **慈善捐款平台為獨立後台與獨立資料庫**（§1.2）：與本 App 無直接關聯，但三份規格的分工敘述須同步。

> 1. **站內商城、購物車、訂單與庫存不在 App 範圍**（§1.3）：商品購買一律回到**官網站內商店**完成（主站規劃書前台 8.3、後台 `S` 模組），App 只提供入口連結。
> 2. **商店連結一律連往官網站內商店**（§2.1「更多」分頁、§3.1 首頁快捷入口）。官網商店的收款主體同為俱樂部，但與 App 內的會籍付款**分屬不同結帳流程**——§5 的 App 內 LINE Pay **僅限會籍費用**，不延伸至商品。

> **本文件的定位**
> 1. 本文件規範**台中磐石足球俱樂部與台中藍鯨女子隊的共同行動 App**（iOS／Android）：以兩隊賽事資訊、會員會籍、特約店家與自售廣告版位為核心的官方應用程式，**共用官方網站的後台與資料庫**。**內容主體是兩隊，收款與法律主體是俱樂部**——這兩件事必須分開理解，見 §1.2。

> 3. 主站規劃書 v2.5 已據本文件同步修訂**四項前提**：**「不另設固定版位」限縮為主站網頁**、**「不接金流」第二次限縮（App 內會籍付款除外）**、**「不做推播與通知中心」限縮為 LINE 推播與網頁站內信**、**「不做報名歸戶與表單自動帶入」於 App 端部分解除**（學員家長綁定維持不做）。
> 4. 本文件為功能規格，**不涉及框架、開發語言、部署環境等技術決策**（延續主站規劃書 §1.3 的既定前提）。第 1.5 節以「平台能力需求」取代技術選型。

## 1. 專案目標與範圍

### 1.1 定位

本 App 不是官方網站的縮小版，也不是把網頁包進殼裡。它存在的理由，是**做網站做不到的事**。

判斷一項功能該不該進 App，只用兩個標準，兩者滿足其一即可：

| 標準 | 說明 |
|---|---|
| **手機才做得到** | 需要定位、離線、推播、原生行事曆、相機等裝置能力 |
| **資料已在既有規格內** | 沿用官網後台既有的內容型別，不需要客戶額外產出內容即可上線 |

兩者皆不滿足的功能一律不納入——那只會做出一個比網站慢、比網站難維護的網站。

三個設計前提決定了整個 App 的樣貌：

| 前提 | 對設計的影響 |
|---|---|
| **App 與官網共用同一套資料** | App 不建立任何平行的內容維護介面。所有內容仍在官網後台維護，App 是第二個呈現端，不是第二個真實來源 |
| **會員在球場、在店家櫃檯使用** | 現場常常沒有網路。電子會員卡、已快取的賽程與已讀新聞**必須離線可用** |
| **廣告是自售，不是聯播網** | 版位賣給在地商家，成效由自家系統量測。因此不需要廣告 SDK、不需要追蹤許可、不做行為定向 |
| **一個 App、兩支球隊、每隊各一份會籍** | 兩隊內容平等呈現，**帳號與收款只有一套**，但**會籍與會員卡是每個俱樂部各一份**（v3.0）。App 不建立兩套會員名單、不做兩個結帳流程 |

**共同主體的界線**——這是本版最容易被實作誤解的一條：

| 層面 | 主體 | 說明 |
|---|---|---|
| **內容與品牌** | **兩隊共同** | 賽程、名單、新聞平等呈現；App 名稱中性，雙標誌並列 |
| **會籍** | **兩隊各自一份**（v3.0） | 會員可分別持有磐石會籍與藍鯨會籍，獨立計期、獨立續會、**各一張會員卡**。帳號仍是一人一組 |
| **收款與發票** | **僅台中磐石足球俱樂部** | 藍鯨會籍採**代收代付**：單一 LINE Pay 商店號、單一發票抬頭，事後依受益俱樂部分帳。**系統不做分潤計算** |
| **法律與帳號** | **僅台中磐石足球俱樂部** | 開發者帳號、推播憑證、隱私政策的資料控制者 |
| **內容維護責任** | **各自維護** | 藍鯨於同一後台有自己的帳號，僅能維護自家內容（§11）。授權與資料範圍設定於主站 `J4` |
| **官方網站** | **各自一站** | 台中磐石官網與**台中藍鯨官網**（獨立網域、雙語）共用同一套後台與資料庫，見 [`TCRFC_台中藍鯨官網功能規劃書.md`](TCRFC_台中藍鯨官網功能規劃書.md) |

> 「共同主體」指的是**對外的品牌與內容關係**，不是法人上的合資。任何實作若讀成「要建兩套會員或兩個收款流程」，一律是錯的。

### 1.2 與官方網站、慈善捐款平台的關係

| 項目 | 做法 |
|---|---|
| **後台** | **共用官方網站後台**，新增 `M. 行動 App` 模組，並擴充既有的 `E` 商業模組（E4–E6 廣告） |
| **資料庫** | **共用同一套資料庫**，App 讀取的是官網後台維護的同一份 `Match`、`Article`、`Member`、`PartnerStore` 等資料 |
| **內容主體** | **台中磐石足球俱樂部 × 台中藍鯨女子隊**，兩隊平等呈現 |
| **收款與法律主體** | **僅台中磐石足球俱樂部**，**與慈善捐款平台的協會主體完全分離** |
| **台中藍鯨的角色** | **內容提供方與品牌共同署名方，不是收款方**。藍鯨於同一後台有自己的帳號，維護自家 `Team`／`Player`／`Staff`／`Match`／`Article`（§8.6）。品牌使用與內容提供**須有書面授權**（§16.2） |
| **官網的角色** | 官網仍是 SEO 與對外內容的主體。App 不承接 SEO 責任；官網另需提供 App 下載頁與 Universal Link 驗證檔（見 §2.3） |
| **慈善捐款平台的角色** | **App 不承接任何捐款金流**。至多於慈善單元提供外連，且須明示收受者為台灣足球策略發展協會，不得讓使用者誤以為捐給俱樂部 |

三份規格的分工：

| 文件 | 承載什麼 | 主體 |
|---|---|---|
| `TCRFC_前後台功能規劃書.md` | 官方網站前台 13 單元、後台 A–L 模組、全部內容型別的定義 | 俱樂部 |

### 1.4 名詞定義

| 名詞 | 定義 |
|---|---|
| **版位（Slot）** | App 畫面上一個固定的廣告呈現位置，長期存在，由 `slot_code` 識別 |
| **檔期（Campaign）** | 一個廣告主在一個版位上、一段期間內的投放。同一版位同時段可有多個檔期輪播 |
| **素材（Creative）** | 檔期底下的實際圖片或影片，含標題、CTA 與點擊目的地。一個檔期可掛多個素材做 A/B 與雙語 |
| **曝光（Impression）** | 廣告區域 **≥50% 面積連續可見 ≥1 秒**。輪播中每一則各自計算 |
| **賽事系列（Competition）** | 一項具名的賽事，例如「企業甲級聯賽」或某項盃賽。**與 `Match.competition` 的四值粗分類（聯賽／盃賽／友誼／其他）不同**——後者是類型，前者是有名字的實際賽事 |
| **追蹤（Follow）** | 使用者選擇關心的球隊。決定首頁顯示哪一隊的下一場、近期賽事如何過濾、賽事推播送給誰。**追蹤與推播可分離**：可以追蹤藍鯨但不收藍鯨推播 |
| **裝置（Device）** | 一次 App 安裝。以 `device_install_id` 識別，解除安裝即失效，不跨 App、不跨裝置 |
| **深連結（Deep Link）** | 可直接開啟 App 內特定畫面的連結，含自訂 scheme 與 Universal Link 兩種 |
| **強制更新** | 舊版 App 因相容性或安全理由被停止服務，啟動時要求使用者更新 |
| **資格基準時間** | 抽獎名單凍結的時間點，沿用主站 `MemberDraw.snapshot_at` 定義 |

**兩隊在導覽上的呈現原則**：

1. **不設「磐石分頁」與「藍鯨分頁」**。兩隊不是兩個並行的 App，分頁依**功能**切分，球隊是每個功能內的篩選維度。做成兩個平行分頁會讓每個功能都要實作兩次。

### 2.3 深連結與 Universal Link

**兩種機制並行**：自訂 scheme `tcrfc://` 供 App 內部與推播使用；Universal Link／App Links 讓官網網址在已安裝 App 的裝置上直接開啟 App。

**畫面與網址的一對一對照**（未安裝 App 時，同一網址須在官網呈現對應內容）：

| App 畫面 | 深連結 | 官網對應網址 |
|---|---|---|
| 賽程（指定球隊） | `tcrfc://schedule/d1`、`tcrfc://schedule/bw1` | `/zh/schedule/d1/`、**（藍鯨：官網尚無對應頁）** |
| 賽事詳情 | `tcrfc://match/{id}` | `/zh/schedule/{slug}` |
| 新聞內文 | `tcrfc://news/{slug}` | `/zh/news/{slug}` |
| 球員詳情 | `tcrfc://player/{slug}` | `/zh/club/first-team/player/{slug}` |
| 特約店家詳情 | `tcrfc://store/{id}` | `/zh/perks/{slug}` |
| 課程詳情 | `tcrfc://program/{slug}` | `/zh/programs/{slug}` |
| 會員卡 | `tcrfc://membercard` | （無對應公開頁） |
| 會籍升級 | `tcrfc://upgrade` | `/zh/member/upgrade/` |

**深連結 scheme 維持 `tcrfc://`，不隨 App 名稱改為中性**——三個理由：

1. Universal Link 與 App Links 必須由**實際持有的網域**提供驗證檔，目前只有 `tcrfc.tw`。
2. 開發者帳號、憑證與收款主體都掛俱樂部（§14.1），scheme 與主體一致較不易出錯。
3. 自訂 scheme 是內部識別，**使用者介面上不可見**，改名沒有對外效益卻要改動所有既有連結。

**對官網的依賴（須由網站專案配合）**：

1. `.well-known/apple-app-site-association` 與 `.well-known/assetlinks.json` **必須由官網網域提供**，內容需 Apple Team ID 與 Android package name，取得後才能填寫。
2. 官網須新增 App 下載頁（`/zh/app/`、`/en/app/`）與頁尾連結。
3. 未安裝 App 的裝置點擊深連結時，一律回退至對應官網網址，**不得顯示錯誤頁**。

> ✅ **v2.0 的落差已解——客戶決定建置台中藍鯨官網**
> v2.0 時官網的 06 女子足球只是單頁導流，沒有藍鯨的賽程頁、球員頁與新聞頁，導致 `tcrfc://schedule/bw1`、`tcrfc://match/{藍鯨賽事}`、`tcrfc://player/{藍鯨球員}` 在未安裝 App 的裝置上無處可回退，分享出去的連結是死的。
> **客戶已選擇當時三個解法中的解法 A**：建置**台中藍鯨官方網站**（獨立網域、中英雙語，見 [`TCRFC_台中藍鯨官網功能規劃書.md`](TCRFC_台中藍鯨官網功能規劃書.md)），賽程、名單與新聞三類頁面都會有對應的回退目標。
>
> ⚠️ **但獨立網域帶來一個新的技術條件，必須處理**：
> - **Universal Link 與 App Links 只能綁定自己持有的網域。** 藍鯨官網若使用 `tcrfc.tw` 以外的網域，該網域**必須由可控方持有**，並能於其根目錄提供 `.well-known/apple-app-site-association` 與 `.well-known/assetlinks.json`。
> - 兩個網域都要各自設定關聯檔，兩份檔案的 Team ID 與 package name **相同**（同一個 App）。
> - **深連結 scheme 維持 `tcrfc://` 不變**——scheme 是 App 的內部識別，與網域無關，改了會讓既有連結失效。
> - 若藍鯨網域的持有或 DNS 控制權不在可控方手上（例如仍由第三方代管），**藍鯨內容的 Universal Link 不得上線**，須退回自訂 scheme 加網頁回退的作法。
>
> **上線前提**：藍鯨網域的持有與 DNS 管理權須確認（主站規劃書第 10 章第 39 點）。

### 2.4 離線與快取策略

| 內容 | 快取策略 | 時效 | 離線可用 |
|---|---|---|---|
| **電子會員卡** | 登入後立即快取，每次啟動嘗試更新 | 永久保留，標示同步時間 | ✅ **必須** |

| 課程梯次與名額 | 不快取 | — | ❌ |

**兩條硬規則**：

1. **離線時不得計算廣告曝光**。曝光事件可在離線時暫存並於連線後回傳，但**必須帶原始發生時間**，且伺服器端須拒收超過 24 小時的事件——否則廣告成效可被人為堆積。
2. **會籍狀態不得以快取值宣告有效**。會員卡離線可出示，但卡面須標示「最後同步：YYYY-MM-DD HH:mm」；超過 7 天未同步時，卡面須顯示提醒。否則已過期的會員可用飛航模式出示舊卡。

### 2.5 雙語與語系決定規則

沿用主站 G-01 的雙語原則（繁中預設、英文為譯本、未翻譯 fallback 繁中並標示、架構預留第三語系），App 端另定三條：

1. **首次啟動跟隨裝置語系**；裝置語系非繁中或英文時，預設繁中。首次啟動引導（S23）**先選語系再選追蹤對象**。
2. **會員登入後改跟隨帳號的語系偏好**（`Member` 既有欄位）。在 App 內變更語系時同步寫回帳號。
3. **推播語系以裝置註冊時的語系為準**（`AppDevice.lang`），與帳號語系不同時以帳號為優先。

**所有 App 內可見的內容型別都必須有 `zh` / `en` 雙欄位**，英文可空但欄位必須存在——與主站規則一致。

### 3.6 電子會員卡

卡面欄位：**所屬俱樂部標誌**、會員編號、QR Code、姓名、層級、有效期限、**最後同步時間**。

**每份會籍一張卡**：持有兩隊會籍者有兩張卡，**各自帶該俱樂部的標誌與品牌色**，以左右滑動或分頁切換。這也解決了「卡面偏向任一隊會讓另一隊的店家質疑效力」的顧慮：藍鯨的店家看到的就是藍鯨的卡。卡面設計待藍鯨品牌資產到位（§16.2）。

| 規則 | 說明 |
|---|---|
| QR 內容 | 即公開驗證頁網址 `/m/<token>`，與官網完全一致 |
| **一卡一 token** | **維持不變**。這條約束的是**卡與 token 的 1:1**——一張卡發兩組 token 等於兩份可撤銷狀態，撤銷時必漏一邊。**它從來就不是「一人一張卡」**：`MembershipPlan.card_quota` 的家庭方案本就可以是 3 張 |
| 驗證頁回傳 | **維持不變**：姓名首字、會員編號、層級、有效／已過期。**不得新增「適用球隊」欄位**——token 已經隱含俱樂部，掃出來就是那一隊的會籍狀態。<br>⚠️ 反過來說，**「一張卡標示兩種會籍狀態」的做法不可採**：不顯示「磐石有效／藍鯨已到期」則店員無法判斷，顯示了就等於新增「適用球隊」欄位 |
| 離線 | 卡面與 QR 離線可出示，但有效狀態以最後同步為準，超過 7 天未同步須顯示提醒 |
| token 重產 | 會員可自行重新產生，舊 token 立即失效 |
| 快速開啟 | 支援生物辨識或捷徑直達（選配） |

**不做掃碼核銷**：店家仍以目視驗卡，App 不提供店家掃描端、不記次、不出店家報表、店家端不需帳號——與主站 8.4 規則完全一致。

### 3.7 加入與升級付費會籍

| 區塊 | 內容 |

| 層級說明 | 一般會員（`registered`，免費）與球迷會員（`fan_club`，付費）的差異。**層級維持兩層，不因雙隊而增設層級** |

**未登入即可檢視**：權益對照表與方案比較是入會轉換的關鍵，不設登入牆。

### 3.8 特約店家與附近地圖

這是 App 相對於網站價值差異最大的一項。會員在外面想「附近有沒有可以打折的店」，就是一次付費會籍的價值兌現，而這件事網頁做不好。

| 功能 | 說明 |
|---|---|
| **距離排序** | 依裝置定位計算直線距離，由近至遠排序，顯示距離 |
| **地圖檢視** | 清單／地圖切換，地圖上以類別圖示標示 |
| **一鍵導航** | 開啟系統地圖導航至該店 |
| **一鍵撥號** | 直接撥打店家電話 |
| 篩選 | 沿用既有維度：類別（餐飲／運動用品／健康／教育／生活服務）與地區 |
| 詳情 | 名稱、照片／Logo、類別、地址、電話、營業時間、地圖連結、官網或社群連結、優惠內容、**適用層級** |

**公開瀏覽，不設登入牆**——與主站 8.4 一致，這是入會轉換的主要誘因。

**定位權限規則**：

1. 僅在**前景**使用定位，**不做背景追蹤**。
2. 首次使用時說明用途後才請求授權，不在啟動時就跳權限視窗。
3. 使用者拒絕授權時，**功能不得中斷**：退回依地區手動篩選 ＋ 後台排序，並保留手動輸入地址查詢的入口。
4. **定位座標不上傳、不儲存**，距離計算在裝置端完成。

**資料前提**：`PartnerStore` 目前只有地址字串，**沒有地理座標**，無法做距離排序。資料模型須新增 `lat` / `lng`（見 §10.2），後台 K4 新增座標欄位與「由地址定位」輔助按鈕，**人工確認後儲存**——不做執行期即時 geocoding，每次開 App 都打第三方服務既慢又貴，也會把使用者位置送出去。

**維持不做**：掃碼核銷、核銷次數統計、店家端帳號、點數、電子錢包。

### 3.9 課程與營隊報名

**先釐清範圍**：官網前台**本來就有線上報名**（兒童訓練、夏令營、冬令營、專項訓練各頁皆列），後台 P3 報名管理完整存在，`Program`／`Session`／`Registration`／`Trial` 四個型別俱在。**App 的報名不是新功能，是既有機制的手機介面。**

真正屬於本次新增的只有兩項，且都是會員對自己資料的操作：

| 項目 | 做／不做 | 說明 |
|---|---|---|
| **表單自動帶入** | ✅ 做 | 已登入會員的姓名、手機、Email 自動填入報名表，仍可修改。手機打字痛苦，這項在 App 上的價值比網頁高一個量級 |
| **我的報名（報名歸戶）** | ✅ 做 | 列出該會員的報名紀錄：課程、梯次、時間、地點、繳費狀態 |
| **學員家長綁定** | ❌ **不做** | 建立「成人↔未成年」的持久關聯，敏感度高一級。家庭會籍當初即刻意避開此設計。學員資料仍照舊存在 `Registration` 中，只是不建立 `Member` ↔ 學員的關聯表 |

**實作方式**：`Registration` 新增 `member_id`（**可為空**——非會員仍可報名，此規則不得更動），後台 P3 報名列表新增「會員」欄位。**不新增任何型別。**

**沿用既有規則，不得更動**：

| 規則 | 出處 |
|---|---|
| 報名狀態流程 `待確認 → 已確認 → 已繳費 → 完成 / 取消 / 候補` | 主站 P3 |
| 梯次狀態 `開放／額滿／候補／已結束`，前台自動顯示「立即報名／額滿候補／已截止」 | 主站 P2 |
| **繳費為線下作業**（匯款或現場收款後由後台標記） | 主站 P3 |
| 報名欄位：學員資料、家長聯絡、健康聲明、備註 | 主站 P3 |
| **課程時段不進行事曆** | 主站資料一致性原則 |

**兩條邊界**：

1. **App 內的 LINE Pay 只開放給會籍費用，不延伸到課程費用。**否則 §5 會從一件事變成兩件事，且課程退費規則遠比會籍複雜。
2. **「我的報名」可顯示梯次時間，但不得寫入 `CalendarEvent`**，也不得出現在賽程分頁的行事曆中。可提供單筆匯出至裝置行事曆。

**試訓**：`Trial` 共用 `Registration`，同一機制涵蓋，不另設流程。

### 3.10 抽獎資訊（唯讀）

主站已明文排除一整份前台抽獎功能清單。**本節的設計目標是在完全不牴觸該清單的前提下，讓付費會員知道自己有資格。**

**App 只做四件事**：

> **v3.0：各俱樂部各自舉辦抽獎。** App 的呈現方式不變，但改為**逐俱樂部顯示**——顯示的是「你在這個俱樂部的會籍是否涵蓋該場抽獎的基準時間」。同時持有兩隊付費會籍者，兩場抽獎都會看到自己具備資格。

| # | 顯示內容 | 資料來源 |
|---|---|---|
| 1 | **個人資格狀態**（布林，**逐俱樂部**）：「你的台中藍鯨會籍在資格基準時間有效，將自動列入」或「會籍尚未涵蓋基準時間」 | 該俱樂部的 `Membership` 即時狀態 |
| 2 | 活動辦法、獎品內容與名額、注意事項（中英雙語）、**主辦俱樂部** | `MemberDraw` 既有公開欄位 |
| 3 | 開獎時間與開獎場合（現場／直播） | `MemberDraw` |
| 4 | 結果已公布時，**連往那則最新消息** | `Article` |

**App 抽獎顯示 vs 主站已定案不做——逐條對照**：

| 主站已定案不做 | App 是否牴觸 | 說明 |
|---|---|---|
| ✗ 抽獎頁與報名按鈕 | 否 | 無報名動作。資格自動具備，會員零操作 |
| ✗ 我的抽獎／我的序號 | 否 | **不顯示序號**。序號只存在於後台快照與現場 CSV |
| ✗ 序號或中獎查詢介面 | 否 | 無任何查詢輸入框 |
| ✗ 站上中獎名單頁 | 否 | 結果一律連往最新消息，App 內不另建名單頁 |
| ✗ 線上開獎動畫 | 否 | 開獎在現場或直播進行，App 不做任何開獎呈現 |
| ✗ 合格人數即時計數器 | 否 | **見下方灰區說明** |
| ✗ 分享增加機會的機制 | 否 | 一人一號，不因任何行為增加 |
| ✗ 中獎通知信 | 否 | 系統信維持五封。**App 推播亦不得用於個別中獎通知**（見 §6.8） |

> **灰區必須寫明**：「我是否具備資格」的**個人布林**，與「合格人數即時計數器」是兩件事。前者是既有會籍狀態的直接呈現，不產生任何新資料；後者是全體人數的即時揭露，會誘發「快去入會以拉低中獎率」或「趁人少趕快入會」的動態。**App 顯示前者，明確不做後者。**

**資料來源限制**：App 讀取的是該俱樂部 `Membership` 的即時狀態與 `MemberDraw` 的公開欄位，**不得讀取 `DrawRoster`**。名單快照是後台稽核資產，不對前台開放。

> ⚠️ **雙會籍下必須顯示的一句話**：活動辦法須載明「**同時具備兩隊會籍者可分別參加兩隊抽獎**」。不寫清楚會被讀成「花錢買兩份＝加大中獎機會」，牴觸主站「不因消費增加中獎機會」的承諾。「一人一號」在**每一場抽獎內**仍然成立。

### 3.11 夥伴與贊助商

| 區塊 | 內容 |
|---|---|
| Our Partners | 依類型分區的 Logo 牆（策略／國際／訓練／教育／品牌）、詳情（合作內容、期間、官網連結） |
| Our Sponsors | 依等級分區（主贊助／官方／支持）、贊助故事連結 |

**兩隊的贊助商必須分區呈現，不得混列**——贊助合約是各自簽的，混列等於對外宣稱不存在的贊助關係。`Sponsor`／`Partner` 新增 `club_id` 欄位標示歸屬（§10.2），區塊標頭顯示所屬俱樂部。

**藍鯨的贊助商是否納入 App 呈現，須先取得藍鯨與其贊助商的同意**（§16.2）。未確認前該區塊不顯示，**不得以空的 Logo 格佔位**。

**贊助商曝光 ≠ 廣告版位**——這是本文件最容易被實作混淆的一條界線：

| | 贊助商 Logo 牆（本節） | 廣告版位（§3.12） |
|---|---|---|
| 資料來源 | `Sponsor`／`Partner` | `AdCampaign`／`AdCreative` |
| 位置 | 固定的夥伴專區與首頁下方 | 指定版位，輪播 |
| **計曝光** | **否** | 是 |
| **入廣告報表** | **否** | 是 |
| 標示「廣告」 | 否 | **必須** |

若某贊助商的合約包含「App 廣告版位 N 檔期」，正確做法是：在後台 E4 建立 `Advertiser` 並以 `sponsor_id` 關聯回既有 `Sponsor`，再開立 `AdCampaign`——成效才進廣告報表。**不得直接統計 Logo 牆的瀏覽數**，那是對不出來的數字。

**素材紅線**：目前尚未取得任何夥伴或贊助商的名稱與 Logo。在素材到位前，**App 內與商店截圖一律不得放置示意用的假 Logo**——那等同於對外宣稱不存在的商業關係。空缺處以「合作洽詢中」的空格位處理。

## 4. 會員與認證

### 4.4 裝置註冊與綁定

| 欄位 | 說明 |
|---|---|

### 4.5 未成年與監護人同意

沿用主站規則並在 App 端落地：

1. 註冊流程須有**年齡閘門**（填寫生日）。
2. **未滿 18 歲須經監護人同意方得註冊**，App 內須呈現同意流程與說明。
3. 未成年會員的個資處理與一般會員相同，均屬受限資料。
4. 課程報名中的學員資料由家長填寫，**不因此建立家長與學員的帳號關聯**（見 §3.9）。

### 4.6 帳號刪除與資料清除

| 項目 | 規範 |
|---|---|
| 路徑 | App 內設定可直接完成，不得僅提供來信申請 |
| 確認 | 二次確認並說明後果（會籍、球衣紀錄、報名紀錄的處理） |

| 不可回溯 | **不得改動已鎖定的歷史抽獎名單**——那會讓開獎失去稽核能力 |

## 5. App 內付款（LINE Pay）

### 5.1 範圍變更聲明

主站規劃書原訂「官網不建購物車、不接金流、不存卡號」，並於 §3.14 註明「LINE Pay API 站內結帳／退款／對帳不在範圍，**要做須先改第 10 章前提**」。

**本節即為該項修訂。**主站規劃書 v2.5 已據此將「不接金流」**第二次限縮**：

| 對象 | 金流 | 收款主體 |
|---|---|---|
| 官網網頁前台 | **仍不接金流**，維持收款連結與現場收款 | 俱樂部 |
| 慈善捐款平台 | 串接 LINE Pay Online API | **協會** |
| **行動 App（本文件）** | **串接 LINE Pay，僅限會籍費用** | **俱樂部**（雙隊平台不改變此點，見 §5.2） |

「**不存卡號**」一條**維持全域適用**——App 同樣不落地任何卡號資料。

**本節僅涵蓋會籍費用。**課程費用、商品、捐款均不在範圍。

### 5.2 收款主體與商店號

> **這是本節最容易出錯、後果最嚴重的一條。**

**三個主體，一個收款方**——v2.0 引入藍鯨後，這張表是判斷任何金流問題的依據：

| 主體 | 在本 App 的角色 | 收款 | LINE Pay 商店號 | 發票抬頭 |
|---|---|---|---|---|
| **台中磐石足球俱樂部** | 內容主體之一、**唯一收款方**、法律主體 | **✅ 全部會籍費用（含藍鯨會籍）** | 俱樂部自己的（待申請） | 俱樂部 |
| **台中藍鯨女子隊** | 內容主體之一、品牌共同署名、**會籍受益方** | **❌ 不收款** | **不申請、不使用** | — |
| 台灣足球策略發展協會 | 與本 App 無關 | ❌ | 慈善平台專用（**獨立後台與資料庫**） | 協會 |

慈善捐款平台使用的是**台灣足球策略發展協會**的 LINE Pay 特約商店號。本 App 的會籍收款主體是**台中磐石足球俱樂部**，**必須申請並使用俱樂部自己的商店號，不得共用**。

收款主體錯誤會同時觸犯兩件事：稅務上的收入歸屬錯誤，以及《公益勸募條例》——協會的勸募商店號不得用於收取俱樂部的商業性會費。

**v3.0 的雙會籍不改變收款結構**：

1. **不申請第二個商店號**。會籍雖然變成兩份，**收款方仍然永遠是俱樂部**——由俱樂部收款、以俱樂部抬頭開立發票，事後依受益俱樂部分帳。付款紀錄同時記下「收款主體」（恆為俱樂部）與「受益俱樂部」兩欄。
2. **App 內任何付款畫面都必須明示收款方為台中磐石足球俱樂部**——使用者是在「台中足球」這個中性品牌下付款，若不明示，會產生「我付給誰」的爭議，也會讓發票抬頭看起來對不上。**購買藍鯨會籍時尤其如此**：畫面須同時說清楚「你買的是台中藍鯨的會籍」與「收款方與發票抬頭是台中磐石足球俱樂部」。
3. **兩隊之間的收入分配（若有）是線下的合約與匯款事項，系統不處理**。本 App **不做分潤計算、不做對帳單**——那是慈善平台 `N` 模組的功能，不得套用到這裡。
4. **若日後藍鯨要獨立收款，屬於重大範圍變更**，需重寫本節、§5.5 的 IAP 論證與會員卡設計，不是加一個商店號就能解決。

**上線前提**：俱樂部的 LINE Pay 特約商店號尚未申請（見 §16.2）。未取得前本節無法實作。

**上線前提二——固定出口 IP**：LINE Pay 正式環境須於商店管理後台登記**付款伺服器的出口 IP**（sandbox 不需要），
因此承載 App 會籍付款的後端**必須具備固定出口 IP**，並於取得商店號後完成登記才能切換至正式環境。
`confirmUrlType` 採 **CLIENT**（由伺服器端於使用者返回後主動呼叫 Confirm），因此不需另外開放連入白名單；
這與 §5.4 「開通一律以伺服器端回呼為準」的要求一致。

發票開立責任歸屬於俱樂部，抬頭為俱樂部，與慈善平台的協會抬頭完全分離。

### 5.3 付款狀態機

```
建立訂單 → 待付款 → 已付款 → 已開通
              ↓         ↓
            已逾時    開通失敗（人工處理）
              ↓
            已取消

另有：已退款（僅後台人工發起）
```

| 狀態 | 說明 |
|---|---|
| `建立訂單` | 產生訂單編號與冪等鍵，尚未跳轉付款 |
| `待付款` | 已跳轉 LINE Pay，等待使用者完成 |
| `已付款` | 收到 LINE Pay 確認，款項已收 |
| `已開通` | 會籍已生效，`paid_until` 已寫入 |
| `已逾時` | 逾時未完成付款（建議 15 分鐘），訂單自動關閉 |
| `開通失敗` | 已收款但開通異常，**須立即告警並由客服人工處理**，不得靜默失敗 |
| `已退款` | 僅後台人工發起，見 §5.6 |

### 5.4 兩段式流程與冪等性

| 步驟 | 動作 |
|---|---|
| 1 | App 建立訂單，帶方案代碼與**冪等鍵**（同一鍵重複請求只成立一筆訂單） |
| 2 | 伺服器向 LINE Pay 請求付款，回傳付款頁 |
| 3 | 使用者完成付款，LINE Pay 回呼伺服器 |
| 4 | 伺服器**驗證回呼來源與金額**，標記為已付款 |
| 5 | 伺服器呼叫 `POST /api/membership/activate` 開通會籍 |
| 6 | 寄送「會籍開通確認」信（既有五封系統信之一），並推播通知 |

**三條硬規則**：

1. **開通一律以伺服器端回呼為準，不得以 App 端回報的付款結果開通會籍。**
2. **金額須於伺服器端重新計算並比對**，不得信任 App 傳來的金額。
3. **`POST /api/membership/activate` 必須具備冪等性**——重複回呼不得重複延長會籍。

> 主站設計此端點時即註明「日後若改採自動收款，只需更換觸發來源，會員模組不動」。本節正是該設計的兌現：**會員模組的開通邏輯完全不變，只是觸發者從客服人員換成付款回呼。**

### 5.5 商店內購（IAP）判定

> **這是本 App 最大的單一上架風險。**

Apple 要求 App 內販售**數位內容與服務**時必須使用內購（IAP）。付費會籍的權益以**實體為主**——入會球衣（實體物品）、特約店家折扣（實體通路消費）、抽獎的實體獎品、球迷活動優先報名（實體活動）——因此有相當理由主張屬於「實體商品與服務」，得使用外部付款。

**但這是審查判斷，不是規則明文，必須預先準備兩條路：**

| 方案 | 做法 | 代價 |
|---|---|---|
| **A（首選）** | App 內以 LINE Pay 完成付款，主張權益為實體商品與服務 | 若審查不通過須改版重送 |
| **B（fallback）** | App 內只顯示方案與付款指引，**外開瀏覽器**完成付款（等同官網現行做法），付款完成後回到 App | 流程斷裂，轉換率下降 |
| **C** | 申請 External Purchase Link Entitlement（依各地區規定） | 申請流程與適用地區須另行確認 |

**規格要求**：付款流程須設計為**可切換**——方案 A 與 B 共用同一組訂單與開通邏輯，差別只在付款頁是 App 內或外部瀏覽器。**不得把付款流程寫死成只支援其中一種**，否則審查一旦不通過就要重寫。

若判定須走 IAP，商店抽成將直接侵蝕會費毛利，且 IAP 無法對接 LINE Pay 與後台既有的開通流程——此情境下應優先採方案 B。

### 5.6 退款、對帳與憑證

| 項目 | 規範 |
|---|---|
| 前台 | **App 內不提供退款申請**。會籍屬期間性服務，比照官網現行規則 |
| 後台 | 誤刷、重複扣款等個案由客服受理後人工退款，須**獨立授權**並寫入稽核日誌 |
| 對帳 | 後台提供 LINE Pay 交易與 `MembershipPayment` 的對帳報表，差異須可標記與註記 |
| 發票 | 由俱樂部開立，抬頭為俱樂部。**與慈善平台的協會發票流程完全分離，不共用開立設定** |
| 會籍處理 | 退款後會籍狀態須同步回復，`paid_until` 沖回並記錄異動原因 |

## 7. 自售廣告版位與成效統計

### 7.1 範圍變更聲明

主站規劃書兩處明文「不另設固定版位」（首頁區塊編排、B3 Banner 管理），其對象是**官網首頁的檔期內容編排**，本意是防止首頁被版位切碎。

主站規劃書 v2.5 已將該條限定為「**本站網頁前台**不另設固定版位」，並註明行動 App 的自售廣告版位屬 App 範圍，**不影響官網首頁編排**。

**一項例外維持不變**：**首頁不設固定慈善版位，App 亦不做慈善相關版位。**慈善捐款的主辦與收款主體是協會，俱樂部的 App 不得販售或贈與慈善相關版位，以免與協會尚未確認的勸募資格混淆。

### 7.2 版位定義

版位是長期資產，建立後很少變動。

| 欄位 | 說明 |
|---|---|
| `slot_code` | 唯一識別碼，命名規則 `<畫面>_<位置>`，例如 `home_top` |
| 名稱（中／英） | 對業務與廣告主呈現的名稱 |
| `surface` | `app`（預留 `web`，日後若官網開版位不需搬表） |
| 畫面位置 | 對應 §2.2 的畫面代碼與區塊順序 |
| 素材規格 | 長寬比、最小像素、檔案大小上限、允許格式 |
| 是否允許影片 | 布林 |
| 單次 session 曝光上限 | 防止同一次使用中反覆曝光 |
| 輪播張數上限 | 同時段最多幾個檔期參與輪播 |
| **備援素材** | 無檔期或載入失敗時顯示的自家內容，**版位永不空白** |
| 啟用狀態 | 上／下架 |

**兒童向畫面不設版位**：學院、課程相關畫面不建立 `AdSlot`（見 §3.12）。

### 7.3 廣告主與合約

| 欄位 | 說明 |

| 名稱（中／英）、統一編號、聯絡窗口、電話、Email | 基本資料 |
| **`sponsor_id`** | **可為空**，指向既有 `Sponsor` |
| 合約備註、合作起訖 | |
| 狀態 | 洽談中／合作中／已結束 |

**`sponsor_id` 是關鍵設計**：同一家公司既是贊助商又購買廣告時，不重複建檔、不混淆兩者的成效歸屬，也不需要兩邊各維護一套聯絡窗口。

**v1 不做廣告主自助後台帳號**——比照慈善捐款平台「不做店家帳號」的既有取捨，報表由業務匯出後寄送。

| 欄位 | 說明 |
|---|---|
| `advertiser_id`、`slot_id` | 一個檔期綁一個版位。跨版位需求以多筆檔期表示，**不做多對多** |
| 名稱、起訖時間 | |
| `weight` | 輪播權重，同版位同時段依相對比例加權隨機 |
| 每日曝光上限 | |
| 每人頻次上限 | 同一裝置每日最多看到幾次 |
| `goal_type` | `曝光保證` / `導流` |
| `goal_impressions` | 曝光保證型的目標次數 |
| `delivered_today` | 當日已投遞計數，供 pacing 使用 |
| 合約金額 | **可設為不公開** |
| 狀態、審核者、建立者 | |

**狀態機**：

```
草稿 → 待審核 → 已排程 → 投放中 → 已結束 → 已結案
                            ↓
                         已暫停 →（可回投放中）

另有：已作廢（任一狀態可轉入，不可逆）
```

`已排程 → 投放中 → 已結束` 由起訖時間自動推進，其餘為人工操作。

**一條寫死的規則**：**素材未通過審核的檔期不得進入「投放中」。**否則會出現沒審過的圖直接上線。

**Pacing（曝光保證型必須做）**：目標曝光須平均分配到檔期天數。沒有 pacing 的話，檔期前兩天就會把保證量燒完，剩下的天數版位空著——這正是 `delivered_today` 欄位存在的理由，**不是可有可無的優化**。

### 7.5 曝光與點擊的定義

> 沒有這一節，廣告主報表無法對帳，版位就賣不出去。

| 事件 | 定義 |
|---|---|
| **有效曝光** | 廣告區域 **≥50% 面積連續可見 ≥1 秒**（比照 IAB／MRC 通行標準）。輪播中每一則各自計算 |
| **有效點擊** | 使用者主動點擊素材。**同一裝置對同一素材 5 秒內的重複點擊只計 1 次** |
| 無效流量 | 離線暫存超過 24 小時的事件、同一裝置異常高頻的事件，一律排除且不計費 |
| 不計曝光 | 版位顯示備援素材時、App 在背景時、廣告載入失敗時 |

**時間基準**：事件以**發生時間**記錄，不以上傳時間記錄。離線暫存的事件回傳時須帶原始發生時間，伺服器端拒收超過 24 小時者。

### 7.6 事件蒐集與聚合

| 層級 | 內容 | 保存期限 |
|---|---|---|
| **原始事件** `AdEvent` | 逐筆曝光與點擊 | **90 天**（供爭議稽核與去重） |
| **日聚合** `AdDailyStat` | 日期 × 檔期 × 素材 × 版位 × 平台 × 語系 | 長期保存 |

**為什麼要分兩層**（資料量估算，附假設）：

| 假設日活躍裝置 | 每人每日曝光 | 事件／日 | 事件／年 | 原始資料量 |
|---|---|---|---|---|
| 500 | 15 | 7,500 | 約 270 萬 | 約 270 MB |
| 2,000 | 20 | 40,000 | 約 1,460 萬 | 約 1.5 GB |
| 5,000 | 25 | 125,000 | 約 4,560 萬 | 約 4.6 GB |

原始事件無限期保留會讓資料庫在一年內膨脹到數 GB，而報表實際只需要聚合值。**90 天保留期同時是個資保存期限政策**，符合主站非功能性需求對保存期限的要求。

**聚合作業**：每日定時執行，聚合完成後標記 `aggregated_at`；聚合失敗須告警，不得靜默跳過。

### 7.7 廣告主報表（後台 E6）

| 項目 | 內容 |
|---|---|
| 維度 | 檔期／版位／素材／平台／語系／日期 |
| 指標 | 曝光數、點擊數、CTR、不重複裝置數、按日趨勢 |
| 對照 | 曝光保證型顯示「目標 vs 已達成」與 pacing 進度 |
| 匯出 | CSV 與 PDF，**須寫入稽核日誌**（誰、何時、哪個檔期、用途） |
| **不提供** | 任何個人層級資料、裝置清單、會員身分關聯 |

### 7.8 隱私與量測誠信

三個決定，一次解決三類問題：

| 決定 | 連帶效果 |
|---|---|
| **不接第三方廣告聯播網**，只做自售 | 不需要追蹤許可提示；商店隱私標籤可宣告「不追蹤」；不存在廣告 SDK 的兒童合規問題 |
| **不使用廣告識別碼（IDFA／AAID）** | 去重僅用 `device_install_id`（解除安裝即失效、不跨 App），不重複裝置統計採當日雜湊 |
| **不做行為定向** | 分眾只到「版位 × 語系 × 平台」，不依個人瀏覽紀錄選擇廣告 |

**這三條同時是給廣告主的說明，而且是賣點**：「我們的數據是自家系統直接量測的誠實數據，不是聯播網轉手的估算值。」

`AdEvent` **明確不儲存**：`member_id`、完整 IP 位址、精確定位座標、廣告識別碼。

### 7.9 廣告揭露與法遵

1. **每個版位必須有「廣告」或「贊助內容」標示**，不得誤導為編輯內容。
2. 廣告素材不得使用俱樂部標誌或暗示官方背書，除非該廣告主確為贊助商且合約載明。
3. 素材內容須經後台審核通過方可上線；發現違規或申訴時須有**即時下架機制**（單一檔期可立即暫停）。
4. **不得刊登**：菸酒、博弈、成人內容、醫療效能宣稱、金融投資招攬。
5. 針對未成年受眾的畫面不置放廣告（見 §3.12）。

## 8. 後台功能規劃

### 8.0 模組總覽

App 相關的後台功能分為兩部分，**刻意不放在同一個模組**：

```
M. 行動 App                          （新增一級模組）
├─ M1 App 版本與發布管理
├─ M2 App 內容編排與深連結
├─ M3 推播通知管理
├─ M4 推播裝置
└─ M5 App 設定與連線檢查

E. 商業模組                          （擴充既有模組）
├─ E1 合作夥伴                        （既有）
├─ E2 贊助商與方案                    （既有）
├─ E3 提案下載與 Lead                 （既有）
├─ E4 廣告主與版位管理                （新增）
├─ E5 廣告投放檔期與素材              （新增）
└─ E6 廣告成效報表                    （新增）
```

**為什麼廣告放 E 而不放 M**：權限最小化。業務人員要賣廣告，不該連帶取得 App 版本發布權與推播發送權——**推播發錯是全體使用者等級的事故，版本發布錯是全體使用者當機**。且同一家公司可能既是 `Sponsor` 又是 `Advertiser`，放在同一模組才不會兩邊各建一套聯絡窗口。

> **命名注意**：後台模組代號 `M` 與電子會員卡的公開驗證頁路徑 `/m/<token>` 是**不同的命名空間**，兩者無關。

**為什麼藍鯨的內容維護不新增模組**：藍鯨維護的是既有型別（`Team`／`Player`／`Staff`／`Match`／`Article`），用的是既有模組（B 內容、C 球隊與賽事）。**需要新增的不是模組，是「資料範圍權限」**——同一個模組，不同帳號看到不同的資料子集（§11）。新增模組反而會製造第二套球員維護介面，違反「App 不建立平行內容維護介面」的前提。

> **俱樂部主檔與後台帳號授權由主站 `J4 俱樂部與授權管理` 承載。** 理由與 `Club` 型別定義於主站相同——該範疇**屬於系統管理，且與 App 無關**（官網後台也要用）。放在 `M` 模組會讓「只做網站不做 App」的情境下找不到俱樂部設定。`M` 模組為 M1–M5。

### 8.1 M1 App 版本與發布管理

- 版本清單：平台、版本號、建置號、發布日期、狀態（測試／已上架／已下架）
- **最低支援版本設定**：低於此版本的 App 啟動時要求更新
- **強制更新**與**建議更新**兩種模式，各自可設定提示文案（中英）
- 維護模式：可全域或分平台開啟，顯示自訂維護訊息
- 版本更新說明（What's New）文案管理，中英雙語

### 8.2 M2 App 內容編排與深連結

- **首頁區塊的開關與排序**（對應 §3.1 的九個區塊）
- 快捷入口的項目與排序
- 「更多」分頁的項目與排序
- 深連結對照表管理：App 畫面 ↔ 官網網址，供推播與廣告素材選用
- App 專屬公告條：文案（中英）、連結、顯示期間、目標對象

**不做**：App 內的內容 CRUD。所有內容（新聞、賽事、球員、店家）仍在既有模組維護，M2 只管**呈現順序與開關**。

### 8.3 M3 推播通知管理

- 推播批次：標題與內文（中英）、圖片、深連結目的地、分眾條件、排程時間
- **發送前分眾人數試算**（只回人數，不寫入）
- 預覽（雙語各一）、指定測試裝置試送
- 發送、取消未送達批次、失敗重送
- 發送紀錄：批次、時間、操作者、觸及裝置數、送出／送達／開啟數
- 自動推播的規則設定（賽事提醒提前時數、到期提醒天數等）

**系統層阻擋**：M3 須阻擋任何以中獎名單為對象的推播，並阻擋帶有 `球迷會員抽獎` 標籤文章的自動推播（見 §6.8）。

### 8.4 M4 推播裝置

- 裝置清單：平台、OS 版本、App 版本、語系、推播權限狀態、綁定會員、最後活躍
- 統計：各平台與版本的裝置分佈（供決定最低支援版本）
- 失效權杖清理
- **權限**：推播權杖與裝置識別碼視同個資，僅系統管理員可見完整值，其他角色見遮罩

### 8.5 M5 App 設定與連線檢查

- App 端功能開關（Feature Flag）：可遠端關閉單一功能而不需送審新版
- **憑證管理**：APNs 憑證、FCM 設定——記錄有效期並於到期前 60 天告警，輪替須寫入稽核日誌
- 診斷：崩潰率、API 錯誤率、啟動耗時的彙總檢視
- App 端錯誤回報的收件與檢視

### 8.6 俱樂部與資料範圍權限（主站 `J4`）

> **俱樂部主檔（`Club`）與後台帳號的資料範圍授權定義於主站規劃書 `4.10 J4 俱樂部與授權管理`**，含 `AdminUserClub`（授權起訖、到期自動失效）、`AdminUserTeam`、`AdminRole.scope_mode` 與資料存取層強制規則。本節只記與 App 相關的部分。
>
> ⚠️ **資料範圍權限是多俱樂部架構的前置條件，不是可延後的優化**：`club_id` 一旦鋪到約 40 張表，後台每個清單查詢都要決定要不要過濾；先當單一俱樂部開發、日後再補，等於重寫整個查詢層。
>
> App 端與此相關的只有一件事：**`Club` 的高倍圖（@2x／@3x）與深色版標誌是 App 特有需求**，網頁用 SVG 即可。建立 `Club` 時須一併上傳，見 §10.1 與 §16.2。

### 8.7 E4 廣告主與版位管理

- 廣告主 CRUD（欄位見 §7.3），可關聯既有 `Sponsor`
- 版位 CRUD（欄位見 §7.2），含備援素材上傳
- 版位預覽：顯示該版位在 App 中的位置示意

### 8.8 E5 廣告投放檔期與素材

- 檔期 CRUD（欄位見 §7.4）與狀態機操作
- 素材上傳與管理：雙語、深淺底、A/B 標記、alt 文字、點擊目的地
- **素材審核**：待審／通過／退回（含退回原因）
- 檔期衝突檢視：同版位同時段的檔期清單與權重佔比預覽
- **緊急暫停**：單一檔期或單一素材可立即停止投放

### 8.9 E6 廣告成效報表

見 §7.7。維度、指標、匯出與稽核規則同該節。

- 最低支援版本由後台 M1 控制，App 啟動時讀取設定端點判斷

### 9.5 錯誤格式與重試

- **統一錯誤結構**：錯誤代碼、可呈現給使用者的訊息（雙語）、是否可重試

- **離線佇列**：廣告事件與推播訂閱變更可離線暫存後補送；付款相關操作**不得離線佇列**
- 所有錯誤訊息不得洩漏內部實作細節

### 9.6 速率限制與冪等性

### 10.3 與既有型別的界線

**五種「商業對象」不可混用**——這是本專案最容易出錯的一組概念：

| 型別 | 是誰 | 在哪 | 金流 | 分潤 | 計曝光 |
|---|---|---|---|---|---|
| `Partner` | B2B 合作夥伴 | 官網 9.1 Logo 牆 | 無 | 無 | 否 |
| `Sponsor` | 贊助商 | 官網 9.2 | 無（線下合約） | 無 | 否 |
| `PartnerStore` | 特約店家（會員折扣） | 官網 8.4、App §3.8 | 無 | 無 | 否 |
| `DonationStore` | 慈善站掃碼引流店家 | 慈善捐款平台 | **有** | **有** | 否 |
| **`Advertiser`** | **廣告主** | **App 廣告版位** | 線下合約 | 無 | **是** |

同一家實體公司可能同時是其中數種，**各建一筆、不共用紀錄**。唯一的例外是 `Advertiser.sponsor_id` 可關聯回 `Sponsor`，用途是避免重複維護聯絡窗口，**不是把兩者合併成一筆**。

**其他界線**：

| 情況 | 正確做法 |
|---|---|
| 抽獎名單 | `DrawRoster` 是**不可變快照**，App **不得讀取**。App 只讀 `Member` 的即時會籍狀態與 `MemberDraw` 的公開欄位 |
| 抽獎資格 | `Member` 層級的**布林判定**，不存在「抽獎報名」「抽獎券」「點數」型別 |
| 課程時段 | 屬 `Session`，**不進 `CalendarEvent`**。App 的「我的報名」可顯示時間，但不得寫入行事曆型別 |
| 球迷會員 | 不是獨立名單，是 `Member` 上的 `fan_club` 層級標記 |
| 家庭會籍 | 只是 `MembershipPlan` 的 `card_quota`／`jersey_quota` 不同，**不建立學員綁定關係** |
| **俱樂部 vs 球隊** | `Club` 是法人與品牌（磐石、藍鯨），`Team` 是隊伍（D1、BW1、U15…）。**一個 `Club` 有多個 `Team`**。深連結與行事曆訂閱用 `Team.code`，Logo 與分區用 `Club` |
| **`Club` vs 五種商業對象** | `Club` 是**內容主體**，不是第六種商業對象。它不計曝光、無金流、無分潤，也不與 `Partner`／`Sponsor` 合併——藍鯨是共同主體，不是俱樂部的贊助商或夥伴 |
| **會籍 vs 俱樂部** | 會籍屬 `Member`，**與 `Club` 無任何關聯**。App 內不存在「磐石會籍」與「藍鯨會籍」 |
| 廣告曝光 vs 贊助曝光 | `AdEvent` 只記錄 `AdCreative` 的曝光。贊助商 Logo 牆**不產生任何 `AdEvent`** |
| 裝置 vs 會員 | `AppDevice` 可獨立存在（未登入亦註冊），`member_id` 為可空的弱關聯，登出即解除 |

### 10.4 雙語欄位規則

沿用主站規則，無例外：

1. **所有 App 內可見的內容型別都必須有 `zh` / `en` 雙欄位**，英文可空但欄位必須存在。
2. 英文缺漏時 fallback 繁中並標示。
3. 架構須能再加第三語系而不改程式。
4. **廣告素材與推播文案同樣適用**——`AdCreative` 依語系分別上傳，`PushMessage` 標題與內文須雙語。

1. **App 版本發布與強制更新（M1）僅限系統管理員**——誤設最低支援版本會讓全體使用者無法使用。
2. **推播發送（M3）須雙人覆核**：公關／媒體可建立與預覽，實際發送需系統管理員核可。推播是不可撤回的全體觸及行為。
3. **推播權杖與裝置識別碼（M4）視同個資**，僅系統管理員可見完整值，其他角色見遮罩。
4. **廣告合約金額**僅商務／贊助與財務可見，其他角色見「不公開」。
5. **廣告成效報表匯出須寫入稽核日誌**（誰、何時、哪個檔期、用途備註），比照會員名單匯出的既有規則。
6. **資料範圍限制必須在 API 層強制**（v2.0）。介面隱藏不算數——擋不住直接呼叫端點，也擋不住匯出功能。
7. **合作球隊帳號只接觸自家的會員資料，且 `Member` 主檔遮罩**（v3.0 改寫）。
   v2.0 原訂「絕不接觸會員資料」，理由是「會籍是俱樂部與會員的收款關係，藍鯨只是內容提供方」。**v3.0 起藍鯨有自己的會籍**，該前提不成立——**藍鯨的客服不能看自家會員，系統就沒法用**。
   改為：**可存取自家 `club_id` 的會籍、付款、球衣與報名紀錄；`Member` 主檔的姓名、Email、電話、生日與 LINE 綁定一律回傳遮罩值**，完整值須另行授權並寫入稽核；**對方俱樂部的任何會籍列一律不可見**。
   ⚠️ **開通前須確認合作範圍與存取欄位**，並於後台 `J4` 設定授權起訖。
8. **合作球隊帳號的授權有起訖日**（v2.0），到期自動失效。合作關係結束時若靠人工記得停用，必然會漏。落地為 `AdminUserClub.expires_on`。
9. **共同內容（`club_id` 為空）對本角色唯讀**（v3.0 新增）。否則「查得到共同內容」與「不能改到別人的內容」兩件事無法同時成立，見主站規劃書 5.4。
10. **第一階段可先不指派使用者**（v3.1）。若藍鯨內容由既有團隊以自己的帳號維護，就不需要另開合作球隊帳號。
    **但資料範圍權限仍然要做**——`club_id` 已鋪到約 40 張表，是系統地基，補在後面等於重寫查詢層。**角色定義先建好、先不指派使用者即可，不擋上線。**

**維持不變**：對方俱樂部的會員資料、推播、廣告與系統管理權限**一律不開放**，這幾條不因雙會籍而放寬。

> ✅ **主站規劃書已備妥資料範圍權限**：`AdminUserClub`／`AdminUserTeam` 兩張授權表、`AdminRole.scope_mode`、`Permission.is_club_scoped`，以及「資料範圍必須在資料存取層強制」的執行期規則。
> **本角色第一階段可先不指派使用者**——若藍鯨內容由既有團隊以自己的帳號維護，就不需要另開合作球隊帳號。資料範圍權限仍要做（系統地基），**但不擋上線**。詳見 §8.6。

1. **特約店家附近地圖排在 Phase B 而非更後面**，因為它成本低、無內容阻塞，且直接支撐付費會籍的價值主張——它與電子會員卡是同一組使用體驗，拆開做會讓 Phase B 少掉一半說服力。
