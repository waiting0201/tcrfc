## 1. 專案目標與範圍

### 1.1 定位

本 App 不是官方網站的縮小版，也不是把網頁包進殼裡。它存在的理由，是**做網站做不到的事**。

判斷一項功能該不該進 App，只用兩個標準，兩者滿足其一即可：

| 標準 | 說明 |
|---|---|
| **手機才做得到** | 需要定位、離線、推播、行動錢包、鎖定畫面、原生行事曆、相機等裝置能力 |
| **資料已在既有規格內** | 沿用官網後台既有的內容型別，不需要客戶額外產出內容即可上線 |

兩者皆不滿足的功能一律不納入——那只會做出一個比網站慢、比網站難維護的網站。

三個設計前提決定了整個 App 的樣貌：

| 前提 | 對設計的影響 |
|---|---|
| **App 與官網共用同一套資料** | App 不建立任何平行的內容維護介面。所有內容仍在官網後台維護，App 是第二個呈現端，不是第二個真實來源 |
| **會員在球場、在店家櫃檯使用** | 現場常常沒有網路。電子會員卡、已快取的賽程與已讀新聞**必須離線可用** |
| **廣告是自售，不是聯播網** | 版位賣給在地商家，成效由自家系統量測。因此不需要廣告 SDK、不需要追蹤許可、不做行為定向 |

### 1.2 與官方網站、慈善捐款平台的關係

| 項目 | 做法 |
|---|---|
| **後台** | **共用官方網站後台**，新增 `M. 行動 App` 模組，並擴充既有的 `E` 商業模組（E5–E7 廣告） |
| **資料庫** | **共用同一套資料庫**，App 讀取的是官網後台維護的同一份 `Match`、`Article`、`Member`、`PartnerStore` 等資料 |
| **主體** | 主體是**台中磐石足球俱樂部**。收款主體亦為俱樂部，**與慈善捐款平台的協會主體完全分離** |
| **官網的角色** | 官網仍是 SEO 與對外內容的主體。App 不承接 SEO 責任；官網另需提供 App 下載頁與 Universal Link 驗證檔（見 §2.3） |
| **慈善捐款平台的角色** | **App 不承接任何捐款金流**。至多於慈善單元提供外連，且須明示收受者為台灣足球策略發展協會，不得讓使用者誤以為捐給俱樂部 |

三份規格的分工：

| 文件 | 承載什麼 | 主體 |
|---|---|---|
| `TCRFC_前後台功能規劃書.md` | 官方網站前台 13 單元、後台 A–L 模組、全部內容型別的定義 | 俱樂部 |
| `TCRFC_慈善捐款平台功能規劃書.md` | 掃碼捐款站台、LINE Pay、電子發票、分潤結算、後台 N 模組 | **協會** |
| `TCRFC_行動App功能規劃書.md`（本文件） | 行動 App 前台、後台 M 模組與 E5–E7、App 專屬型別、API 規範 | 俱樂部 |

**衝突處理原則**：內容型別與後台既有模組的定義，一律以主站規劃書為準；本文件只定義 App 專屬的新增與擴充。

| 11 | 夥伴與贊助商 | Logo 牆與詳情頁、官網連結 |

**不在本次範圍**

| 項目 | 理由 |
|---|---|
| **店家掃碼核銷、集點、核銷報表** | 主站 8.4 已定案不做。一旦做了就要幫店家開帳號、做核銷報表，等於長出第二套系統 |
| **會員點數、電子錢包（儲值）、票務與門票套票** | 主站已定案不做，不因 App 而改變 |
| **球迷相片牆、UGC 投稿、留言板** | 素材含未成年學員，開放上傳等於把審核責任攬上身 |
| **App 內捐款** | 收款主體是協會不是俱樂部。俱樂部的 App 收慈善款會直接踩到勸募資格問題。至多外連 |
| **課程費用線上支付** | 官網 P3 明訂課程繳費為線下作業。課程退費規則遠比會籍複雜，納入會讓 §5 從一件事變成兩件事 |
| **學員家長綁定** | 建立「成人↔未成年」的持久關聯，敏感度高一級。家庭會籍當初即刻意避開此設計 |
| **開屏廣告（Splash Ad）** | 最容易引發負評的版位，影響啟動體驗與商店審查觀感 |
| **即時比分自動更新** | 賽事資料全部人工維護，做不到「即時」，做了只會失信 |
| **第三方廣告聯播網** | 見 §7.8。自售是刻意的選擇，不是能力不足 |
| **站內商城、購物車、訂單、庫存** | 商品一律導向 Shopify，與主站規則一致 |
| **女足名單與賽程** | 導向台中藍鯨女足官網，與主站規則一致 |
| **SEO／GEO 優化** | App 內容不由搜尋引擎索引。官網的 App 下載頁仍適用主站 SEO 規範 |
| **技術選型** | 本文件為功能規格，不涉及框架、CMS、部署環境等技術決策 |

### 1.4 名詞定義

| 名詞 | 定義 |
|---|---|
| **版位（Slot）** | App 畫面上一個固定的廣告呈現位置，長期存在，由 `slot_code` 識別 |
| **檔期（Campaign）** | 一個廣告主在一個版位上、一段期間內的投放。同一版位同時段可有多個檔期輪播 |
| **素材（Creative）** | 檔期底下的實際圖片或影片，含標題、CTA 與點擊目的地。一個檔期可掛多個素材做 A/B 與雙語 |
| **曝光（Impression）** | 廣告區域 **≥50% 面積連續可見 ≥1 秒**。輪播中每一則各自計算 |
| **裝置（Device）** | 一次 App 安裝。以 `device_install_id` 識別，解除安裝即失效，不跨 App、不跨裝置 |
| **深連結（Deep Link）** | 可直接開啟 App 內特定畫面的連結，含自訂 scheme 與 Universal Link 兩種 |
| **強制更新** | 舊版 App 因相容性或安全理由被停止服務，啟動時要求使用者更新 |
| **行動錢包（Wallet）** | Apple Wallet 與 Google Wallet。電子會員卡可寫入其中，於鎖定畫面直接出示 |
| **資格基準時間** | 抽獎名單凍結的時間點，沿用主站 `MemberDraw.snapshot_at` 定義 |

### 1.5 平台能力需求（取代技術選型）

技術選型不在本文件範圍，但 App 的功能可行性有其底線。以下是**必須具備的平台能力**，任何技術方案只要能滿足即可採用：

| # | 能力 | 為什麼是必要的 |
|---|---|---|
| 1 | **原生推播（APNs／FCM）** | §6 全部功能的前提 |
| 2 | **離線讀取本機快取** | 會員卡在球場沒訊號時必須能出示；已讀新聞與已載入賽程須離線可讀 |
| 3 | **深連結與 Universal Link** | 推播點擊落地、網頁分享回 App、廣告素材導向 App 內畫面 |
| 4 | **前景可見度量測** | §7.5 曝光定義的前提。無法精確判定元件可見面積與持續時間，廣告成效就無法對帳 |
| 5 | **裝置定位授權（僅前景）** | §3.8 附近特約店家的距離排序 |
| 6 | **行動錢包 pass 寫入與遠端更新** | §3.6 電子會員卡 |
| 7 | **系統行事曆寫入** | §3.2 賽事加入行事曆 |
| 8 | **商店內購或外部付款連結的合規路徑** | §5.5 |
| 9 | **生物辨識解鎖**（選配） | 會員卡快速開啟 |

> 這份清單實質上排除了「純 WebView 外殼」的方案（第 4、6 項難以精確達成），但這是**功能需求的結果**，不是技術偏好。

### 2.1 分頁架構

底部固定五個分頁，深度不超過三層：

| 分頁 | 內容 | 需登入 |
|---|---|---|
| **首頁** | 下一場賽事、最新消息、廣告版位、快捷入口、贊助商 Logo 牆 | 否 |

### 2.3 深連結與 Universal Link

**兩種機制並行**：自訂 scheme `tcrfc://` 供 App 內部與推播使用；Universal Link／App Links 讓官網網址在已安裝 App 的裝置上直接開啟 App。

**畫面與網址的一對一對照**（未安裝 App 時，同一網址須在官網呈現對應內容）：

| App 畫面 | 深連結 | 官網對應網址 |
|---|---|---|
| 賽程（指定隊別） | `tcrfc://schedule/d1` | `/zh/schedule/d1/` |
| 賽事詳情 | `tcrfc://match/{id}` | `/zh/schedule/{slug}` |
| 新聞內文 | `tcrfc://news/{slug}` | `/zh/news/{slug}` |
| 球員詳情 | `tcrfc://player/{slug}` | `/zh/club/first-team/player/{slug}` |
| 特約店家詳情 | `tcrfc://store/{id}` | `/zh/perks/{slug}` |
| 課程詳情 | `tcrfc://program/{slug}` | `/zh/programs/{slug}` |
| 會員卡 | `tcrfc://membercard` | （無對應公開頁） |
| 會籍升級 | `tcrfc://upgrade` | `/zh/member/upgrade/` |

**對官網的依賴（須由網站專案配合）**：

1. `.well-known/apple-app-site-association` 與 `.well-known/assetlinks.json` **必須由官網網域提供**，內容需 Apple Team ID 與 Android package name，取得後才能填寫。
2. 官網須新增 App 下載頁（`/zh/app/`、`/en/app/`）與頁尾連結。
3. 未安裝 App 的裝置點擊深連結時，一律回退至對應官網網址，**不得顯示錯誤頁**。

### 2.4 離線與快取策略

| 內容 | 快取策略 | 時效 | 離線可用 |
|---|---|---|---|
| **電子會員卡** | 登入後立即快取，每次啟動嘗試更新 | 永久保留，標示同步時間 | ✅ **必須** |
| 賽程與賽果 | 啟動時更新整季 | 6 小時 | ✅ |
| 新聞列表 | 下拉更新 | 30 分鐘 | ✅ |
| 新聞內文 | 開啟過即快取 | 30 天 | ✅ |
| 特約店家 | 啟動時更新 | 24 小時 | ✅（不含即時距離） |
| 球員與球隊 | 啟動時更新 | 24 小時 | ✅ |
| 漫畫集數 | 使用者主動下載 | 使用者主動刪除 | ✅ |
| 會籍狀態與抽獎資格 | 每次進入畫面更新 | 不快取顯示為「有效」 | ❌ |
| 廣告素材 | 預先下載當日檔期素材 | 檔期結束即清除 | ❌（離線不計曝光） |
| 課程梯次與名額 | 不快取 | — | ❌ |

**兩條硬規則**：

1. **離線時不得計算廣告曝光**。曝光事件可在離線時暫存並於連線後回傳，但**必須帶原始發生時間**，且伺服器端須拒收超過 24 小時的事件——否則廣告成效可被人為堆積。
2. **會籍狀態不得以快取值宣告有效**。會員卡離線可出示，但卡面須標示「最後同步：YYYY-MM-DD HH:mm」；超過 7 天未同步時，卡面須顯示提醒。否則已過期的會員可用飛航模式出示舊卡。

### 2.5 雙語與語系決定規則

沿用主站 G-01 的雙語原則（繁中預設、英文為譯本、未翻譯 fallback 繁中並標示、架構預留第三語系），App 端另定三條：

1. **首次啟動跟隨裝置語系**；裝置語系非繁中或英文時，預設繁中。
2. **會員登入後改跟隨帳號的語系偏好**（`Member` 既有欄位）。在 App 內變更語系時同步寫回帳號。
3. **推播語系以裝置註冊時的語系為準**（`AppDevice.lang`），與帳號語系不同時以帳號為優先。

**所有 App 內可見的內容型別都必須有 `zh` / `en` 雙欄位**，英文可空但欄位必須存在——與主站規則一致。

## 5. App 內付款（LINE Pay）

### 5.1 範圍變更聲明

主站規劃書原訂「官網不建購物車、不接金流、不存卡號」，並於 §3.14 註明「LINE Pay API 站內結帳／退款／對帳不在範圍，**要做須先改第 10 章前提**」。

**本節即為該項修訂。**主站規劃書 v2.5 已據此將「不接金流」**第二次限縮**：

| 對象 | 金流 | 收款主體 |
|---|---|---|
| 官網網頁前台 | **仍不接金流**，維持收款連結與現場收款 | 俱樂部 |
| 慈善捐款平台 | 串接 LINE Pay Online API | **協會** |
| **行動 App（本文件）** | **串接 LINE Pay，僅限會籍費用** | **俱樂部** |

「**不存卡號**」一條**維持全域適用**——App 同樣不落地任何卡號資料。

**本節僅涵蓋會籍費用。**課程費用、商品、捐款均不在範圍。

### 5.2 收款主體與商店號

> **這是本節最容易出錯、後果最嚴重的一條。**

慈善捐款平台使用的是**台灣足球策略發展協會**的 LINE Pay 特約商店號。本 App 的會籍收款主體是**台中磐石足球俱樂部**，**必須申請並使用俱樂部自己的商店號，不得共用**。

收款主體錯誤會同時觸犯兩件事：稅務上的收入歸屬錯誤，以及《公益勸募條例》——協會的勸募商店號不得用於收取俱樂部的商業性會費。

**上線前提**：俱樂部的 LINE Pay 特約商店號尚未申請（見 §16.2）。未取得前本節無法實作。

發票開立責任歸屬於俱樂部，抬頭為俱樂部，與慈善平台的協會抬頭完全分離。

### 5.3 付款狀態機

```
建立訂單 → 待付款 → 已付款 → 已開通
              ↓         ↓
            已逾時    開通失敗（人工處理）
              ↓
            已取消

另有：已退款（僅後台人工發起）
```

| 狀態 | 說明 |
|---|---|
| `建立訂單` | 產生訂單編號與冪等鍵，尚未跳轉付款 |
| `待付款` | 已跳轉 LINE Pay，等待使用者完成 |
| `已付款` | 收到 LINE Pay 確認，款項已收 |
| `已開通` | 會籍已生效，`paid_until` 已寫入 |
| `已逾時` | 逾時未完成付款（建議 15 分鐘），訂單自動關閉 |
| `開通失敗` | 已收款但開通異常，**須立即告警並由客服人工處理**，不得靜默失敗 |
| `已退款` | 僅後台人工發起，見 §5.6 |

### 5.4 兩段式流程與冪等性

| 步驟 | 動作 |
|---|---|
| 1 | App 建立訂單，帶方案代碼與**冪等鍵**（同一鍵重複請求只成立一筆訂單） |
| 2 | 伺服器向 LINE Pay 請求付款，回傳付款頁 |
| 3 | 使用者完成付款，LINE Pay 回呼伺服器 |
| 4 | 伺服器**驗證回呼來源與金額**，標記為已付款 |
| 5 | 伺服器呼叫 `POST /api/membership/activate` 開通會籍 |
| 6 | 寄送「會籍開通確認」信（既有五封系統信之一），並推播通知 |
| 7 | 推送行動錢包 pass 更新（見 §3.6） |

**三條硬規則**：

1. **開通一律以伺服器端回呼為準，不得以 App 端回報的付款結果開通會籍。**
2. **金額須於伺服器端重新計算並比對**，不得信任 App 傳來的金額。
3. **`POST /api/membership/activate` 必須具備冪等性**——重複回呼不得重複延長會籍。

> 主站設計此端點時即註明「日後若改採自動收款，只需更換觸發來源，會員模組不動」。本節正是該設計的兌現：**會員模組的開通邏輯完全不變，只是觸發者從客服人員換成付款回呼。**

### 5.5 商店內購（IAP）判定

> **這是本 App 最大的單一上架風險。**

Apple 要求 App 內販售**數位內容與服務**時必須使用內購（IAP）。付費會籍的權益以**實體為主**——入會球衣（實體物品）、特約店家折扣（實體通路消費）、抽獎的實體獎品、球迷活動優先報名（實體活動）——因此有相當理由主張屬於「實體商品與服務」，得使用外部付款。

**但這是審查判斷，不是規則明文，必須預先準備兩條路：**

| 方案 | 做法 | 代價 |
|---|---|---|
| **A（首選）** | App 內以 LINE Pay 完成付款，主張權益為實體商品與服務 | 若審查不通過須改版重送 |
| **B（fallback）** | App 內只顯示方案與付款指引，**外開瀏覽器**完成付款（等同官網現行做法），付款完成後回到 App | 流程斷裂，轉換率下降 |
| **C** | 申請 External Purchase Link Entitlement（依各地區規定） | 申請流程與適用地區須另行確認 |

**規格要求**：付款流程須設計為**可切換**——方案 A 與 B 共用同一組訂單與開通邏輯，差別只在付款頁是 App 內或外部瀏覽器。**不得把付款流程寫死成只支援其中一種**，否則審查一旦不通過就要重寫。

若判定須走 IAP，商店抽成將直接侵蝕會費毛利，且 IAP 無法對接 LINE Pay 與後台既有的開通流程——此情境下應優先採方案 B。

### 5.6 退款、對帳與憑證

| 項目 | 規範 |
|---|---|
| 前台 | **App 內不提供退款申請**。會籍屬期間性服務，比照官網現行規則 |
| 後台 | 誤刷、重複扣款等個案由客服受理後人工退款，須**獨立授權**並寫入稽核日誌 |
| 對帳 | 後台提供 LINE Pay 交易與 `MembershipPayment` 的對帳報表，差異須可標記與註記 |
| 發票 | 由俱樂部開立，抬頭為俱樂部。**與慈善平台的協會發票流程完全分離，不共用開立設定** |
| 會籍處理 | 退款後會籍狀態須同步回復，`paid_until` 沖回並記錄異動原因 |

## 7. 自售廣告版位與成效統計

### 7.1 範圍變更聲明

主站規劃書兩處明文「不另設固定版位」（首頁區塊編排、B4 Banner 管理），其對象是**官網首頁的檔期內容編排**，本意是防止首頁被版位切碎。

主站規劃書 v2.5 已將該條限定為「**本站網頁前台**不另設固定版位」，並註明行動 App 的自售廣告版位屬 App 範圍，**不影響官網首頁編排**。

**一項例外維持不變**：**首頁不設固定慈善版位，App 亦不做慈善相關版位。**慈善捐款的主辦與收款主體是協會，俱樂部的 App 不得販售或贈與慈善相關版位，以免與協會尚未確認的勸募資格混淆。

### 7.2 版位定義

版位是長期資產，建立後很少變動。

| 欄位 | 說明 |
|---|---|
| `slot_code` | 唯一識別碼，命名規則 `<畫面>_<位置>`，例如 `home_top` |
| 名稱（中／英） | 對業務與廣告主呈現的名稱 |
| `surface` | `app`（預留 `web`，日後若官網開版位不需搬表） |
| 畫面位置 | 對應 §2.2 的畫面代碼與區塊順序 |
| 素材規格 | 長寬比、最小像素、檔案大小上限、允許格式 |
| 是否允許影片 | 布林 |
| 單次 session 曝光上限 | 防止同一次使用中反覆曝光 |
| 輪播張數上限 | 同時段最多幾個檔期參與輪播 |
| **備援素材** | 無檔期或載入失敗時顯示的自家內容，**版位永不空白** |
| 啟用狀態 | 上／下架 |

**兒童向畫面不設版位**：漫畫、學院、課程相關畫面不建立 `AdSlot`（見 §3.13）。

### 7.3 廣告主與合約

| 欄位 | 說明 |
|---|---|
| 名稱（中／英）、統一編號、聯絡窗口、電話、Email | 基本資料 |
| **`sponsor_id`** | **可為空**，指向既有 `Sponsor` |
| 合約備註、合作起訖 | |
| 狀態 | 洽談中／合作中／已結束 |

**`sponsor_id` 是關鍵設計**：同一家公司既是贊助商又購買廣告時，不重複建檔、不混淆兩者的成效歸屬，也不需要兩邊各維護一套聯絡窗口。

**v1 不做廣告主自助後台帳號**——比照慈善捐款平台「不做店家帳號」的既有取捨，報表由業務匯出後寄送。

### 7.4 投放檔期與輪播權重

| 欄位 | 說明 |
|---|---|
| `advertiser_id`、`slot_id` | 一個檔期綁一個版位。跨版位需求以多筆檔期表示，**不做多對多** |
| 名稱、起訖時間 | |
| `weight` | 輪播權重，同版位同時段依相對比例加權隨機 |
| 每日曝光上限 | |
| 每人頻次上限 | 同一裝置每日最多看到幾次 |
| `goal_type` | `曝光保證` / `導流` |
| `goal_impressions` | 曝光保證型的目標次數 |
| `delivered_today` | 當日已投遞計數，供 pacing 使用 |
| 合約金額 | **可設為不公開** |
| 狀態、審核者、建立者 | |

**狀態機**：

```
草稿 → 待審核 → 已排程 → 投放中 → 已結束 → 已結案
                            ↓
                         已暫停 →（可回投放中）

另有：已作廢（任一狀態可轉入，不可逆）
```

`已排程 → 投放中 → 已結束` 由起訖時間自動推進，其餘為人工操作。

**一條寫死的規則**：**素材未通過審核的檔期不得進入「投放中」。**否則會出現沒審過的圖直接上線。

**Pacing（曝光保證型必須做）**：目標曝光須平均分配到檔期天數。沒有 pacing 的話，檔期前兩天就會把保證量燒完，剩下的天數版位空著——這正是 `delivered_today` 欄位存在的理由，**不是可有可無的優化**。

### 7.5 曝光與點擊的定義

> 沒有這一節，廣告主報表無法對帳，版位就賣不出去。

| 事件 | 定義 |
|---|---|
| **有效曝光** | 廣告區域 **≥50% 面積連續可見 ≥1 秒**（比照 IAB／MRC 通行標準）。輪播中每一則各自計算 |
| **有效點擊** | 使用者主動點擊素材。**同一裝置對同一素材 5 秒內的重複點擊只計 1 次** |
| 無效流量 | 離線暫存超過 24 小時的事件、同一裝置異常高頻的事件，一律排除且不計費 |
| 不計曝光 | 版位顯示備援素材時、App 在背景時、廣告載入失敗時 |

**時間基準**：事件以**發生時間**記錄，不以上傳時間記錄。離線暫存的事件回傳時須帶原始發生時間，伺服器端拒收超過 24 小時者。

### 7.6 事件蒐集與聚合

| 層級 | 內容 | 保存期限 |
|---|---|---|
| **原始事件** `AdEvent` | 逐筆曝光與點擊 | **90 天**（供爭議稽核與去重） |
| **日聚合** `AdDailyStat` | 日期 × 檔期 × 素材 × 版位 × 平台 × 語系 | 長期保存 |

**為什麼要分兩層**（資料量估算，附假設）：

| 假設日活躍裝置 | 每人每日曝光 | 事件／日 | 事件／年 | 原始資料量 |
|---|---|---|---|---|
| 500 | 15 | 7,500 | 約 270 萬 | 約 270 MB |
| 2,000 | 20 | 40,000 | 約 1,460 萬 | 約 1.5 GB |
| 5,000 | 25 | 125,000 | 約 4,560 萬 | 約 4.6 GB |

原始事件無限期保留會讓資料庫在一年內膨脹到數 GB，而報表實際只需要聚合值。**90 天保留期同時是個資保存期限政策**，符合主站非功能性需求對保存期限的要求。

**聚合作業**：每日定時執行，聚合完成後標記 `aggregated_at`；聚合失敗須告警，不得靜默跳過。

### 7.7 廣告主報表（後台 E7）

| 項目 | 內容 |
|---|---|
| 維度 | 檔期／版位／素材／平台／語系／日期 |
| 指標 | 曝光數、點擊數、CTR、不重複裝置數、按日趨勢 |
| 對照 | 曝光保證型顯示「目標 vs 已達成」與 pacing 進度 |
| 匯出 | CSV 與 PDF，**須寫入稽核日誌**（誰、何時、哪個檔期、用途） |
| **不提供** | 任何個人層級資料、裝置清單、會員身分關聯 |

### 7.8 隱私與量測誠信

三個決定，一次解決三類問題：

| 決定 | 連帶效果 |
|---|---|
| **不接第三方廣告聯播網**，只做自售 | 不需要追蹤許可提示；商店隱私標籤可宣告「不追蹤」；不存在廣告 SDK 的兒童合規問題 |
| **不使用廣告識別碼（IDFA／AAID）** | 去重僅用 `device_install_id`（解除安裝即失效、不跨 App），不重複裝置統計採當日雜湊 |
| **不做行為定向** | 分眾只到「版位 × 語系 × 平台」，不依個人瀏覽紀錄選擇廣告 |

**這三條同時是給廣告主的說明，而且是賣點**：「我們的數據是自家系統直接量測的誠實數據，不是聯播網轉手的估算值。」

`AdEvent` **明確不儲存**：`member_id`、完整 IP 位址、精確定位座標、廣告識別碼。

### 7.9 廣告揭露與法遵

1. **每個版位必須有「廣告」或「贊助內容」標示**，不得誤導為編輯內容。
2. 廣告素材不得使用俱樂部標誌或暗示官方背書，除非該廣告主確為贊助商且合約載明。
3. 素材內容須經後台審核通過方可上線；發現違規或申訴時須有**即時下架機制**（單一檔期可立即暫停）。
4. **不得刊登**：菸酒、博弈、成人內容、醫療效能宣稱、金融投資招攬。
5. 針對未成年受眾的畫面不置放廣告（見 §3.13）。

## 8. 後台功能規劃

### 8.0 模組總覽

App 相關的後台功能分為兩部分，**刻意不放在同一個模組**：

```
M. 行動 App                          （新增一級模組）
├─ M1 App 版本與發布管理
├─ M2 App 內容編排與深連結
├─ M3 推播通知管理
├─ M4 裝置與推播權杖
└─ M5 App 設定、憑證與診斷

E. 商業模組                          （擴充既有模組）
├─ E1 合作夥伴                        （既有）
├─ E2 贊助商與方案                    （既有）
├─ E3 提案下載與 Lead                 （既有）
├─ E4 商品櫥窗                        （既有）
├─ E5 廣告主與版位管理                （新增）
├─ E6 廣告投放檔期與素材              （新增）
└─ E7 廣告成效報表                    （新增）
```

**為什麼廣告放 E 而不放 M**：權限最小化。業務人員要賣廣告，不該連帶取得 App 版本發布權與推播發送權——**推播發錯是全體使用者等級的事故，版本發布錯是全體使用者當機**。且同一家公司可能既是 `Sponsor` 又是 `Advertiser`，放在同一模組才不會兩邊各建一套聯絡窗口。

> **命名注意**：後台模組代號 `M` 與電子會員卡的公開驗證頁路徑 `/m/<token>` 是**不同的命名空間**，兩者無關。

### 8.1 M1 App 版本與發布管理

- 版本清單：平台、版本號、建置號、發布日期、狀態（測試／已上架／已下架）
- **最低支援版本設定**：低於此版本的 App 啟動時要求更新
- **強制更新**與**建議更新**兩種模式，各自可設定提示文案（中英）
- 維護模式：可全域或分平台開啟，顯示自訂維護訊息
- 版本更新說明（What's New）文案管理，中英雙語

### 8.2 M2 App 內容編排與深連結

- **首頁區塊的開關與排序**（對應 §3.1 的九個區塊）
- 快捷入口的項目與排序
- 「更多」分頁的項目與排序
- 深連結對照表管理：App 畫面 ↔ 官網網址，供推播與廣告素材選用
- App 專屬公告條：文案（中英）、連結、顯示期間、目標對象

**不做**：App 內的內容 CRUD。所有內容（新聞、賽事、球員、店家）仍在既有模組維護，M2 只管**呈現順序與開關**。

### 8.3 M3 推播通知管理

- 推播批次：標題與內文（中英）、圖片、深連結目的地、分眾條件、排程時間
- **發送前分眾人數試算**（只回人數，不寫入）
- 預覽（雙語各一）、指定測試裝置試送
- 發送、取消未送達批次、失敗重送
- 發送紀錄：批次、時間、操作者、觸及裝置數、送出／送達／開啟數
- 自動推播的規則設定（賽事提醒提前時數、到期提醒天數等）

**系統層阻擋**：M3 須阻擋任何以中獎名單為對象的推播，並阻擋帶有 `球迷會員抽獎` 標籤文章的自動推播（見 §6.8）。

### 8.4 M4 裝置與推播權杖

- 裝置清單：平台、OS 版本、App 版本、語系、推播權限狀態、綁定會員、最後活躍
- 統計：各平台與版本的裝置分佈（供決定最低支援版本）
- 失效權杖清理
- **權限**：推播權杖與裝置識別碼視同個資，僅系統管理員可見完整值，其他角色見遮罩

### 8.5 M5 App 設定、憑證與診斷

- App 端功能開關（Feature Flag）：可遠端關閉單一功能而不需送審新版
- **憑證管理**：APNs 憑證、FCM 設定、**Apple Pass Type ID**、**Google Wallet Issuer**——記錄有效期並於到期前 60 天告警，輪替須寫入稽核日誌
- 診斷：崩潰率、API 錯誤率、啟動耗時的彙總檢視
- App 端錯誤回報的收件與檢視

### 8.6 E5 廣告主與版位管理

- 廣告主 CRUD（欄位見 §7.3），可關聯既有 `Sponsor`
- 版位 CRUD（欄位見 §7.2），含備援素材上傳
- 版位預覽：顯示該版位在 App 中的位置示意

### 8.7 E6 廣告投放檔期與素材

- 檔期 CRUD（欄位見 §7.4）與狀態機操作
- 素材上傳與管理：雙語、深淺底、A/B 標記、alt 文字、點擊目的地
- **素材審核**：待審／通過／退回（含退回原因）
- 檔期衝突檢視：同版位同時段的檔期清單與權重佔比預覽
- **緊急暫停**：單一檔期或單一素材可立即停止投放

### 8.8 E7 廣告成效報表

見 §7.7。維度、指標、匯出與稽核規則同該節。

### 8.9 既有模組的擴充

本 App 需要對既有模組做四項小幅擴充，**均不改變既有功能**：

| 模組 | 擴充內容 | 對應章節 |

- 最低支援版本由後台 M1 控制，App 啟動時讀取設定端點判斷

### 9.5 錯誤格式與重試

- **統一錯誤結構**：錯誤代碼、可呈現給使用者的訊息（雙語）、是否可重試
- 網路錯誤與伺服器 5xx 可自動重試，採指數退避；4xx 不重試
- **離線佇列**：廣告事件與推播訂閱變更可離線暫存後補送；付款相關操作**不得離線佇列**
- 所有錯誤訊息不得洩漏內部實作細節

### 9.6 速率限制與冪等性

| 對象 | 要求 |

### 10.3 與既有型別的界線

**五種「商業對象」不可混用**——這是本專案最容易出錯的一組概念：

| 型別 | 是誰 | 在哪 | 金流 | 分潤 | 計曝光 |
|---|---|---|---|---|---|
| `Partner` | B2B 合作夥伴 | 官網 9.1 Logo 牆 | 無 | 無 | 否 |
| `Sponsor` | 贊助商 | 官網 9.2 | 無（線下合約） | 無 | 否 |
| `PartnerStore` | 特約店家（會員折扣） | 官網 8.4、App §3.8 | 無 | 無 | 否 |
| `DonationStore` | 慈善站掃碼引流店家 | 慈善捐款平台 | **有** | **有** | 否 |
| **`Advertiser`** | **廣告主** | **App 廣告版位** | 線下合約 | 無 | **是** |

同一家實體公司可能同時是其中數種，**各建一筆、不共用紀錄**。唯一的例外是 `Advertiser.sponsor_id` 可關聯回 `Sponsor`，用途是避免重複維護聯絡窗口，**不是把兩者合併成一筆**。

**其他界線**：

| 情況 | 正確做法 |
|---|---|
| 抽獎名單 | `DrawRoster` 是**不可變快照**，App **不得讀取**。App 只讀 `Member` 的即時會籍狀態與 `MemberDraw` 的公開欄位 |
| 抽獎資格 | `Member` 層級的**布林判定**，不存在「抽獎報名」「抽獎券」「點數」型別 |
| 課程時段 | 屬 `Session`，**不進 `CalendarEvent`**。App 的「我的報名」可顯示時間，但不得寫入行事曆型別 |
| 球迷會員 | 不是獨立名單，是 `Member` 上的 `fan_club` 層級標記 |
| 家庭會籍 | 只是 `MembershipPlan` 的 `card_quota`／`jersey_quota` 不同，**不建立學員綁定關係** |
| 廣告曝光 vs 贊助曝光 | `AdEvent` 只記錄 `AdCreative` 的曝光。贊助商 Logo 牆**不產生任何 `AdEvent`** |
| 裝置 vs 會員 | `AppDevice` 可獨立存在（未登入亦註冊），`member_id` 為可空的弱關聯，登出即解除 |

### 10.4 雙語欄位規則

沿用主站規則，無例外：

1. **所有 App 內可見的內容型別都必須有 `zh` / `en` 雙欄位**，英文可空但欄位必須存在。
2. 英文缺漏時 fallback 繁中並標示。
3. 架構須能再加第三語系而不改程式。
4. **廣告素材與推播文案同樣適用**——`AdCreative` 依語系分別上傳，`PushMessage` 標題與內文須雙語。

## 15. 開發階段與優先順序建議

| Phase | 內容 | 前置條件 |

**兩點說明**：

1. **特約店家附近地圖排在 Phase B 而非更後面**，因為它成本低、無內容阻塞，且直接支撐付費會籍的價值主張——它與電子會員卡是同一組使用體驗，拆開做會讓 Phase B 少掉一半說服力。
2. **內容相依的功能獨立成 Phase D**，避免 113 篇文稿與漫畫素材的交付進度卡住整個 App 上線。
