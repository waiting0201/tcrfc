# TCRFC 台中磐石足球俱樂部 — 慈善捐款平台功能規劃書

> **文件版本**：v1.3
> **建立日期**：2026-09-03（v1.3 修訂：2026-09-04）
> **品牌主張**：LOCAL ROOTS. GLOBAL PATHWAYS. 在地扎根 · 放眼世界

> **本文件的定位**
> 1. 本文件規範**慈善捐款平台**：一個以實體通路 QR Code 為入口、獨立網域的小額捐款站台，**共用官方網站的後台與資料庫**。
> 2. 與 [`TCRFC_前後台功能規劃書.md`](TCRFC_前後台功能規劃書.md)（v2.1 起）是**互補而非重疊**的兩份規格：官網主站不再承接任何捐款金流，主站單元 11「慈善與社會影響」只保留理念、計畫、事蹟與影響力數據的**介紹**，並將「球迷捐款」導流至本平台。
> 3. 主站規劃書 v2.1 已同步修訂三項前提：**捐款不再走 Shopify 品項與銀行匯款**、**志工報名移出範圍**、**「不接金流」的適用對象限縮為主站**。
> 4. 本文件為功能規格，**不涉及框架、CMS、部署環境等技術決策**（延續主站規劃書 §1.3 的既定前提）。

> **v1.3 修訂摘要——前台不提供退款**
> 1. **對外不受理退款**：捐款須知頁明寫「捐款一經完成，原則上不受理退款」，前台不再有退款規則、退款申請管道與任何退款承諾。
> 2. **後台仍保留退款能力**：誤捐、重複扣款、金額誤植等個案由客服受理後，於 N3 以人工退款處理。退款仍需**獨立授權**並寫入稽核日誌，§8.5 退款沖回與第四封退款通知信維持不變。
> 3. **發票作廢與折讓不受影響**：§5.4 屬稅法要求，且「開立錯誤」本來就要作廢，與退不退款是兩件事，維持原規格。
> 4. 捐款項目**不得附帶回饋品**：附回饋品可能使捐款被認定為買賣或附負擔贈與，進而落入消費者保護法的通訊交易解除權，與「不受理退款」的前提衝突。此限制寫入 §1.3 不在本次範圍。

> **v1.2 修訂摘要——移除募款進度**
> 1. **前台不呈現募款進度**：3.1 項目卡片牆與 3.2 項目詳情頁**移除**進度條、已募得金額、目標金額與捐款筆數。捐款人看到的是項目在做什麼、錢用在哪裡，不看數字進度。
> 2. **後台同步移除**：N2 捐款項目管理的「目標金額」欄位與「募款進度是否公開」顯示控制**一併取消**，資料模型 `DonationProject` 不再有目標金額欄位。
> 3. **後台仍看得到累計數字**：各項目的捐款筆數與累計金額由 **N6 捐款報表**提供（§7），只是不對前台公開。移除的是**前台呈現**，不是統計能力。
> 4. 原第 10 章尚待確認第 14 項「募款進度是否公開」**已定案為不做**，自待確認清單移除並寫入已定案前提表。

> **v1.1 修訂摘要——不做 SEO／GEO 優化**
> 1. **本平台不進行 SEO 與 GEO 優化**：不做關鍵字研究與內容經營、不寫結構化資料（`Schema.org` 標記）、不做 sitemap 提交與收錄監控、不做 AI 搜尋（GEO）優化，也**不設任何搜尋排名相關的驗收標準**。主站規劃書第 7 章的 SEO / GEO 規範**不適用於本平台**。
> 2. **頁面維持可被搜尋引擎索引**：掃碼落地頁與項目詳情頁不加 `noindex`，`hreflang` 三組仍須提供（避免雙語頁被判為重複內容），`/result/` 結果頁與捐款徵信頁的 `noindex` 規定不變。
> 3. 本次只調整**成效期待與工作範圍**，頁面清單、URL 結構、雙語欄位規則與其他所有功能**皆未變動**。

## 1. 專案目標與範圍

### 1.1 定位

以**實體通路的 QR Code** 為入口的小額捐款平台。合作的餐廳、飲料店等店家於店內張貼專屬 QR Code，客人以手機掃碼即進入本平台，看到**該店家的名稱**，選擇想支持的捐款項目，讀完項目說明後於頁面底部完成 LINE Pay 捐款，系統自動開立電子發票或捐贈收據。

三個設計前提決定了整站的樣貌：

| 前提 | 對設計的影響 |
|---|---|
| **掃碼場景 100% 為手機** | 行動優先不是選項而是唯一考量；桌機版僅需可讀，不需優化 |
| **客人多半在等餐、結帳的零碎時間內完成** | 從掃碼到付款完成的步驟數必須壓到最低；**不要求註冊、不要求登入** |
| **店家是引流方，不是系統使用者** | 店家不需要帳號、不需要登入、不需要安裝任何東西；店家端唯一的動作就是把 QR Code 貼出來 |

### 1.2 與官方網站主站的關係

| 項目 | 做法 |
|---|---|
| **網域** | **獨立網域**（名稱待定，見 §13），與 `www.tcrfc.tw` 分離 |
| **前台** | **完全獨立的專案**，不與主站 73 頁的前台骨架共用建置流程 |
| **後台** | **共用官方網站後台**，以新增的 `N. 慈善捐款` 模組承載（見 §6） |
| **資料庫** | **共用同一套資料庫**，因此可與 `CharityProgram`、`Charity`、`Member` 等既有型別建立關聯 |
| **視覺** | 沿用 TCRFC 品牌資產與 design tokens（桃紅 `#E0218A`／品牌黑 `#231916`），但版型與導覽自成一套 |
| **主站的角色** | 單元 11 只做介紹與導流：11.1 慈善理念、11.2 慈善計畫、11.3 事蹟紀錄、11.4 影響力數據維持不變；CTA 由三種收斂為兩種（企業合作／球迷捐款），**球迷捐款一律外連至本平台** |

> **為什麼要獨立網域而非開在主站底下**：掃碼落地頁必須極簡且轉換路徑最短，不應套用主站的 mega menu 與 13 單元導覽；且本平台涉及金流與發票，安全邊界與主站分離較為單純。

### 1.3 系統範圍

**在本次範圍**：

- 掃碼落地頁（顯示店家名稱）、捐款項目列表與詳情、捐款表單、LINE Pay 付款、結果頁
- 電子發票與捐贈收據的開立（依項目設定二選一）
- 後台：店家管理與 QR Code 產生、項目管理、捐款紀錄、回饋金結算、發票管理、捐款報表、站台設定
- 店家與項目的分潤百分比設定與結算
- 繁體中文（預設）＋英文雙語

**不在本次範圍**：

- **店家端帳號與登入區** —— 店家不註冊、不登入、不看後台。回饋金對帳單由俱樂部主動提供
- **掃碼核銷、核銷次數統計、店家成效即時儀表板**（與主站 8.4 特約店家的既定前提一致）
- **定期定額捐款**（每月自動扣款）—— 列為後續評估
- **實體收據郵寄**、紙本發票列印
- **勸募活動的主管機關申報流程**（系統不代辦，僅提供報表供人工申報）
- **前台的退款申請管道** —— 捐款須知明示不受理退款；誤捐等個案由客服受理後於後台人工處理，見 §4.4
- **捐款回饋品** —— 捐款項目不得附帶球衣、贈品等對價物；附回饋品可能被認定為買賣或附負擔贈與，與「不受理退款」的前提衝突
- **捐款人帳號、捐款紀錄查詢區** —— 捐款人不登入，紀錄以 Email 寄送
- **技術選型** —— 框架、CMS、主機、部署環境均不在本文件範圍

### 1.4 名詞定義

本專案有兩組名稱極易混淆的概念，**必須在實作前分清楚**：

| 本平台的型別 | 主站既有的型別 | 差異 |
|---|---|---|
| **`DonationStore` 捐款合作店家** | **`PartnerStore` 特約店家**（主站 8.4） | 前者是**引流方**，貼 QR Code 帶來捐款、有**分潤**；後者是**會員折扣**的提供方，會員出示電子會員卡享優惠、**無金流也無分潤**。<br>**兩者是不同的資料表，即使是同一家實體店也各自建檔、不共用紀錄。** |
| **`DonationProject` 捐款項目** | **`CharityProgram` 慈善計畫**（主站 11.2） | 前者是**募款的標的**，有金額選項、分潤設定與發票模式；後者是**已執行的公益計畫**，記錄受贈團體與捐助內容。<br>項目**可關聯**一個慈善計畫，用於向捐款人展示「這筆錢最後做了什麼」。 |

其他名詞：

- **店家分潤（`store_share_pct`）**：捐款金額中回饋給引流店家的比例。店家有實質收入。
- **項目分潤（`project_share_pct`）**：捐款金額中撥付給該項目指定收款對象（如受贈公益團體或執行單位）的比例。
- **俱樂部留存**：捐款金額扣除上述兩者後的餘額。
- **捐款單（`Donation`）**：一次捐款行為的主檔，沿用並擴充主站規劃書既有的 `Donation` 型別。

## 2. 網站架構與 URL

### 2.1 頁面清單

雙語以 `/zh/`、`/en/` 區隔，架構預留第三語系（與主站規範一致）。

| 頁面 | URL | 說明 |
|---|---|---|
| **掃碼落地頁** | `/{lang}/s/<store_slug>` | QR Code 的目標。**頁首顯示該店家名稱**，其下為捐款項目卡片列表 |
| 一般入口 | `/{lang}/` | 無店家歸屬的直接捐款入口（例如從主站 11 章點進來） |
| **項目詳情頁** | `/{lang}/p/<project_slug>` | 項目完整說明；**頁面最下方為捐款表單**。帶 `?s=<store_slug>` 承接店家歸屬 |
| 結果頁 | `/{lang}/result/<order_no>` | 付款成功／失敗／處理中 |
| 捐款徵信 | `/{lang}/donors/` | 具名捐款者名單（僅顯示姓名，不顯示金額）。可於後台整站關閉 |
| 成果回顧 | `/{lang}/impact/` | 摘要呈現關聯的慈善計畫成果，並導回主站 11.3 |
| 隱私權政策 | `/{lang}/privacy/` | 獨立網域需自有一份，內容涵蓋捐款人個資與發票資料 |
| 捐款須知 | `/{lang}/terms/` | **不受理退款的說明**、發票規則、款項用途說明 |

### 2.2 店家歸屬的傳遞規則

店家分潤成立與否，取決於「這筆捐款是從哪一家店掃進來的」能否正確傳遞到建單那一刻。規則如下：

1. 掃碼進入 `/{lang}/s/<store_slug>` 時，將 `store_slug` 寫入**短期 Cookie**（建議 24 小時）。
2. 由落地頁點進項目詳情頁時，同時以 `?s=<store_slug>` 帶在網址上。
3. 建立捐款單時的取值**優先序**：`URL 參數` > `Cookie` > `無店家`。
4. 取不到店家時，捐款**照常成立**，`store_id` 記為空值，歸類為「無店家歸屬」，店家分潤為 0，項目分潤照算。
5. `store_slug` 對應不到有效店家（已停止合作、已刪除）時，**視同無店家歸屬**，不得報錯中斷捐款流程。

> `store_slug` 僅作為**歸屬標記**，網址中**不得**出現金額、分潤比例或任何可影響帳務的參數，避免被竄改。

### 2.3 QR Code 規格

| 項目 | 規範 |
|---|---|
| 目標網址 | `https://<慈善站網域>/zh/s/<store_slug>`。一律指向中文版，使用者可於站內切換語系 |
| `store_slug` | 由後台產生，**不可由店家編號推導**（避免被猜出其他店家的網址），英數與連字號，全站唯一 |
| 容錯等級 | 建議 **Q 級（25%）**，因印刷品常有污損與局部遮擋 |
| 最小尺寸 | 建議印刷成品的碼區不小於 **3×3 公分**，四周留白至少 4 個模組寬 |
| 產出格式 | **PNG**（一般用途）、**SVG**（可無損放大）、**含店名的印刷版 PDF**（見下） |
| 印刷版樣板 | 含 TCRFC 標誌、店家名稱、一句行動呼籲、QR 碼本體。標誌只用 `brand/svg/` 的三種組合，**不得自行排字、不得加 SINCE 或年份** |
| 重新產生 | 後台可為店家重新產生 `store_slug`（舊碼作廢情境）；**重產後舊 QR 立即失效**，需明確警示並記錄操作者 |

### 2.4 雙語與搜尋引擎

- `hreflang` 需完整提供 `zh-Hant`、`en`、`x-default` 三組
- 所有前台可見的內容型別（店家名稱、項目名稱與說明、站台文案）皆須有 **`zh` / `en` 雙欄位**，英文可空但欄位必須存在
- 英文未填時 fallback 顯示繁中，並標示「本頁尚無此語系版本」
- 語系切換須停留在當前頁的對應語系版本，不跳回首頁
- 掃碼落地頁與項目詳情頁**維持可被搜尋引擎索引**；`/result/` 結果頁需 `noindex`

> **本平台不做 SEO / GEO 優化。**
> 流量來源以**實體通路的 QR Code 掃碼**與主站單元 11 的導流為主，搜尋曝光不是本平台的成效指標。
> 因此**不做**：關鍵字研究與內容經營、結構化資料（`Schema.org` 標記）、sitemap 提交與收錄監控、
> AI 搜尋（GEO）優化，以及任何搜尋排名相關的驗收標準。
> **仍要做**的只有基本可讀性：每頁正確的 `<title>`、`og:title` / `og:description` / `og:image`
> 基本標記（**LINE 分享是主要傳播路徑**，卡片顯示錯誤會直接影響捐款轉換）、上述 `hreflang`，
> 以及必要的 `noindex` 設定。主站規劃書第 7 章 SEO / GEO 規範**不適用於本平台**。

## 3. 前台功能規劃

### 3.1 掃碼落地頁 `/{lang}/s/<store_slug>`

| 區塊 | 內容 |
|---|---|
| 店家識別 | **店家名稱（必要）**、店家 Logo 或照片（選填）、一句感謝語（如「感謝 ○○○ 與台中磐石一起做公益」）。**店家未設 Logo 時降級為純文字的店名區塊，不留空框** |
| 說明 | 一段簡短說明本平台在做什麼、捐款如何被使用（後台可編輯） |
| **項目列表** | 卡片牆：封面圖、項目名稱、一句話說明、「了解並捐款」按鈕。**不顯示募款進度** |
| 信任區塊 | 俱樂部簡介、統一編號／立案資訊、連回主站 11 章的成果紀錄 |
| 頁尾 | 隱私權政策、捐款須知、聯絡方式 |

- 店家已停止合作時，此網址仍可開啟，但**不顯示店家區塊**，等同一般入口
- 頁面須在**行動網路下快速開啟**，首屏不依賴大圖

### 3.2 項目詳情頁 `/{lang}/p/<project_slug>`

由上而下：

1. **封面與標題**：項目名稱、一句話訴求
2. **項目說明**：區塊編輯器排版，支援圖文、引言、清單
3. **款項用途**：明列這筆錢會用在哪裡
4. **關聯的慈善計畫**（選填）：連向主站 11.2 對應的 `CharityProgram`，讓捐款人看到過往成果
5. **捐款表單**（見 3.3）—— **依需求置於頁面最下方**
6. **常見問題**：發票、款項運用、**捐款完成後不受理退款**

> **前台不呈現募款進度**：不顯示進度條、已募得金額、目標金額與捐款筆數。各項目的累計數字改由後台 N6 捐款報表（§7）掌握，不對捐款人公開。

> 若進入本頁時帶有店家歸屬，頁面需以**低調但明確**的方式標示「您正透過 ○○○ 捐款」，讓捐款人知道歸屬關係，同時不喧賓奪主。

### 3.3 捐款表單

| 欄位 | 規則 |
|---|---|
| **捐款金額** | 金額選項卡（由後台逐項目設定，如 NT$100／300／500／1,000）＋「其他金額」自由輸入 |
| 金額限制 | 後台可設**最低**與**最高**單筆金額；超出範圍時即時提示 |
| **姓名** | 必填。用於發票／收據抬頭與致謝 |
| **Email** | 必填。用於寄送感謝信與發票通知。**格式即時驗證** |
| 具名／匿名 | 單選。具名者列於捐款徵信名單（**僅顯示姓名，不顯示金額**） |
| **發票／收據欄位** | 依項目的 `invoice_mode` **動態切換**，見 §5.2 |
| 個資同意 | 必勾。連結至本站隱私權政策，載明蒐集目的與保存期限 |
| 防濫用 | Turnstile 或同等機制；同一 IP 短時間內大量建單需節流 |
| 送出 | 「以 LINE Pay 捐款 NT$ ○○○」——按鈕上**顯示實際金額**，避免誤按 |

- 捐款人**不需註冊、不需登入**
- 表單狀態需在導向 LINE Pay 前保存，付款失敗返回時**不得要求重填**

### 3.4 付款流程的前台呈現

```
填表 → 送出 → 建立捐款單（created）
     → 導向 LINE Pay 付款頁
     → 使用者完成付款 → 返回本站 → 結果頁（成功）
     → 使用者取消／逾時 → 返回本站 → 結果頁（未完成，提供重試）
```

- 返回本站到確認完成之間若有延遲，結果頁顯示**「處理中」**狀態並自動輪詢；**逾時上限與逾時後的文案需明確定義**，不可無限轉圈
- 「處理中」文案不得讓捐款人誤以為失敗而重複付款

### 3.5 結果頁與系統信

**結果頁**（`/{lang}/result/<order_no>`）：

- 成功：感謝訊息、捐款單號、金額、項目、發票／收據的開立狀態說明、分享按鈕、返回入口
- 未完成：說明可能原因、**重試按鈕**（沿用原捐款單，不重複建單）、聯絡方式
- 頁面須 `noindex`，且**不顯示完整個資**（Email 遮罩）

**系統信共四封**：

| # | 信件 | 觸發時機 |
|---|---|---|
| 1 | 捐款感謝信 | 付款成功後立即寄出，含單號、金額、項目與款項用途 |
| 2 | 電子發票／捐贈收據通知 | 發票開立成功後寄出，含發票號碼或收據編號與檢視連結 |
| 3 | 開立失敗通知（寄給俱樂部） | 發票開立失敗，通知後台人員人工補開 |
| 4 | 退款通知 | 後台完成退款後寄給捐款人 |

所有寄送須寫入 `EmailLog`（沿用主站既有型別）。

### 3.6 捐款徵信名單 `/{lang}/donors/`

- 僅列出選擇「具名」的捐款人姓名，**不顯示金額、不顯示 Email、不顯示店家**
- 可依項目與期間篩選
- 後台可整站關閉，亦可逐筆隱藏

### 3.7 無障礙與效能

- 掃碼場景為 100% 手機，行動優先；觸控目標不小於 44×44 px
- 表單欄位須有 `label` 與正確的 `inputmode`（金額用數字鍵盤、Email 用 email 鍵盤）
- 色彩對比符合 WCAG AA；小字情境的桃紅改用安全版 `#D61E83`
- 所有圖片須有 `alt` 與 `width`／`height`

## 4. 金流串接（LINE Pay）

> **這是相對於主站規劃書的範圍變更。** 主站 v2.0 的「官網不接金流」前提**限縮為只適用於主站**；本平台**正式串接 LINE Pay Online API**，可自動取得付款結果、自動開立發票、自動產生報表。主站規劃書 v2.1 的已定案表已同步修訂。

### 4.1 捐款單狀態機

| 狀態 | 說明 | 可轉移至 |
|---|---|---|
| `created` | 已建單，尚未導向付款 | `pending`、`expired` |
| `pending` | 已導向 LINE Pay，等待付款結果 | `paid`、`failed`、`expired` |
| `paid` | **付款成功**，可開立發票、計入報表與分潤 | `refunded` |
| `failed` | 付款失敗或使用者取消 | `pending`（重試） |
| `expired` | 逾時未完成 | `pending`（重試） |
| `refunded` | 已退款 | — |

- **只有 `paid` 會計入報表與分潤**；`created` / `pending` 不得出現在捐款金額統計中
- 狀態轉移需記錄時間與觸發來源（使用者／金流回呼／後台人員）

### 4.2 兩段式流程與冪等性

LINE Pay 採 Request（建立交易）／Confirm（確認扣款）兩段式：

1. 建立捐款單並取得內部單號 `order_no`
2. 呼叫 Request 取得付款網址，記下金流端交易識別碼
3. 導向使用者付款
4. 使用者返回後呼叫 Confirm 完成扣款
5. Confirm 成功 → 捐款單轉 `paid` → 觸發發票開立與感謝信

**冪等性為硬性要求**：同一 `order_no` 重複 Confirm 不得重複入帳、不得重複開立發票、不得重複寄送感謝信。實作須以單號加鎖或狀態檢查保證。

### 4.3 例外處理

| 情況 | 處理 |
|---|---|
| 使用者中途放棄 | 捐款單留在 `pending`，逾時後自動轉 `expired` |
| 逾時 | 建單後超過設定時間（建議 30 分鐘）未完成即 `expired` |
| **重複付款** | 同一捐款單只允許一次成功扣款；使用者重試時**沿用原單**而非新建 |
| **已扣款但 Confirm 失敗** | 最嚴重的例外。系統須將該單標記為**待人工處理**，進入後台的異常佇列並主動通知，**絕不可靜默丟棄** |
| 金流服務中斷 | 前台顯示明確錯誤與聯絡方式，不留下語意不明的半完成狀態 |

### 4.4 退款

**前台不提供退款**：捐款須知頁明示「捐款一經完成，原則上不受理退款」，站上沒有退款申請表單、沒有退款規則、不做任何退款承諾。

**後台保留退款能力**，供下列個案在客服受理後人工處理：誤按金額、重複扣款、非本人操作。規則如下：

- 一律由後台發起（見 §6 N3），需填退款原因與經辦人，**需獨立授權**並寫入稽核日誌
- 退款連動三件事：**發票作廢或折讓**（見 §5.4）、**回饋金沖回**（見 §8.5）、**寄送退款通知信**
- 部分退款不在本次範圍，僅支援全額退款

> 保留後台退款的理由：誤捐在民法上可能構成不當得利或意思表示錯誤，個案上仍可能有返還義務；金流服務商的特約商店契約通常也要求配合爭議款處理。**對外不承諾**與**內部做得到**是兩件事。

### 4.5 對帳

- 每日將本站的 `paid` 捐款單與 LINE Pay 的交易明細比對
- 差異情形（本站有金流無、金流有本站無、金額不符）列為異常清單供人工處理
- 對帳結果保留供稽核

## 5. 電子發票與捐贈收據

### 5.1 依項目設定二選一

每個捐款項目在後台設定 `invoice_mode`，決定該項目的所有捐款走哪一種憑證：

| 模式 | 說明 | 適用 |
|---|---|---|
| **`b2c_invoice` 電子發票** | 開立雲端發票（B2C），在稅務上視為銷售額 | 一般募款項目 |
| **`donation_receipt` 捐贈收據** | 開立捐贈收據，可供捐款人列舉扣除 | 具備受贈資格的公益項目 |

> **前提**：能否開立捐贈收據取決於俱樂部的法人性質與是否具備受贈資格，須由客戶與會計師確認後才可啟用該模式（見 §11 與 §13）。

### 5.2 表單欄位的動態切換

**`b2c_invoice` 時**：

| 欄位 | 規則 |
|---|---|
| 發票類型 | 單選：**手機條碼載具**／**捐贈發票**／**統一編號** |
| 手機條碼 | 選手機條碼時必填，格式 `/` + 7 碼英數，須格式驗證 |
| 捐贈碼 | 選捐贈發票時必填，數字碼；後台可預設一組常用碼 |
| 統一編號 | 選統編時必填，8 碼數字，須做**檢核碼驗證** |
| 發票抬頭 | 選統編時必填 |

**`donation_receipt` 時**：

| 欄位 | 規則 |
|---|---|
| 收據抬頭 | 預設帶入捐款人姓名，可修改 |
| 身分證字號 | **選填**。供列舉扣除申報用；**必須加密儲存**，後台預設遮罩 |
| 通訊地址 | 選填。本次不做實體寄送，僅供收據內容與後續聯繫 |
| 年度彙總 | 可選擇「單筆開立」或「年度彙總開立」，後者於年底統一產出 |

### 5.3 開立時機與失敗處理

- **開立時機**：捐款單轉為 `paid` 後**自動觸發**，不需人工介入
- **失敗重試**：自動重試若干次（含退避），仍失敗則標記 `failed` 並通知後台
- **人工補開**：後台可對開立失敗的單筆重新觸發，或手動填入外部開立的號碼
- 開立狀態：`pending` 待開立／`issued` 已開立／`failed` 開立失敗／`voided` 已作廢／`allowance` 已折讓

### 5.4 作廢與折讓

- 退款時連動處理：當期內作廢，跨期則開立折讓
- **開立錯誤**（抬頭、統編、載具誤植）同樣走作廢或折讓，與退款無關
- 作廢與折讓皆須記錄原因與經辦人
- 已作廢的發票不得重複作廢

### 5.5 加值中心串接

- 串接對象（發票加值中心廠商）**不在本文件指定**，列為待確認
- 規格層面要求：串接實作須抽象為**單一介面**（開立／作廢／折讓／查詢四個動作），日後換廠商時只換實作，捐款與報表模組不動
- API 金鑰與商家憑證的保管要求見 §11

## 8. 分潤與帳務規則

### 8.1 計算式

**店家分潤與項目分潤相加，分別入帳**——兩者是**兩筆不同對象的撥付**，不是同一筆錢的再分配：

```
店家回饋金 = 捐款金額 × store_share_pct
項目撥付金 = 捐款金額 × project_share_pct
俱樂部留存 = 捐款金額 − 店家回饋金 − 項目撥付金

約束：store_share_pct + project_share_pct ≤ 100%
```

- 兩筆分潤在 N4 **各自結算、各自產對帳單、各自登記付款狀態**
- 無店家歸屬的捐款：`store_share_pct` 視為 0，項目分潤照算

### 8.2 計算基準

- 分潤以**捐款金額（毛額）**為基準，不是扣除金流手續費後的淨額
- **金流手續費由俱樂部留存的部分吸收**；若留存不足以覆蓋手續費（兩個分潤率合計過高），系統於設定時提示風險，但不強制阻擋
- 手續費歸屬的最終決定見 §13 待確認

### 8.3 進位規則

- 兩筆分潤金額均**無條件捨去至整數元**
- 捨去產生的尾差併入俱樂部留存
- 報表顯示的合計必須等於逐筆加總，不可因四捨五入而對不上

### 8.4 分潤設定異動不追溯

**每筆捐款於成立（`paid`）時，快照當下的 `store_share_pct` 與 `project_share_pct`**，寫入捐款單。

- 後台事後調整店家或項目的分潤率，**只影響之後的新捐款**，不影響歷史
- 已結算的期間不因設定變更而重算
- 這是帳務正確性的硬性要求：對帳單一旦送出給店家，金額不能事後浮動

### 8.5 退款沖回

| 情況 | 處理 |
|---|---|
| **尚未結算** | 該筆捐款直接排除於結算之外，不產生任何回饋金 |
| **已結算但未付款** | 從該期對帳單中扣除，重出對帳單 |
| **已結算且已付款** | **不追討**，改以**負項**計入下一期結算，於對帳單上明列沖回原因與原捐款單號 |

### 8.6 結算與匯款流程

1. 期末於 N4 執行結算 → 產生店家與項目兩份對帳單
2. 財務人工核對後，於系統外執行匯款
3. 回到 N4 登記匯款日期、方式與備註，狀態轉 `已付款`
4. 系統不經手任何出款金流

### 9.3 與既有型別的界線

| 情況 | 正確做法 |
|---|---|
| 掃碼引流的店家 | `DonationStore`。**不是** `PartnerStore` |
| 提供會員折扣的特約店家 | `PartnerStore`（主站 8.4）。**不是** `DonationStore` |
| 同一家店既引流又給會員折扣 | **兩邊各建一筆**，不共用紀錄、不建立外鍵關聯 |

| 捐款人是否為會員 | **僅以 Email 軟性比對後標示**，不寫入 `Member`、不建立關聯欄位 |

### 9.4 雙語

## 11. 個資、安全與法規

### 11.1 個資

- 蒐集項目：姓名、Email、（捐贈收據模式下）身分證字號與地址
- **身分證字號必須加密儲存**，後台預設遮罩，且僅在開立收據的必要範圍內使用
- 隱私權政策須載明蒐集目的、利用範圍與**保存期限**（實際年限待客戶與法務確認，見 §13）
- 徵信名單只公開姓名，且以捐款人明示同意為前提

### 11.2 安全

- **不儲存任何卡號或支付憑證**
- LINE Pay 商家憑證與發票加值中心金鑰以密文保管，不進版控、不在後台明碼顯示
- 金流回呼須驗證來源與簽章
- `store_slug` 僅為歸屬標記；**網址中不得攜帶金額或分潤參數**
- 捐款建單須有防濫用機制（Turnstile、IP 節流）
- 後台的退款、分潤設定、匯出三類操作全數留下稽核軌跡

### 11.3 法規

- **公開向不特定人募款可能適用《公益勸募條例》**，是否需取得勸募許可、以何種法人身分辦理，直接決定本平台能否上線
- **捐贈收據的開立資格**取決於俱樂部的法人性質與受贈資格
- 上述兩點須由客戶與會計師／法務確認；**這是上線前提，不是一般待確認事項**（見 §13）
