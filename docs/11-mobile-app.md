## 1. 一分鐘理解

**台中磐石足球俱樂部 × 台中藍鯨女子隊**的共同 iOS／Android App，對外名稱中性「台中足球 Taichung Football」。**共用主站後台與資料庫**，新增後台 `M. 行動 App` 模組（**M1–M5；俱樂部與授權管理在主站 `J4`**），並擴充既有 `E` 商業模組為 E4–E6（廣告）。

**內容主體是兩隊，收款與法律主體只有俱樂部**——務必分開理解：

| 層面 | 主體 |
|---|---|
| 內容與品牌 | **兩隊共同**（雙標誌、中性名稱） |
| **會籍** | **兩隊各自一份**（v3.0，`Membership` 型別，**每份會籍一張卡**） |
| **收款與發票** | **僅俱樂部**（藍鯨會籍採**代收代付**，單一商店號與發票抬頭） |
| 法律與帳號 | **僅俱樂部**（開發者帳號、憑證、資料控制者） |
| 內容維護 | **各自維護**（藍鯨有自己的後台帳號，僅限自家內容） |
| **官方網站** | **各自一站**（磐石官網＋**藍鯨官網**，共用後台與資料庫） |

與慈善捐款平台的協會主體則完全分離。

### 選功能的兩個標準

一項功能要進 App，須滿足其一：**手機才做得到**（定位、離線、推播、原生行事曆），或**資料已在既有規格內**（不需客戶額外產內容）。兩者皆不滿足者不納入。

### 十二項功能

| # | 功能 | 性質 |
|---|---|---|
| 1 | **兩隊內容（賽程、名單、新聞）** | **v2.0 主體變更**，新增 `Club` 型別與 `BW1` 隊別 |

|---|---|

| 學員家長綁定 | **不做**（網頁、App、後台三方皆然） |
| **兩隊各自的 App** | **不做**（v2.0） |
| **兩隊分潤計算** | **不做**（v2.0，屬線下合約，系統不處理） |
| 抽獎 | 前台僅顯示個人資格布林與活動辦法；不顯示序號、不做查詢、不做名單頁、不做計數器 |
| 技術選型 | **規劃書不記**（§1.3 排除），改以 §1.5「平台能力需求」表述。**客戶端選型見 [`19-app-tech-stack.md`](19-app-tech-stack.md)：原生 Swift ＋ Kotlin** |
| **首個上架版本**（v3.10） | **不含 App 內付款**，加入與升級以外部瀏覽器導回官網完成（§5.5 方案 B）。App 內 LINE Pay 排在 **§15 的 Phase E** |

## 4. 已知踩雷點

0. ✅ **v2.0 時代的「主站尚未同步」落差已於 v3.0 解除。** 主站規劃書已升 v3.0：§3.6【06】改寫為藍鯨官網入口、多俱樂部架構與 `club_id` 維度已定義、`J` 模組資料範圍權限已補、`Club`／`Competition` 已移入主站型別表。
   **客戶並已決定建置台中藍鯨官網**（獨立網域、雙語，見 [`13-blue-whale-site.md`](13-blue-whale-site.md)），這正是 §2.3 的解法 A。
   ⚠️ **[`12-database-schema.md`](12-database-schema.md) 的女足敘述已更新**（`type='women'` 廢除，改用獨立的 `Team.gender`），但該檔的 **§4 資料表總覽、17 張 ERD、§6 五節明細、§11.1 唯一鍵表、§14 檢核表尚未逐一改寫**——檔頭「v3.0 落差」段落列出全部項目，**轉 DDL 前必須完成**。

2. **內容主體是兩隊，收款主體只有俱樂部。** 藍鯨是**內容提供方、品牌共同署名方與會籍受益方，但不是收款方**——**藍鯨會籍採代收代付**：不申請第二個商店號、不開第二份發票、**系統不做兩隊分潤**（只記受益俱樂部並提供加總匯出）。
   ⚠️ **代收代付的稅務認定尚未完成**（是銷貨還是受託代銷？是否需要協會開進項發票？），**未確認前不得開發藍鯨會籍的 App 內付款**。
   慈善捐款平台的主體則是台灣足球策略發展協會，三者的 **LINE Pay 商店號一律不得共用**——收款主體錯誤會同時踩到稅務與《公益勸募條例》。

3. ⚠️ **v3.0 改為雙會籍，但 `Member` 仍然不加 `club_id`——結論相同，理由換了。**
   v2.0 的理由是「一張卡通兩隊，加了會被讀成兩種會籍」。**v3.0 起真的是兩份會籍**，該理由不成立。
   新的理由：`Member.email` 是**登入鍵**（加了等於兩組密碼、兩次 LINE 綁定、兩次刪帳號），`line_user_id` 與 LINE 帳號 1:1 複製不了，**個資法上的當事人是「人」不是「會籍」**。俱樂部維度放在**主站的 `Membership` 型別**。
   **`Member` 的 `tier`／`membership_start_on`／`membership_end_on` 三欄已移入 `Membership`**——看到還寫在 `Member` 上的是舊規格。
3a. **會員卡改為「每份會籍一張」，但兩條約束一字未改。**
   **「一張卡只有一組 token」約束的是卡與 token 的 1:1**，不是人與卡的 1:1（`card_quota` 家庭方案本來就可以是 3 張）。
   **驗證頁 `/m/<token>` 的回傳欄位一欄未改，仍不得新增「適用球隊」欄位**——token 已隱含俱樂部。
   反過來說，**「一張卡標示兩種會籍」不可採**：不顯示「磐石有效／藍鯨已到期」店員無法判斷，顯示了就等於加了適用球隊欄位。
   **v2.0 的「卡面中性雙標誌」整段已作廢。**

4. **`Team.code` 維持全站唯一，藍鯨一線隊是 `BW1` 不是第二個 `D1`。**（v2.0）`code` 是行事曆訂閱網址與官網既有路徑（`/zh/schedule/d1/`）的識別鍵，改成「俱樂部 × 代號」複合鍵會破壞既有網址與已被訂閱的行事曆來源。
   **兩隊都有「一線隊」，所以任何同時呈現兩隊賽事的畫面，每張卡片都必須標球隊。**

5. **藍鯨標誌必須是向量主檔**，**不得自行造標、不得從網頁截圖描摹、不得把點陣圖放大充當向量**（✅ 2026-09-14 已取得**點陣主檔**——自既有官網下載的去背原圖 3299×3243＠300dpi，見 [`../brand/blue-whale/`](../brand/blue-whale/README.md)，文件、網頁與 App 圖示夠用，**向量仍缺**）；球員照片**須有肖像同意**（未成年須監護人同意）。兩者未到位前對應區塊不顯示，**不得放假圖或空 Logo 格**。
   💡 藍鯨由磐石在 running，這些在自己手上——是盤點問題（背景見 [`15-out-of-scope-record.md`](15-out-of-scope-record.md)）。

6. **`Club` 不是第六種商業對象。**（v2.0）它是內容主體，不計曝光、無金流、無分潤，**不與 `Partner`／`Sponsor` 合併**——藍鯨是共同主體，不是俱樂部的贊助商或夥伴。

7. **金流只涵蓋會籍費用。** 課程費用維持線下（主站 P3 未變）、捐款不做；**商品自主站 v2.6 起改由網頁的站內商店（8.3／後台 `S`）承接，App 本身不做商店、不做購物車**。看到「App 內繳課程費」「App 內購物」一律是錯的。
   ⚠️ **首個上架版本連會籍費用都不在 App 內收**（v3.10）——加入與升級改為外部瀏覽器導回官網（§5.5 方案 B），**App 內 LINE Pay 排在 §15 的 Phase E**。但**訂單建立、金額伺服器端重算與 `activate` 冪等開通在 Phase B 就要到位**，兩條付款路徑共用同一組訂單邏輯。

8. **`M` 模組與 `/m/<token>` 無關。** 後台模組代號 `M` 是行動 App，`/m/<token>` 是電子會員卡的公開驗證頁，兩者是不同命名空間。

9. **廣告在 E 模組不在 M 模組。** 這是權限最小化的刻意設計：業務賣廣告不該連帶取得 App 版本發布權與推播發送權。

10. **贊助商 Logo 牆不計曝光。** `Sponsor`／`Partner` 的呈現**不產生 `AdEvent`、不進廣告報表**。贊助合約若含 App 版位，須另建 `Advertiser`（可用 `sponsor_id` 關聯回 `Sponsor`）再開 `AdCampaign`。

11. **五種「商業對象」不可混用**：`Partner`／`Sponsor`／`PartnerStore`／`DonationStore`／`Advertiser`。同一家公司可能同時是數種，**各建一筆**。唯一例外是 `Advertiser.sponsor_id`，那是關聯不是合併。

12. **抽獎只顯示個人布林，不顯示合格人數。** 「我是否具備資格」是既有會籍狀態的呈現；「合格人數即時計數器」是主站明文不做的項目。**App 不得讀取 `DrawRoster`。**
    ⚠️ **v3.0 起抽獎由各俱樂部各自舉辦**，布林值改為**逐俱樂部顯示**。同時持有兩隊付費會籍者會在兩份名單各佔一號，**活動辦法須明示「可分別參加兩隊抽獎」**，否則牴觸主站「不因消費增加中獎機會」的承諾。
12a. ⚠️ **「合作球隊絕不接觸會員資料」已於 v3.0 改寫。** 原規則的前提是「藍鯨只是內容提供方」，雙會籍後不成立——藍鯨的客服不能看自家會員，系統就沒法用。
    改為：**可存取自家 `club_id` 的會籍、付款、球衣與報名；`Member` 主檔欄位一律遮罩；對方俱樂部的任何會籍列絕對不可見。**
12b. **這個角色第一階段可先不指派使用者**（v3.1）——藍鯨由磐石的團隊在維護，用自己既有的帳號即可。**但資料範圍權限仍要做**（`club_id` 已鋪到 50 張表，是系統地基），**不擋上線**。
12c. **藍鯨官網是獨立網域，Universal Link 有新條件。** 該網域**必須由可控方持有**並能放 `.well-known/apple-app-site-association` 與 `assetlinks.json`；控制權不在手上則**藍鯨深連結不得上線**。**深連結 scheme 維持 `tcrfc://` 不變**——scheme 是 App 內部識別，與網域無關。

13. **推播不得用於個別中獎通知。** 主站承諾中獎只以最新消息遮罩公布、系統信維持五封。後台 M3 須**以系統層阻擋**，不能只靠人工注意。同理，帶 `球迷會員抽獎` 標籤的文章不得進入新聞分類推播。

14. **學員家長綁定三方皆不做。** App 解除的只有「表單自動帶入」與「我的報名」兩項，且僅限會員本人資料。`Registration.member_id` **可為空**——非會員仍可報名，這條不得更動。

15. **課程梯次不進 `CalendarEvent`。** 「我的報名」可顯示梯次時間，但不得寫入行事曆型別，也不得出現在賽程分頁。

16. **會員卡 token 只有一組。** 會員卡在 App 內出示（離線可用、標示最後同步時間），一張卡只有一組 token——發兩組等於兩份可撤銷狀態，撤銷時必然漏掉一邊。

17. **會員卡離線可出示，但不得以快取值宣告有效。** 卡面須標示最後同步時間，超過 7 天須提醒——否則過期會員可用飛航模式出示舊卡。

18. **`PartnerStore` 與 `Venue` 目前沒有座標。** 只有地址字串，做不了距離排序與導航。座標由後台 K4「由地址定位」輔助、**人工確認後儲存**，不做執行期即時 geocoding。
