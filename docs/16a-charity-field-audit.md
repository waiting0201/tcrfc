## §1 核對方法與判準

**核對方式**：以規劃書 §6 後台功能規劃（行 466–551，N1–N7 七個模組）與 §9 資料模型（行 633–683）為主，

**三種情形的判準**（同 `12d` §1）：

| 標記 | 判準 |
|---|---|
| 🔴 **真的缺** | 規劃書有明文（可指出行號與原文），`docs/16` §3 主表屬性方塊沒有對應欄位，i18n 側表也沒有承接 |
| 🟡 **落點存疑** | 規劃書有寫，但語意可能已由其他既有欄位／機制間接滿足，或規劃書字面與資料模型設計慣例衝突，需要人工判斷 |

## §3 🔴 真的缺

### 2.1 `N` 捐款核心

#### `DonationStore`
- **缺欄位**：Logo 或照片主檔欄位（如 `logo_key`）
- **規劃書行 487**：「店家欄位｜名稱（zh / en）、**Logo 或照片**、類別、地址、聯絡人與電話、合作起訖、狀態（合作中／已停止）」
- **目前 `docs/16` 哪裡都沒有**：`docs/16` §3 ER 圖的 `donation_store { }` 屬性方塊為 `id`／`store_slug`／`name_zh`／`category`／`address`／`contact_name`／`contact_phone`／`store_share_pct`／`start_on`／`end_on`／`status`，**沒有任何圖片欄位**。`docs/16` §2.1 資料表總覽的文字敘述雖有寫「Logo」二字，但 ER 圖屬性方塊沒有對應欄位，依 `12d` 判準（文字提過不算數，要看屬性方塊）算真的缺。⚠️ `db/charity-schema.sql` 已補 `logo_key`／`logo_width`／`logo_height`，DDL 領先 `docs/16`，見檔頭「另外要查的三件」第 3 點的反向情形——這裡方向相反，是 **DDL 有、`docs/16` 沒有**，但因規劃書明文要求，仍算 `docs/16` 的真缺，不歸入 §7

#### `DonationProject`
- **缺欄位**：封面圖主檔欄位（如 `cover_key`）
- **規劃書行 500**：「項目欄位｜名稱（zh / en）、**封面圖**、一句話說明、說明內文（區塊編輯器）、款項用途、`project_slug`」
- **目前 `docs/16` 哪裡都沒有**：`docs/16` §3 ER 圖的 `donation_project { }` 屬性方塊為 `id`／`project_slug`／`name_zh`／`min_amount`／`max_amount`／`project_share_pct`／`invoice_mode`／四個快照欄位／`sort_order`／`status`，**沒有封面圖欄位**。同 `DonationStore`，`db/charity-schema.sql` 已補 `cover_key`／`cover_width`／`cover_height`，DDL 領先 `docs/16`

#### `DonationInvoice`（四項）
- **缺欄位 1**：發票抬頭（統編模式，如 `invoice_title`）
- **規劃書行 433**：「發票抬頭｜選統編時必填」
- **缺欄位 2**：收據抬頭（如 `receipt_title`）
- **規劃書行 439**：「收據抬頭｜**預設帶入捐款人姓名，可修改**」——明文要求「可修改」，代表這是獨立於 `Donation.donor_name` 的可編輯欄位，不能只靠父表帶入值
- **缺欄位 3**：年度彙總開立旗標（如 `is_annual_summary`）
- **規劃書行 442**：「年度彙總｜可選擇「單筆開立」或「年度彙總開立」，後者於年底統一產出」
- **缺欄位 4**：作廢或折讓的原因與經辦人（如 `void_reason`／`voided_by`）
- **規劃書行 455**：「作廢與折讓皆須記錄**原因**與**經辦人**」
- **目前 `docs/16` 哪裡都沒有**：`docs/16` §3 ER 圖的 `donation_invoice { }` 屬性方塊為 `id`／`donation_id`／`invoice_type`／`invoice_no`／`issued_at`／`carrier_type`／`carrier_id_encrypted`／`tax_id`／`national_id_encrypted`／`receipt_address`／`issue_status`／`void_status`，四項全部沒有對應欄位。§4.4 關鍵表明細同樣只列了兩種模式與 `issue_status`／`void_status`／抬頭（僅說明是協會，未展開統編模式的抬頭欄位），沒有補上。**這是本次盤點單一一張表缺最多欄位的案例**

### 4.2 分潤與帳務（`Settlement` / `SettlementLine`）

#### `Settlement`
- **缺欄位**：匯款方式（如 `remit_method`）
- **規劃書行 529**：「付款紀錄｜實際匯款於系統外執行；後台僅登記**匯款日期、方式與備註**，供對帳與稽核」
- **目前 `docs/16` 哪裡都沒有**：`docs/16` §3 ER 圖的 `settlement { }` 屬性方塊有 `remitted_on`（日期）與 `remit_note`（備註），**沒有「方式」欄位**（如匯款／轉帳／其他）。規劃書明文列了三項「日期、方式與備註」，目前只承接了兩項

#### `SettlementLine`
- **缺欄位**：退款沖回原因（如 `clawback_reason`）
- **規劃書行 622**：「已結算且已付款｜不追討，改以負項計入下一期結算，於對帳單上**明列沖回原因**與原捐款單號」
- **目前 `docs/16` 哪裡都沒有**：`docs/16` §3 ER 圖的 `settlement_line { }` 屬性方塊為 `id`／`settlement_id`／`donation_id`／`share_amount`／`is_clawback`。原捐款單號已由 `donation_id` 承接，但「沖回原因」的文字說明沒有對應欄位——`is_clawback` 只是布林旗標，不能承載原因文字

### ⬛ 對帳結果——**規劃書明文要求的資料結構，在 `docs/16` §2 的 23 張表清單裡完全不存在**

- **規劃書行 402–406**（§4.5 對帳）：「每日將本站的 `paid` 捐款單與 LINE Pay 的交易明細比對／差異情形（本站有金流無、金流有本站無、金額不符）列為異常清單供人工處理／**對帳結果保留供稽核**」
- **規劃書行 517**（N3 異常佇列）：「獨立分頁列出「已扣款但確認失敗」「發票開立失敗」「**對帳差異**」三類待人工處理項目」
- **目前哪裡都沒有**：`docs/16` §2 的 23 張表清單裡沒有任何「對帳批次」「對帳差異」相關型別（如 `ReconciliationRun`／`ReconciliationDiscrepancy`）。「已扣款但確認失敗」與「發票開立失敗」兩類異常可分別由 `Donation.status`（配合 `IX_donations_status_created_at` 索引）與 `DonationInvoice.issue_status` 查詢出，**但「對帳差異」這一類——本站有金流無、金流有本站無、金額不符——沒有任何欄位或表能標記或保存**，「對帳結果保留供稽核」這句話目前無處可落。這與主站 12d 盤點發現的「贊助活動 Activations 整個型別缺席」是同一種嚴重程度的缺漏

## §4 🟡 落點存疑

| 表 | 規劃書字面 | 存疑原因 |
|---|---|---|
| `Settlement` | 行 526：「狀態｜`待結算` → `已結算` → `已付款`，**每次異動記錄經辦人與時間**」 | `settlement` 只有共通欄位 `updated_at`／`updated_by`，能記錄「最後一次異動」的經辦人與時間，但三段狀態各自的異動時間點無法從單一欄位還原（例如「誰在何時把它從待結算轉為已結算」與「誰在何時轉為已付款」是兩件事）。是否需要獨立的狀態異動歷程，或共通欄位已足夠滿足「記錄」二字的字面要求，规劃書字面不夠具體 |
| `AuditLog` | 行 574：「匯出含個資的明細（姓名、Email、身分證字號）須額外授權，且每次匯出寫入稽核日誌：誰、何時、**匯出幾筆**、用途備註」 | `audit_log` 有 `admin_user_id`（誰）、`occurred_at`（何時）、`purpose_note`（用途備註），但沒有結構化的「匯出幾筆」欄位（如 `record_count`）。可能已由通用的 `change_summary`（`string_500`，自由文字）承載這個數字，但那是非結構化欄位，不保證可靠地被報表或稽核查詢使用 |

> **附帶一項規劃書自身的殘留矛盾，非 `docs/16` 缺漏**：§7.2「依項目」報表（行 567）寫「每個項目的筆數、金額、**目標達成率**、分潤率、應撥付金額、平均單筆」，但 §1.2／N2（行 501、`docs/16` 行 319）明文「不設目標金額」「⛔ 不存在的欄位：目標金額、已募得金額、捐款筆數」。`docs/16` 正確遵循了後者（沒有目標金額欄位），但「目標達成率」這句報表敘述因此無從算起——這是規劃書 §7.2 與 §1.2/§6.2 自相矛盾的殘留文字，類型與 `docs/16` §10 已登記的「§9.3 表格最後一列」殘留問題相同，建議一併排入同步鏈處理，不算本檔的缺漏筆數。

## §5 「可多張」／需要歷程記錄缺子表

全文搜尋規劃書「圖集」「可多張」「批次」「藝廊」關鍵字，**慈善規劃書未出現任何多圖集需求**（店家與項目皆為單一 Logo／封面圖）。但有一類功能性質相同——**同一實體會隨時間累積多筆狀態變化紀錄**，單一欄位無法承載：

| 型別 | 規劃書字面與行號 | 現狀 |
|---|---|---|
| `Donation` | 行 366（§4.1）：「狀態轉移需記錄**時間**與**觸發來源（使用者／金流回呼／後台人員）**」；行 514（N3 詳情）：「完整捐款單、金流交易識別碼、**狀態異動紀錄**、發票資訊、分潤快照」 | ⬛ **缺歷程子表**。`donation` 主表只有 `status`（目前狀態）與共通欄位 `created_at`／`updated_at`／`updated_by`，**無法還原一張捐款單從 `created` → `pending` → `paid` 等多次轉移的完整歷程**，且「觸發來源」明文包含「金流回呼」——這不是一個 `admin_user`，`updated_by` 欄位（指向 `admin_users.id`）結構上無法承接這個值。需要一張類似 `DonationStatusLog` 的歷程子表，或至少把「觸發來源」的值域擴充為非管理員來源 |

## §6 值域未定義的欄位清單

規劃書提到「類別」「狀態」等 enum 型欄位，但沒有給出完整值域，或給出的值域沒有被 `docs/16`／DDL 承接。**只列出，不推值域**：

| 表.欄位 | 問題 |
|---|---|
| `DonationStore.category`（店家類別） | 規劃書行 487 只寫「類別」二字，全文未列舉具體分類值（餐飲／飲料店／其他？），`docs/16` 與 DDL 均未給 `CHECK` 約束，屬合理（規劃書本身沒給） |
| `DonationPayment.status`（金流交易狀態） | `docs/16` §3 ER 圖只寫 `enum status`，規劃書全文未列舉具體值；`db/charity-schema.sql` 自行推定為 `requested`／`confirmed`／`failed` 三值並在欄位註解自承「規劃書與 `docs/16` 均未明文列舉」，屬工程判斷非規格明文 |
| `Permission.domain`（權限網域） | `docs/16` §2.3 只說「本庫的 `module_code` 是 `N`、`submodule_code` 是 `N1`–`N7`」，沒有列舉 `domain` 欄（如 `store`／`project`／`donation`／`settlement`／`invoice`／`report`／`setting`）的具體值域；DDL 註解已自承這點，未加 `CHECK` |
| `DonationInvoice.carrier_type`（發票類型子分類） | **與前三項不同，規劃書其實有給值域**——行 429：「發票類型｜單選：**手機條碼載具／捐贈發票／統一編號**」，三個具體選項。但 `docs/16` §3／§4.4 與 DDL 都只寫 `carrier_type`／`string_16`，未把這三個值寫成可核對的值域或 `CHECK` 約束，等於規劃書給的值域沒有被承接下來 |

## §7 DDL 有但規劃書沒有的

以下欄位存在於 `db/charity-schema.sql`，但規劃書與 `docs/16` 逐欄核對時都找不到明確對應文字——多數是合理的工程性補充，**列出是為了讓人工確認來源，不代表建議刪除**：

| 表.欄位 | 說明 |
|---|---|
| `email_logs.recipient_email`／`sent_at`／`status`／`email_template_id` | 規劃書行 328 只說「所有寄送須寫入 `EmailLog`（沿用主站既有型別）」，`docs/16` §2.5 也只提到「`type` 值域 4 個」，沒有逐欄列舉收件人、寄送時間、狀態、對應樣板四欄。DDL 註解已自承「本檔依『寄送紀錄』的功能需求補上的最小必要欄位」。**這組欄位邏輯上必要**（沒有收件人與時間就不是一份「紀錄」），但目前沒有規劃書或 `docs/16` 文字依據，建議至少回填進 `docs/16` §2.5／§4，不需要改規劃書 |
| `payment_channels` 的 `(channel_type, environment)` 唯一鍵 | DDL 註解自承「依主站 `PaymentChannel` 的對應唯一鍵設計類推而來，`docs/16` 未明文列出本表的唯一鍵」。屬結構性補充而非欄位，列於此處供確認 |
| `donations.donor_name`／`donor_email` 的 `NOT NULL` | 規劃書 §3.3 表單（行 288–289）「姓名」「Email」皆標「必填」，`docs/16` §4.1／ER 圖沒有明講必填與否但 DDL 已正確定為 `NOT NULL`，**方向與 `logo_key`／`cover_key` 相反**（DDL 對，`docs/16` 沒寫明），列在此處供對照，不算缺漏 |

## §8 無從核對的表

以下表在 `docs/16` §2 有一列，但**慈善規劃書全文找不到任何欄位級文字描述**（不同於「有描述但 ER 圖沒接住」的 §3／§5，這裡是規劃書本身就沒寫到這個細節，通常是因為該表被規劃書自己定位為「沿用主站同形」或「本檔技術性展開」）：

| 表 | 說明 |
|---|---|
| `CharityRef` / `CharityProgramRef` | 規劃書 §9.3（行 673）只說「清單同步採 N2 後台的 CSV 匯入，或主站提供的唯讀 API 定期拉取」，**沒有把這兩張表列為型別**，欄位（`ref_code`／`name`／`imported_at`／`source`）是 `docs/16` 自行設計的落地形式。`docs/16` §10 已自行標注這點為「本檔不決定的事」第一項，本檔重複確認、不重複列為新發現 |
| `AdminUser`／`AdminRole`／`AdminUserRole`／`Permission`／`RolePermission` | 規劃書 §10（行 684–706）只列出沿用主站的九個角色**名稱**與各角色在慈善模組的權限範圍敘述，**沒有逐欄描述帳號表本身**。`docs/16` §2.3 明文「與主站 `Permission` 同形」「欄位形狀比照主站 `admin_users`」，欄位定義依據是主站 `docs/12b` §7，不是本規劃書，因此對慈善規劃書而言無從核對（主站那份的欄位完整性已由 `12d` 涵蓋，不重複） |
| `Locale`／`UiString`／`UiStringTranslation` | 規劃書全文沒有針對這三張技術性支撐表的欄位描述，只在 §2.4／§9.4 提到「架構預留第三語系」「雙語欄位」等原則性文字。`docs/16` §2.5 承認這三張是「共通機制」的技術性展開，與主站 `12d` §8 對 `Locale`／`UiString` 的認定（「規劃書從未逐欄描述」）性質相同 |

> 上述 10 張表**不是「漏寫」**，是規劃書本身就停在名稱或原則層級，沒有進到欄位。列在此處是為了誠實標注「這裡沒有更多可核對的依據」。
