# 10 — 慈善捐款平台

> 來源：[`../output/TCRFC_慈善捐款平台功能規劃書.md`](../output/TCRFC_慈善捐款平台功能規劃書.md)（v1.5，共 755 行）

獨立網域的掃碼捐款平台，**由台灣足球策略發展協會（以下簡稱協會）主辦與收款**，**共用台中磐石足球俱樂部官網的後台與資料庫**。俱樂部官網單元 11 只做介紹與導流，捐款金流全在這裡。

> **客戶說明用的站台地圖**：[`../output/TCRFC_慈善捐款站台地圖.html`](../output/TCRFC_慈善捐款站台地圖.html)
> 與英文版 [`TCRFC_Charity_Donation_Sitemap_EN.html`](../output/TCRFC_Charity_Donation_Sitemap_EN.html)
> ——把八個前台頁面依捐款動線排開，每站附手機示意畫面。**HTML 是母檔，PDF 由
> `node output/tools/build-pdf.mjs sitemap-zh sitemap-en` 產生，勿手改 PDF。**
> 規格有異動時這兩份要一併更新（頁面清單、畫面區塊、版本戳記）。

```
店家貼 QR → 客人掃碼 → 落地頁（顯示店家名稱） → 選捐款項目
          → 項目詳情頁（最下方是捐款表單） → LINE Pay → 發票／收據 → 感謝信
```

## 3. 後台模組速查　`行 424–510`

```
N. 慈善捐款平台
├── N1 店家管理與 QR Code    店家欄位、store_share_pct、store_slug、QR 產出（PNG/SVG/印刷版 PDF）
├── N2 捐款項目管理          金額選項、project_share_pct、invoice_mode、關聯 CharityProgram（**無目標金額**）
├── N3 捐款紀錄              逐筆檢視、退款、Email 比對會員（僅標示）、異常佇列
├── N4 回饋金結算            店家與項目分開結算、對帳單 + CSV、人工匯款只登記狀態
├── N5 發票與收據管理        補開、作廢、折讓、匯出
├── N6 捐款報表              總覽／依店家／依項目／發票狀況／逐筆明細
└── N7 站台設定              文案 zh/en、四封信樣板、金額上下限、環境切換
```

> 代號用 `N`：`D` 因課程模組 D1–D4 改名 P1–P4 的歷史避用，`M` 易與 Member 混淆。

## 4. 分潤怎麼算　`行 537–590`

```
店家回饋金 = 捐款金額 × store_share_pct
項目撥付金 = 捐款金額 × project_share_pct
協會留存 = 捐款金額 − 店家回饋金 − 項目撥付金
約束：store_share_pct + project_share_pct ≤ 100%
```

四條容易踩到的規則：

1. **兩筆分潤相加、分別入帳**，是兩個不同對象的撥付，N4 產兩份對帳單。
2. **以捐款毛額計算**，不是扣手續費後的淨額；手續費由協會留存吸收。
3. **成立時快照百分比**，事後改設定**不追溯**——對帳單送出去就不能浮動。
4. **無條件捨去至整數元**，尾差歸協會留存；報表合計必須等於逐筆加總。

## 5. 容易搞錯的關係

| 情況 | 正確做法 |
|---|---|
| 掃碼引流的店家 | `DonationStore`（有分潤、有金流）。**不是** `PartnerStore` |
| 給會員折扣的特約店家 | `PartnerStore`（主站 8.4，無金流無分潤）。**不是** `DonationStore` |
| 同一家店兩邊都做 | **各建一筆**，不共用紀錄、不建外鍵 |
| 募款的標的 | `DonationProject` |
| 已執行的公益計畫 | `CharityProgram`（主站 11.2）。`DonationProject` 可關聯它，反向不成立 |
| 受贈公益團體 | `Charity`（主站既有），項目撥付對象直接關聯它 |
| 捐款人是不是會員 | **只用 Email 軟性比對後標示**，不寫入 `Member`、不建關聯欄位、不做歸戶 |
| 捐款主檔放哪 | **擴充主站既有的 `Donation`**，不另建 `DonationOrder`——主站捐款管道已收掉，避免兩份真實來源 |
| 只有 `paid` 才算數 | `created` / `pending` **不得**出現在任何金額統計與分潤計算中 |

## 6. 已知踩雷點

1. **「店家」有兩種、「項目」有兩種**——見上表。這是本專案最大的混淆源，後台介面也必須把名稱區分清楚。
2. **主站已經不做站內捐款與志工報名**（規劃書 v2.1）。看到舊文件寫 Shopify 捐款品項、銀行匯款、物資捐贈、匯款回報表單、志工報名表單，一律視為錯誤。
3. **「官網不接金流」只適用於主站**。本平台正式串 LINE Pay，別把主站的前提套過來。
4. **勸募資格與捐贈收據資格是上線前提，不是一般待確認事項**。未確認前不應開始印製 QR Code。
5. **QR 網址不可攜帶金額或分潤參數**，`store_slug` 只是歸屬標記，且不可由店家編號推導。
6. **冪等性是硬性要求**：同一 `order_no` 重複 Confirm 不得重複入帳、重複開票、重複寄信。
7. **「已扣款但 Confirm 失敗」不可靜默丟棄**，必須進 N3 的異常佇列並主動通知。
8. 網域未定前，主站的導流連結一律留 `.pending-inline` 標記，**不要杜撰網址**。
9. **本平台不做 SEO／GEO**（v1.1）。[`05-i18n-seo.md`](05-i18n-seo.md) 與規劃書第 7 章是**主站專用**，不要套到這裡；但頁面仍要可被索引，`hreflang` 三組、`<title>` 與 `og:` 基本標記（LINE 分享用）照做。
10. **前台沒有募款進度**（v1.2）。不做進度條、目標金額、已募得金額與捐款筆數，`DonationProject` 也沒有目標金額欄位。看到舊文件寫「募款進度可逐項關閉」一律視為錯誤。各項目累計數字只從 **N6 捐款報表**取得，不要為了前台顯示而回頭加欄位。
11. **退款是「對外不做、對內做得到」**（v1.3）。前台沒有退款規則、沒有申請管道，捐款須知明示不受理；但後台 N3 的人工退款、§8.5 回饋金沖回、第四封退款通知信**全部保留**，供誤捐與重複扣款的個案處理。把後台退款一起刪掉是錯的。
12. **發票作廢與折讓不隨退款移除**（v1.3）。§5.4 是稅法要求，且「開立錯誤」本來就要作廢，與退不退款無關。
13. **捐款項目不得附回饋品**（v1.3）。附球衣或贈品可能使捐款被認定為買賣或附負擔贈與，落入消保法通訊交易解除權，與「不受理退款」的前提衝突。回饋品是主站付費會員的事，不要帶進慈善站。
14. **主體是協會，不是磐石**（v1.4）。前台的標誌、站名、信任區塊、發票與收據抬頭、系統信署名、對帳單抬頭一律為**台灣足球策略發展協會**。看到舊文件寫「俱樂部留存」「寄給俱樂部」「沿用 TCRFC 品牌資產」一律視為錯誤。`club_amount` 已更名為 `association_amount`。
15. **協會品牌資產尚未提供**（v1.4）。前台與 QR 印刷版樣板一律留佔位，**不得沿用 `brand/svg/` 的 TCRFC 標誌，也不得自行為協會排字造標**。英文版一律以 the Association 代稱，協會英文全名待確認。
16. **後台仍共用俱樂部官網，但個資蒐集者是協會**（v1.4）。兩造須簽委託處理個人資料的書面約定，並於隱私權政策揭露。這是上線前的必要文件，不是可延後的行政事項。
17. **「立案」不等於「法人登記」**（v1.5）。協會的人民團體立案已完成（台內團字第 1150283692 號），但《公益勸募條例》的勸募團體限於公立學校、行政法人、**公益性社團法人**與財團法人，須另向法院完成社團法人登記。**看到「立案證書已取得，所以可以開始勸募」一律視為錯誤**；法人登記未確認前不得公開勸募、不得印製 QR Code。
18. **協會統編尚未取得**（v1.5）。兩張證書皆無統編，發票抬頭、捐贈收據與對帳單都要用到，屬上線前提。信任區塊可先填立案字號、成立日期與會址。
19. **負責人姓名與出生日期是個資**（v1.5）。只存在 `reference/` 的證書影像裡，**不得寫入規格、前台頁面或任何會公開的檔案**，也不要在對話與交付物中複述出生日期。
