## 1. 為什麼要有 docs/

專案的規格集中在一份 1138 行的 [`../output/TCRFC_前後台功能規劃書.md`](../output/TCRFC_前後台功能規劃書.md)。
它對人類閱讀是好的（一份文件、線性、可直接交付客戶），但對 AI 工作有兩個問題：

1. **整份載入會吃掉大量 context**，排擠實際工作所需的檔案內容。
2. **規格與執行規範混在一起**——「網站要有什麼」跟「我們怎麼做」是兩件事，前者屬客戶交付物，後者屬內部工作方式。

因此切成三層：

| 層 | 檔案 | 職責 | 可否修改 |
|---|---|---|---|
| **真實來源** | `output/TCRFC_前後台功能規劃書.md` | 網站要有什麼功能 | 改動＝需求變更，須同步英文版與 PDF |
| **導航層** | `docs/01`–`docs/05` | 規劃書的濃縮與索引，附行號指回原文 | 隨規劃書同步 |
| **執行層** | `docs/06`–`docs/08`、`CLAUDE.md` | 我們怎麼做：慣例、管線、排程 | 隨工作方式演進 |

**衝突處理原則**：導航層與真實來源不一致時，以真實來源為準，並修正導航層。
**禁止**在 `docs/` 憑空新增規劃書沒有的功能規格——那會製造第二個真實來源。

## 4. 適合委派給子代理的工作

本專案的多數任務是單線的文件與內容工作，**不需要動用子代理**。真正值得委派的只有幾種：

| 情境 | 建議 |
|---|---|
| 掃描收件夾、盤點數百個檔案 | 交給 `Explore` 或 `general-purpose`，只回報結論清單，不要把檔案內容全帶回主 context |
| 網站實作階段的前端元件 | `frontend-architect` |
| 部署到 Cloudflare | `deployment-engineer`（既有 mockup 已用 Cloudflare Pages） |
| 資料表與 API 設計 | `system-analyst` 或 `backend-engineer` |

**不要**為了「寫一段文案」「改一個表格」啟動子代理——委派成本高於直接做。

## 5. 已知的踩雷點

1. **`D1` 撞名**：`D1` 是隊別代號（一線隊）。後台課程模組原本編 `D1–D4`，已改為 `P1–P4`。看到「D1 課程管理」一律是舊資料。
2. **女足的例外**：06 女子足球是**單頁 Page**，不套用 `Team`/`Player`/`Match` 模型，也不進行事曆。很容易誤當成第五支球隊。
3. **行事曆是彙整層不是資料源**：賽事在 C4 維護，行事曆（L）只提供統一檢視。不要設計成兩份資料。
4. **課程不進行事曆**：兒童訓練、夏／冬令營、專項訓練的時段留在 05 課程頁，行事曆只放比賽與俱樂部活動。
5. **Shopify 邊界**：官網只做櫥窗與導流，任何購物車／金流／庫存／訂單的需求都超出範圍。
6. **會員與 Shopify 不做 SSO**：會員優惠一律以發送折扣碼處理。
7. **本目錄不是 git repo**：沒有 undo。
