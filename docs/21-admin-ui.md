## 1. 版面骨架

### 1.0 先排除一種：純頂欄式選單（不比較，直接刷掉）

14 個一級模組、最深兩層（一級模組 → 子模組，`S` 有 6 個子模組），這個量放進頂欄的橫向選單或 mega-menu
會過寬且必須換行或水平捲動。這一點與配色無關，深色化不會讓它變得可行，所以不列入下面的正式比較，
直接沿用 v1 的排除結論。

### 1.1 兩種可行骨架的比較

以下兩種都用 Element Plus 現成元件組得出來，都通得過「不需要大量自訂元件」這條實作成本門檻，值得認真比較：

| | **方案 A：側欄＋頂欄（單一導覽面板）** | **方案 C：圖示軌＋內容面板（雙層導覽面板）** |
|---|---|---|
| 結構 | 一個可展開／收合的側欄（`el-menu` vertical），展開時同時看到分組標籤與模組名稱 | Level 0 是固定寬度的圖示軌（僅圖示，約 8 個群組圖示），點擊後在圖示軌右側浮出/釘住一個內容面板列出該群組的模組 |
| 找模組的點擊次數 | 展開態 1 次；收合態 hover 後 1 次 | 恆定 2 次（先選群組圖示，再選模組），即使側欄本來就展開也一樣 |
| 中文模組名稱的辨識度 | 全程看得到文字，不依賴圖示語意 | Level 0 只有圖示，6 組分組要各自對應一個夠獨特的圖示，中文模組名（如「搜尋與 AI 能見度」）本來就不好濃縮成一個圖示，容易產生「這個圖示是什麼」的二次學習成本 |
| 深層結構的呈現 | 手風琴子選單（`unique-opened`），與 v1 相同機制 | 兩層面板天生對映「6 群組 → 14 模組」，但 `S1–S6` 這種**第三層**仍要在內容面板裡再做一次展開，一樣需要手風琴，並沒有真的省掉一層 |
| 實作成本 | 重用 `el-menu` 官方 API，无需自訂同步邏輯 | 需要兩個面板互相同步當前選中狀態、面板寬度動畫、圖示軌本身要另外設計選中態視覺——是**自訂複合元件**，不是單一 `el-menu` 呼叫 |
| 桌面內容區可用寬度 | 展開態佔 240px；收合態佔 64px | 圖示軌固定佔約 64–72px；內容面板另外再佔約 220px（釘住時）——與方案 A 展開態寬度相近，並沒有明顯省寬度 |
| 對本專案既有 nav 資料結構（`NAV_GROUPS`：6 群組 → 14 模組 → 子模組）的貼合度 | 直接對映，一份資料結構打完收工 | 同一份資料結構要拆成「Level 0 群組」與「Level 1+2 模組樹」兩套渲染邏輯 |

**決定：維持方案 A（側欄＋頂欄），但版面骨架本身要有實質修改**，不是換個顏色就交差。理由：

- 兩種方案在「能放下 14 模組」這件事上打平，方案 C 唯一的優勢（圖示軌更省視覺重量）在 14 個模組、6 個分組
  的規模下並不明顯，卻要多付兩個面板同步的實作成本，且圖示語意化中文模組名稱的學習成本是真實成本，
  不是想像出來的風險。
- 方案 C 的點擊次數是**恆定 2 次**，即使使用者已經記熟某個模組在哪裡，也無法像方案 A 展開態那樣一眼直接點——
  這對「天天使用的內部工具」是負向影響，天天用的工具應該讓熟練使用者越用越快，不是每次都固定兩步。
- **沒有任何一條原本支持方案 A 的理由是因為淺色主題才成立**——v1 選側欄是因為模組數量與深度，這件事跟
  配色無關，深色化不會讓側欄變得不適用，所以沒有「因為換深色所以要換骨架種類」的理由。

**但骨架內部的三個部件全部重新設計（這才是「不是精修」的部分）**：頂欄從一列改兩列（§1.2）、側欄的密度與
選中態視覺改用色階而非填色塊（§1.3、§7）、行高與間距尺度整套重定義（§2、§3）。

### 1.2 頂欄拆成兩列：系統列＋頁面列

v1 只有一列 56px 的頂欄，站台切換器、hamburger、通知、使用者選單、模組標題、「這裡管理的是」全部擠在
同一行，寬度不夠時（見 §13.3 舊版實作教訓）容易互相碰撞。這次拆成語意不同的兩列：

| 列 | 高度 | 放什麼 | 色階（見 §7） |
|---|---|---|---|
| **系統列** | 40px | hamburger／收合鈕、站台切換器、通知、使用者選單——這些是**跨模組、任何頁面都一樣**的全域控制 | `--admin-bg-surface-2`（比頁面列更亮一階，讀起來像一條固定貼在最上面的系統膠條） |
| **頁面列** | 64px | 模組標題（`<h1>`）＋「這裡管理的是」meta 列（見 §6）——這是**隨頁面內容變動**的區域 | `--admin-bg-surface`（與側欄、卡片同一色階，屬於「內容邊框」而非「系統膠條」） |

理由：深色介面下，區塊之間如果只靠一條 1px 邊框分隔，視覺切分會比淺色底弱很多（淺色底可以靠陰影與留白
暗示層次，深色底這兩招都比較弱，見 §7 的陰影失效討論）。把「全域」與「頁面」兩種不同語意的控制**用不同
色階明確分層**，比硬擠進同一列再用間距去暗示分組更可靠——這是本次真正的骨架級修改，不是換顏色。

系統列與頁面列之間、頁面列與內容區之間，都各自維持 1px 的 `--admin-border`，但主要的層次感來自色階差異
而不是邊框。

**新增的是選中態與 hover 態的視覺規則（v1 完全沒定義，直接用 Element Plus 預設藍底白字）**：

| 狀態 | 視覺 | 為什麼不用填色塊 |
|---|---|---|
| 一般 | `--admin-text-secondary` 文字，透明底 | — |
| Hover | `--admin-bg-surface-2` 底，`--admin-text-primary` 文字 | 只是「滑過」，不代表選中，用色階變化即可，不需要色相介入 |

## 2. 列表頁標準型（14 個模組共用一套）

骨架（由上到下）不變：篩選列 → 工具列 → 表格 → 分頁。**這次重新定義的是密度、字級與間距尺度**——
v1 完全沒訂這一層，各頁面各自為政，深色化後密度不一致的問題會比淺色更明顯（深色底下留白與擁擠的觀感差異
比淺色更劇烈，因為對比度天生比淺色高）。

### 2.1 間距尺度（spacing scale）

全站只用這一組數字，不要另外發明：

```
4 / 8 / 12 / 16 / 20 / 24 / 32 / 48（px）
```

| 用途 | 值 |
|---|---|
| 頁面外距（桌面） | 24px（手機降為 16px，見 §8） |
| 篩選列／工具列／表格三個 `el-card` 之間的垂直間距 | 16px |
| `el-card` 內距 | 20px |
| 表單欄位群組之間（`el-form-item` 上下） | 16px |
| 標籤與輸入框之間 | 8px |
| 按鈕群組內的間距 | 8px |
| 編輯頁各分段 `el-card` 之間 | 24px |

### 2.2 字級尺度（type scale）

**全部沿用 Element Plus 內建的 `--el-font-size-*`**，不另訂新尺度——Element Plus 預設的 12/13/14/16/18/20px
本來就跟後台操作介面常見的尺度幾乎一致，重新發明一套只會製造「這個字級用 Element Plus 的還是用 admin 自己
的」的判斷負擔。只需要明確列出**後台各層級文字對應哪一個**（v1 沒有這張表）：

| 層級 | 對應 Element Plus token | 字級 | 用途 |
|---|---|---|---|
| 頁面標題 | `--el-font-size-extra-large` | 20px | 頁面列的 `<h1>`（如「新聞與故事」） |
| 分段標題 | 介於 medium／large 間，手動指定 15px | 15px | 編輯頁 `el-card` 的段落標題（如「基本資訊」） |
| 內文／表格 | `--el-font-size-base` | 14px | 表格儲存格、表單輸入內容 |
| 次要文字 | `--el-font-size-small` | 13px | 表格次要欄位、批次操作列的「已選取 N 筆」 |
| 說明／時間戳 | `--el-font-size-extra-small` | 12px | 圖片上傳提示、欄位說明文字、卡片 meta |

### 2.3 表格密度與圖片欄的實際尺寸（v1 沒講清楚，這次講清楚）

v1 文字寫「一律顯示 160px 方形縮圖」，但 160px 其實是**規劃書 §4.0 圖片上傳通則規定的衍生檔規格**
（伺服器端固定產出的其中一個尺寸），不是「表格裡這張圖要佔 160px」的意思——現有可點 mockup
（`NewsListView.vue`）已經是用縮小顯示的做法，這裡把這件事正式寫進規格，避免下一次有人字面理解成
表格列高要做到 160px：

| 情境 | 實際顯示尺寸 | 來源 |
|---|---|---|
| 表格列內的縮圖 | **48×48px**，置中裁切，`4px` 圓角 | 直接用 160px 衍生檔按比例縮小顯示，瀏覽器算，不必後端另生一個更小的檔 |
| 點擊縮圖放大檢視 | 用 `el-image` 的 `preview-src-list`，帶出 1280px 衍生檔 | 160px 衍生檔解析度不夠拿來放大看，這裡改接規劃書定義的另一個尺寸級距 |
| 手機卡片式列表的縮圖 | 56×56px | 見 §8，卡片式列表本身有更多留白，縮圖可以比桌面表格略大 |

## 3. 編輯頁標準型

分界點不變（欄位少、無雙語長文字用 `el-dialog`／`el-drawer`；欄位多或含雙語內容用整頁）、欄位分組順序
不變（基本資訊 → 內容（雙語）→ 圖片 → 專屬欄位 → 發布設定）、必填標示不變（統一放 label 前方）、
雙語呈現規則不變（短欄位並排、長欄位用 `el-tabs`）、儲存／發布／預覽按鈕邏輯不變（同一顆按鈕依狀態變化
文字）、離開未儲存提醒不變——**這些都是與配色、骨架種類無關的互動規則，重新設計版面骨架不代表要重新發明
已經驗證合理的互動細節**，故全部沿用 v1，不在此重複列出理由（理由請見本檔舊版歷史或規劃書 §4.0）。

### 3.1 深色底下真正需要重新設計的：分段卡片的「層次感」怎麼做

v1 的卡片分層靠「1px 邊框 + 極淺陰影」。**這個做法在深色底下實質失效**：`box-shadow` 要讓人感知到，
依賴陰影顏色比周圍背景更暗、且周圍要有夠亮的底色襯托陰影的邊緣；深色 UI 裡陰影本身通常也是深色（黑色
半透明），疊在已經很暗的背景上，人眼幾乎分辨不出陰影的邊界在哪——這是深色介面設計的通識問題，不是本專案
特有的疑慮（Material Design 的深色主題規範正是因為這個原因，改用「色階分層（tonal elevation）」取代陰影：
海拔越高的元件，背景就疊加更多白色調、變得更亮，而不是加深陰影）。

**本檔採同樣邏輯**：编輯頁的分段卡片不再靠陰影分層，改靠 §7 定義的四層背景色階本身的亮度差異來分層：

```
canvas（頁面底，最暗）→ surface（分段卡片、側欄、頁面列）→ surface-2（卡片內的巢狀表格／hover／選中態）
→ overlay（下拉選單／對話框／彈出提示，最亮，因為這些是暫時浮在最上層的東西）
```

編輯頁的分段卡片一律用 `surface`，卡片內如果有巢狀表格（如商品規格子表）用 `surface-2` 做出「卡中卡」的
層次，不使用陰影。卡片仍保留 1px `--admin-border` 邊框，邊框在深色底下的作用比淺色底更吃重（陰影不可靠，
邊框變成主要的邊界線索），所以**邊框不可省略**，這點與淺色主題（邊框可有可無、靠陰影就夠）不同。

## 4. 狀態呈現

四態模型（草稿／排程發布／已發布／已停用）本身、語意、不是每個模組都有四態、商店訂單走自己的狀態機但
沿用「顏色語意化」這個視覺語言——這些都不變。**重新計算的是深色底下的實際色票**，並回應「四態要能被
色盲使用者區分、不能只靠色相」這條要求。

### 4.1 色盲可辨識性：真正的防線是文字標籤，不是色相選得多巧妙

v1 與本次設計的四態 tag **本來就都帶文字**（「草稿」「排程發布」「已發布」「已停用」直接印在 tag 裡），
這已經滿足「不能只靠色相傳達資訊」——WCAG 對「使用色彩」的要求本來就是「色彩不能是唯一的資訊管道」，
文字標籤已經是主要管道，色相只是輔助加速辨識。所以這裡**不需要另外加圖示**（加圖示是可以做但不是必要的
加分項，本檔不把它列為規格，避免無謂墊高實作成本）。

真正要注意的是：四個顏色即使色相不同，**在色盲模擬下彼此的「明度」不能太接近**，否則色盲使用者掃視表格
時連輪廓都分不出來（文字要湊近看才分得出來，但操作介面本來就期待可以遠遠掃一眼分辨狀態）。下表選色時
刻意讓四色的明度／飽和度也拉開差距（草稿最暗最中性、已停用是暗酒紅、警告是高明度琥珀、成功是中高明度綠），
不是四個顏色明度都差不多只靠色相分。

### 4.2 四態色票（深色底，附實際對比度）

底色統一用「深色語意底＋亮色語意文字」的 tag 樣式（不是 v1 那種淺色語意底），理由：深色底上如果沿用
Element Plus 淺色 tag 的做法（極淺色底＋深色字），淺色色塊在深色頁面裡會變成一塊突兀的高亮方塊，破壞
整頁的深色調性；改成「深色但帶色相的底 ＋ 高亮度同色相文字」，色塊本身仍融在深色介面裡，靠文字的亮度
與色相做出辨識度。

🔴 **v3（2026-09-22）更新**：草稿 tag 的底色／文字色**跟著 §7.2／§7.3 的新暖色階連動**（它們本來就是直接
借用 `--admin-bg-surface-2`／`--admin-text-secondary` 這兩個 token，不是獨立寫死的色號，token 值換了它們就跟著換）。
排程發布／已發布／已停用三態是**獨立配色、不掛在中性色階上**，這次沒有改值，只重新驗算對比度（背景不變，
數字理論上不變，但仍照 `E-31` 的規矩實跑一次，不是「應該沒變就跳過」）。

| 狀態 | 畫面文字 | 底色 | 文字色 | 對比度 | 使用情境 |
|---|---|---|---|---|---|
| 草稿 | **草稿** | `#31231F`（`--admin-bg-surface-2`，v3 起＝品牌黑 `--ink-2`） | `#B7B0AC`（`--admin-text-secondary`，v3 暖化） | **7.06:1 ✅ AA**（v2 為 6.93:1，數字微升是因為新底、新字色的相對亮度都重算過，不是筆誤） | 尚未對外顯示 |
| 排程發布 | **排程發布** | `#3A2E14`（獨立配色，不隨中性色階變動） | `#FFB84D` | **7.73:1 ✅ AA**（與 v2 相同） | 已通過審核、等時間自動轉已發布 |
| 已發布 | **已發布** | `#13301F`（獨立配色，不隨中性色階變動） | `#5FD68A` | **7.80:1 ✅ AA**（與 v2 相同） | 前台看得到 |

相同且在深色底下依然成立：已停用是「狀態」，危險色是「這個操作會造成不可逆後果」的警示，兩者語意不同，
不該共用一套顏色讓使用者以為刪除按鈕也在講「已停用」這件事。**v3 危險色的色相往橘紅移動後（見 §4.3 的
色差實測）與已停用的暗酒紅、與品牌桃紅都拉得更開**，這條區隔在 v3 底下更成立不是更薄弱。

### 4.3 操作型語意色（表格文字、按鈕、非四態的其他 tag）

🔴 **v3（2026-09-22）設計問題：主色改桃紅之後，危險色（紅）與主色（桃紅）在深色底上的辨識度會不會下降？**
這是使用者拍板時明確要求回答的問題，不能迴避。做法是**先實測色差，再決定要不要動危險色**，不是憑印象
覺得「應該分得出來」：

- **量測方法**：CIE76 ΔE（Lab 色彩空間的歐氏距離；比更精細的 CIEDE2000 簡化，但仍是實際公式運算，
  不是眼睛比對）＋ Lab 色相角（判斷兩色在色相環上多接近，這對色覺辨識能力較弱的使用者更關鍵，因為色盲
  主要影響的是色相辨識而不是明度／彩度辨識）。
- **v2 舊配色的實測結果（不是猜的）**：舊危險文字 `#FF9494` 與品牌桃紅 `#E0218A` 的 Lab 色相角相距
  **30.71°**、ΔE76 **49.31**——這兩個數字其實已經不算太差（ΔE76 一般認為 >10 就是人眼容易分辨的差異），
  但 30.71° 的色相間距偏窄（兩者都在「洋紅－紅」這個窄區間裡），對色覺辨識較弱的使用者是可以再拉開的空間。
- **v3 的處理：把危險色的色相往橘紅推移**，明度與飽和度沿用 v2 的原值不變（只調色相，方便對照），
  從 `H≈0°`（純紅）推到 `H=14°`（橘紅，介於純紅與 `#FFB84D` 琥珀警告色的 `H≈36°` 之間，兩邊都留出間距，
  不會被誤認成警告色）：
  - **文字**：`#FF9494` → **`#FFAD94`**（`H,S,L` 從 `0°,100%,79.02%` 改為 `14°,100%,79.02%`，只動色相）
  - **實心按鈕底**：`#B3453F` → **`#B35A3F`**（`H,S,L` 從 `3.10°,47.93%,47.45%` 改為 `14°,47.93%,47.45%`）
  - **推移後與品牌桃紅的色相相距拉大到 49.69°（原 30.71°，+62%），ΔE76 拉大到 65.03（原 49.31，+32%）**，
    危險文字對 `--admin-primary`（`#E85BA9`）的 ΔE76 為 **55.49**，危險按鈕底對 `--admin-primary-fill`
    （`#D61E83`）的 ΔE76 為 **56.14**——兩組都比 v2 的品牌色／危險色間距更遠，不是更近。
- **誠實的但書**：這個色差在正常視覺下**本來就不算嚴重的問題**（ΔE76 ~49 已經是容易分辨的差距），
  v3 的橘紅化是「錦上添花的加碼保險」，不是「修一個原本會混淆的錯誤」。真正決定使用者分不分得清楚的，
  其實是下面這條結構性理由：**危險操作在列表頁本來就是純文字／連結按鈕**（§2.4「危險操作（刪除文字按鈕／
  連結）」），**只有主要操作（儲存／發布）才是實心填色按鈕**——兩者形狀本來就不同（有無底色），色相
  只是輔助線索，不是唯一線索。**唯一的例外場景**是刪除確認對話框（`el-dialog`）裡「確認刪除」與「取消」
  兩顆按鈕相鄰：這裡明訂 **「取消」一律用預設（中性）樣式，不得用 primary 樣式**，避免對話框裡出現
  「桃紅實心 vs 橘紅實心」兩顆同形狀按鈕並排的情境——這條規則寫進本檔正式規格，不是建議。

| 用途 | 文字色（單獨置於 `surface` `#231916` 上） | 對比度 | 實心按鈕底 | 按鈕文字 | 對比度 |
|---|---|---|---|---|---|
| 危險（刪除、不可逆操作） | `#FFAD94`（v3 由 `#FF9494` 橘紅化） | **9.54:1 ✅ AA** | `#B35A3F`（v3 由 `#B3453F` 橘紅化） | 白字 `#FFFFFF` | **4.72:1 ✅ AA**（v2 為 5.47，橘紅化後降低但仍有 0.22 餘裕） |
| 警告 | `#FFB84D`（不變） | **10.00:1 ✅ AA**（v2 為 9.61，新 `surface` 略暗，數字微升） | `#FFB84D` | **深字** `#150F0D`（v3 起＝新 `--admin-bg-canvas`，不用白字，見下） | **11.04:1 ✅ AA**（v2 為 10.54） |

⚠️ **警告色的實心按鈕刻意用深字不用白字**：白字直接套在 `#FFB84D` 這種高明度琥珀色底上只有 **1.72:1**
（v3 重驗仍是 1.72，這組不依賴中性色階，數字不變），過不了小字 AA；文字改用 `--admin-bg-canvas`
深色則有 **11.04:1**。這不是隨意選擇——琥珀／黃色系底配深色文字是業界慣例（Material、Bootstrap 的警告色
按鈕都用深字不用白字），本檔採用同樣做法，理由完全是對比度數字算出來的，不是美感偏好。

### 4.4 編輯頁的狀態呈現

排程顯示「將於 2026-09-25 08:00 發布」；已停用顯示「於 2026-06-01 由王小明 下架」。

## 5. 站台切換器

位置（頂欄，見 §1.2 現在在**系統列**）、下拉行為、只授權一個俱樂部時改純文字標籤——這些互動規則不變。
**這次要正面回答的是任務指定的問題：「深色主題本身就是一次全站換色，這跟『切換站台只換一個徽章、不換品牌色』
的決定是否還相容？」**

### 5.1 兩件事不是同一種「換色」

v1 的理由是：如果切換站台會讓整個後台變成粉紅色或藍色，使用者會把「顏色」誤讀成「我現在的權限範圍」，
但實際的資料範圍限制是在資料存取層強制的，跟畫面顏色無關；規劃書明文「切換器是介面便利，不是安全邊界」，
設計上不該做出容易被誤讀成安全機制的效果。

深色化本身確實是「整個後台的顏色都變了」，但這跟「切換站台換色」是**兩種性質完全不同的變色**：

| | 深色主題 | 若切換站台換品牌色 |
|---|---|---|
| 變化的時機 | 系統層級設定，登入前就固定，不隨操作變動 | **隨每一次切換動作**即時變化 |
| 是否與「目前操作範圍」相關 | 完全無關——不管站在哪個俱樂部底下，深色永遠是深色 | **直接與**目前操作的俱樂部**綁定** |
| 是否所有俱樂部看到的一樣 | 一樣（兩個俱樂部的後台深色調完全相同） | 不一樣（磐石桃紅 vs 藍鯨藍，兩站分別著色） |
| 會不會被誤讀成「顏色標示權限範圍」 | 不會，因為顏色從不因操作而改變 | **會**，這正是 v1 想避免的效果 |

深色主題是**與俱樂部無關的全域系統設定**，切換站台換品牌色則是**與俱樂部強相關、隨操作變動**的視覺效果——
會製造「顏色＝權限範圍」錯覺的是後者這種特性，不是「畫面是深是淺」本身。所以**深色化不影響、也不稀釋
v1 這條決定的理由，兩者不衝突，維持不換品牌色的決定**。

### 5.1.1 v3 新問題：主色本身就是磐石品牌色了，藍鯨維運人員會不會覺得「這是磐石的系統」

🔴 **這是使用者拍板時明確要求正面回答的問題，不是可以迴避的枝節**。v2 時代操作主色是與任何俱樂部都無關
的 Element Plus 中性藍，「不換色」的意思是「這套系統的顏色跟哪隊都沒關係」；v3 之後操作主色本身**就是**
磐石的品牌桃紅（`--brand` 系），「不換色」現在的實際意思變成「不管站在哪一隊底下，畫面裡的按鈕、連結、
focus 外框、側欄選中態通通是磐石的顏色」。這是兩件不同的事，必須誠實面對，不能因為要順從拍板就美化。

**這個疑慮是真的，理由如下：**

- 操作主色**不是偶爾出現**的裝飾——它是儲存按鈕、發布按鈕、連結色、focus 外框、側欄選中態 accent bar
  這些**每天、每個操作都會看到**的元素，且**藍鯨自己的隊徽藍（`#2196D5` 系）在這次拍板後仍然只被用在
  站台切換器的裝飾性小圖示，不會出現在任何一顆功能性按鈕上**——藍鯨員工每天使用的介面，操作層面的顏色
  語言全部是磐石的，藍鯨的顏色只在頂端一個小圖示。
- 這與 v1／v2 的「不因切站而換色」不是同一件事：v1／v2 的規則解決的是「顏色會不會被誤讀成權限範圍」
  這個**安全／誤讀**問題；這次的新問題是「品牌歸屬感」問題，是完全不同的軸線，v2 的論證從未回答過這一題，
  因為 v2 的主色本來就是中性的，根本沒有「這顏色是哪隊的」這個問題可以問。

**但這個疑慮不足以推翻拍板，理由如下（結論可能被使用者推翻，但推理過程要誠實）：**

1. **這是品牌歸屬感問題，不是 v1／v2 那條規則要解決的安全問題**——§5.1 的論證（主色不隨操作變動、
   不會被誤讀成權限範圍）在新問題底下**依然完全成立**，兩者是不同的軸線，新問題的存在不代表舊論證
   失效，只代表**多了一個舊論證沒有涵蓋到的面向**，這個面向需要另外評估，不是自動推翻舊結論。
2. **現階段的實際使用者是同一批人**：依 [`14-invariants.md`](14-invariants.md)，藍鯨官網與後台
   「由磐石的團隊在營運」，且「第一階段這個角色可以先不指派使用者」——換句話說，**目前會用這套後台的
   人，本來就是磐石自己的營運團隊在管理兩隊的資料，不存在『藍鯨自己的員工打開後台覺得這不是我的系統』
   這個場景**。這個疑慮描述的是一個**尚未發生的未來狀態**（藍鯨有了自己獨立的營運人力之後），不是現在
   要解決的問題。
3. **色彩可逆、成本低**：整套配色是變數化的 token（§7.0 已經是既有原則），日後若藍鯨真的有了獨立營運
   團隊、且真的反映這個困擾，換掉 `--admin-primary` 系的幾個 token 值是一次性的改值，不是重新設計系統。
   現在為了一個假設性的未來場景去否決已經拍板、且已經花時間驗算過對比度的方案，不成比例。

**因此判斷：這個疑慮成立但不夠格推翻拍板，維持「配色改品牌桃紅、切站不換主色」的決定。** 但建議兩件低
成本的緩解措施，寫進正式規格（見 §5.3、§7.7）：**站台切換器的隊徽圖示改用兩隊各自的真實隊徽圖像**（不是
純色色塊），讓「這是哪一隊」的識別**來自圖像本身**而不是操作色系；並將此列為**待追蹤事項**（見 §12）——
一旦藍鯨有了獨立於磐石團隊之外的實際操作人員，這題要重新徵詢當事人的真實感受，不能只靠現在的推論定案。

### 5.2 深色底下品牌色的對比度重新計算

品牌色的值不變（唯一來源仍是 `reference/TCR_logo_CMYK.ai` 與 `brand/blue-whale/`），但深色底下要用哪一個
既有的衍生色階（`--brand` / `--brand-aa` / `--brand-bright` / `--brand-deep`），對比度跟白底完全不同，
必須重算。**v3 起 `surface` 本身換成品牌黑 `#231916`（見 §7.2），所以這張表全部要重新對新的 `surface` 算一次**
——這不只是「配色風格改了」，是**背景色的實際數值變了，任何一組舊數字都不能延用**：

| 用途 | 磐石桃紅 | 對比度（against 新 `surface` `#231916`） | 藍鯨藍 | 對比度（against 新 `surface`） |
|---|---|---|---|---|
| 隊徽色塊本身（非文字，裝飾用） | `--brand` `#E0218A` | 3.89:1（v2 為 3.74，裝飾用不強制達文字 AA） | `--brand` `#2196D5` | 5.23:1（v2 為 5.03） |
| 小範圍文字／icon 點綴／連結／accent bar／focus 外框 | `--brand-bright` `#E85BA9` | **5.32:1 ✅ AA**（v2 為 5.12） | `--brand-bright` `#50B0E4` | **7.10:1 ✅ AA**（v2 為 6.82） |
| 實心底＋白字（v3 起也是操作主色實心按鈕 default，見 §7.5） | `--brand-aa` `#D61E83` 底配白字 | **4.80:1 ✅ AA**（不依賴 `surface`，自成對，數字不變） | `--brand-aa` `#1A78AA` 底配白字 | **4.87:1 ✅ AA**（同上，不變） |

**注意這跟白底的規則完全相反**：白底時 `--brand` 對白只有 4.42:1／3.29:1（磐石／藍鯨），過不了小字 AA，
所以白底小字要改用 `--brand-aa`；深色底時反而是 `--brand` 正色本身當文字用對比度不夠（3.89:1／5.23:1，
磐石那組甚至連大字都勉強），要改用更亮的 `--brand-bright` 才夠。**深色與淺色底下「哪一個衍生色階該用在
哪裡」不是同一套規則，這是本次重算最容易被誤用舊規則的地方**，下一位工程師照抄 v1／`06-conventions.md`
白底的規則表直接套進深色 admin，會做出對比度不足的畫面。

🔴 **v3 新增**：`--brand-aa` 與 `--brand-deep` 這次**升格為操作主色本身**（不再只是「品牌色小範圍點綴」的
角色），完整的操作主色四階分工（文字／連結／icon 用哪一階、實心底 default／hover／active 各用哪一階）
見 §7.5，那裡是本次色票重算的主戰場，這裡不重複。

### 5.3 站台切換器視覺（深色版）

```
[🏉台中磐石 ▾]     ← 系統列，隊徽小圖示（16px）改用真實隊徽圖像，見下
```

🔴 **v3 更新：隊徽小圖示不再是純色圓點色塊，改用兩隊各自的真實隊徽圖像**（磐石用
[`brand/svg/`](../brand/svg/) 的隊徽 SVG、藍鯨用 [`brand/blue-whale/`](../brand/blue-whale/README.md) 的
點陣主檔裁切出的圖示）。**理由直接回應 §5.1.1 的疑慮**：v2 的做法是「16px 圓點，色塊本身用 `--brand`
正色」，v3 操作主色也改成品牌桃紅系之後，如果圖示仍是純色圓點，它會**視覺上融進其他一堆同色系的操作
元件（按鈕、連結、focus 外框）裡**，失去「這是俱樂部識別」的獨立辨識度——換成真實隊徽圖像後，圖示的
辨識來源是**圖形本身**（磐石隊徽 vs 藍鯨隊徽兩個完全不同的圖案），不是色相，天然不會被操作色系稀釋，
也不需要额外的色彩對比度規則（隊徽圖像本身有自己的用色，不受 `--admin-primary` 系 token 支配）。

切換後行為不變：跳 `el-message`（success 樣式，深色版見 §7）「已切換至台中藍鯨的管理畫面」；共用內容
（`club_id` 為空）唯讀時仍顯示「共用內容（唯讀）」tag（沿用 §4.3 的中性／資訊色）＋ 儲存按鈕 disabled
＋ tooltip「這是兩隊共用的內容，你的帳號僅能檢視」。這條「唯讀情境的按鈕不隱藏、要解釋原因」的例外規則
與配色無關，不變。

## 6. 「這裡管理的是」呈現

規劃書 §4.0 的硬性規定（「對不上的模組就是切錯了」）內容不變：每個模組頁首要說清楚它產出前台的哪裡，
並附預覽連結。**這次重新設計的是呈現形式**，順便處理掉 §14.3 記錄的舊版手機換行問題——不是事後補丁，
是從版面結構上讓那個問題不會發生。

### 6.1 v1 的問題：擠在標題同一行右側

v1 把「這裡管理的是：{名稱} ↗」放在頁首標題**同一行的最右側**（`justify-content: space-between`）。
這個排法在桌面沒問題，但手機寬度下標題與這段說明文字要共用一行的空間本來就不夠，v1 只能靠 `flex-wrap`
讓它自己換到標題下一行，換行後那一行內部又設了 `nowrap` 導致文字被裁掉（§14.3 記錄的實際踩雷）。

### 6.2 v2：獨立成頁面列的第二行，不與標題搶同一行

配合 §1.2 的頁面列改版，「這裡管理的是」現在**本來就是頁面列的第二行**（標題在第一行，meta 列在第二行），
不需要跟標題共用寬度，也就不會有兩者互相擠壓的問題——這是結構性解法，不是加媒體查詢補救：

```
新聞與故事                                                    ← 頁面列第一行（標題）
這裡管理的是：新聞中心 ↗                                         ← 頁面列第二行（meta，永遠獨立一行）
```

meta 列本身允許自然斷行（不設 `nowrap`），桌面與手機共用同一份排版規則，不需要為手機另外寫斷行例外——
這比 v1「桌面 nowrap、手機另外拔掉 nowrap」的做法更簡單，也从根源上排除同一類坑。

### 6.3 三種行為不變

延續 §14.1 記錄的規則（`link`／`none`／`app` 三種）：

- **有對應前台頁面**（`link`／`multi`）：可點擊連結，深色底下連結色用 `--admin-primary`
  （v3 起＝品牌桃紅 `--brand-bright` `#E85BA9`，against `surface` `#231916` **5.32:1 ✅ AA**，見 §7.5），
  hover 加底線。⚠️ **這個連結色只保證在 `canvas`／`surface`／`surface-2`／`input` 四層過 AA，`overlay`
  層（對話框、下拉選單）對比度只有 4.02:1、過不了小字 AA**（見 §7.5 的使用範圍限定）——但「這裡管理的是」
  這種連結固定出現在頁面列（`surface`），不會出現在 overlay 情境，這條限制不影響本節的實際用法。
- **無前台產出**（`none`，如儀表板、系統管理）：灰字說明「本頁僅供後台管理使用，沒有對應的前台頁面」，
  用 `--admin-text-tertiary`（v3 起＝ `#A39B95`，對 `surface` **6.28:1 ✅ AA**，比 v1 淺色底下的規則同樣
  要求可讀，不因為是次要說明文字就放寬到不過 AA）。
- **產出行動 App 或「前台只送出」的模組**（`app`，如 `M` 全部、`E4–E6`、`P3`／`P4`、`G1`／`G2`）：
  灰字顯示但不可點擊，理由不變（沒有 URL 可連，硬做連結會連到 404）。

編輯頁（單筆資料層級）同樣位置，連結指到這一筆資料的實際前台網址；尚未發布的資料維持 §3 的「預覽」按鈕
disabled + tooltip 處理方式（草稿預覽機制仍是待補的後端功能，見 §12）。

## 7. 配色與 design tokens

### 7.0 決定：深色是唯一主題，不做深／淺雙主題（🔴 使用者已拍板，2026-09-21）

🔴 **使用者拍板（2026-09-21）：只做深色，不做淺／深雙主題。** 本檔原先把這題列為待決並建議只做深色，使用者已明確採納。以下保留當初的理由，因為它們同時也是往後「要不要回頭加淺色模式」的判斷依據：

1. **雙主題的維護成本是持續性的，不是一次性的**：14 個模組、往後每一個新畫面都要同時驗證兩組 token 在
   兩種底色下的對比度，這比單一主題的工作量不只多一倍——因為深色與淺色底下「同一個語意色該用哪個衍生
   色階」的規則常常相反（見 §5.2 的實例：品牌色在深底要用更亮的變體，在淺底要用更暗的 AA 變體），兩套
   規則要同時維護、同時測試，錯一邊很容易漏掉。
2. **「深色影響照片色調判斷」這個疑慮，正確的解法不是切回淺色，而是 §9 的中性看片台**：任何色彩管理
   軟體（Lightroom、Photoshop）都不會用「整個應用程式介面的底色」當作照片判色的參考面，而是在圖片預覽
   區塊本身鋪一塊固定的中性灰（或透明棋盤格），這塊參考面**不隨應用程式的主題切換而改變**。也就是說，
   就算做了淺色模式，只要圖片預覽框不是中性灰，淺色模式一樣不能保證色彩判斷準確（一般網頁的純白底其實
   也會讓亮部看起來偏暗、偏冷，不是天然的判色參考面）。真正解決這個疑慮的是 §9 訂的中性看片台，
   跟整體介面深淺無關，所以「怕影響照片判斷」不構成一定要做淺色模式的理由。
3. **使用者已經拍板要深色**，若同時做雙主題、又把淺色設為預設或平行選項，會稀釋掉這次改版真正要驗證的
   東西（深色 token 系統本身好不好用）。先把深色做完整、跑過幾個模組驗證沒問題，之後若真的需要淺色，
   再回頭加第二套主題的成本是可控的（tokens 架構已經是變數化的，加一組值不是砍掉重練）。

**拍板後的實作意義**：`main.ts` 固定在 `<html>` 加 `class="dark"`，**不做主題切換開關、不留淺色 token
分支**（見 §7.9）。往後若真的要補淺色模式，成本仍是可控的——tokens 已經全部變數化，加的是第二組值不是
砍掉重練——但在那之前，**不要為了「將來可能要雙主題」而預先把樣式寫成兩套**，那等於現在就付了雙主題的
維護成本卻沒有得到它的好處。

### 7.1 實作策略：接 Element Plus 官方深色模式機制，不是從零手刻

Element Plus 2.9 本身就有**官方深色模式**（`element-plus/theme-chalk/src/dark/css-vars.scss`，透過在根
節點加 `class="dark"` 啟動），內建元件（按鈕、表格、標籤、輸入框、下拉選單、對話框……）已經各自定義好
深色版的 `--el-bg-color`、`--el-bg-color-page`、`--el-bg-color-overlay`、`--el-text-color-primary` 等
一整組變數，並且元件庫自己的 CSS 已經用這組變數畫好了每個元件的深色版外觀。

**這代表本次深色化的實作成本遠低於「大量覆寫 Element Plus 內建樣式」**——不需要重新畫按鈕、表格、下拉
選單的深色版外觀，只需要：

1. 在根節點掛 `class="dark"`，載入 Element Plus 的深色樣式表；
2. **覆寫**官方深色模式已經預留的那組 CSS variable 的**值**（不是新增選擇器去蓋樣式），換成本檔 §7.2
   定義的色票；
3. 只有 Element Plus 沒有對應變數的部分（例如本檔四個背景層級裡的 `surface-2`、四態 tag 的自訂色、
   側欄選中態的 accent bar）才需要額外寫 CSS，這部分範圍明確、可控，不是大面積覆寫。

**唯一需要誠實列出的額外成本**：Element Plus 官方深色變數只分三層（`--el-bg-color`／`--el-bg-color-page`／
`--el-bg-color-overlay`），本檔的分層需求是四層（見 §7.2 的 canvas/surface/surface-2/overlay），多出來的
`surface-2` 沒有現成官方變數可覆寫，需要**自訂一個 `--admin-bg-surface-2` 變數**並在側欄選中態、表格
hover／選中列、四態 tag 底色、系統列背景等處手動套用（不能透過覆寫官方變數自動生效）。這是本次唯一
「需要自己接線」的部分，其餘都是改值不改結構。

### 7.2 四層背景色階（v3：由品牌黑推導，不再是與品牌無關的中性冷灰）

```
canvas（最暗，內容區底、退到最後）
  ↓
surface（側欄、頁面列、分段卡片——與內容同一個平面）
  ↓
surface-2（系統列、巢狀卡片、表格 hover／選中列、四態 tag 底、側欄選中態底）
  ↓
overlay（下拉選單、對話框、彈出提示、抽屜——暫時浮在最上層的東西，最亮）
```

🔴 **推導方法（誠實交代，不是「取自品牌主檔」）**：品牌主檔只給了兩階深色 `--ink` `#231916`（K100）與
`--ink-2` `#31231F`。經實測，兩者是**同一條色相／彩度線上的兩個明度點**（`--ink`：H=13.85°／S=22.81%／
L=11.18%；`--ink-2`：H=13.33°／S=22.50%／L=15.69%，H／S 幾乎相同，只有 L 差 4.51 個百分點）。推導規則：

1. **`surface` 與 `surface-2` 直接沿用 `--ink`／`--ink-2` 原值**，不重新計算，因為品牌主檔剛好給了四層
   裡中間兩層需要的明度。
2. **`canvas`（比 `surface` 更暗）與 `overlay`（比 `surface-2` 更亮）用同一條色相／彩度線（`H=13.85°`／
   `S=22.81%`，取自 `--ink` 本身）往兩端各推一階，階距沿用 `--ink→--ink-2` 本來的 4.5 個百分點**，
   維持整條色階等距：`canvas` 的 `L = 11.18% − 4.5% = 6.68%` → `#150F0D`；`overlay` 的
   `L = 15.69% + 4.5% = 20.19%` → `#3F2D28`。
3. **`input`（比 `canvas` 更暗，做出表單欄位的「凹陷」感）再往同方向推一階**：`L = 6.68% − 4.5% = 2.18%`
   → `#070504`。
4. 以上 `canvas`／`overlay`／`input` 三個值**是本檔的衍生值，不是品牌主檔的實際用色**，只是沿用主檔的
   色相與彩度、不混入冷灰——這條交代清楚是為了不誤導下一位讀者以為這三個值也「取自 `.ai` 主檔」。

| Token | 值 | 對應 Element Plus 變數 | 用途 | 來源 |
|---|---|---|---|---|
| `--admin-bg-canvas` | `#150F0D` | 覆寫 `--el-bg-color-page` | 內容區背景（路由容器） | **衍生值**：`--ink` 同色相／彩度，L −4.5pp |
| `--admin-bg-surface` | `#231916` | 覆寫 `--el-bg-color` | 側欄、頁面列、`el-card` 預設底 | **= `--ink` 原值**，直接沿用 |
| `--admin-bg-surface-2` | `#31231F` | **自訂，無對應官方變數** | 系統列、巢狀卡片、表格 hover／選中列、四態 tag 底、側欄選中態底 | **= `--ink-2` 原值**，直接沿用 |
| `--admin-bg-overlay` | `#3F2D28` | 覆寫 `--el-bg-color-overlay` | `el-dropdown`／`el-dialog`／`el-popover`／`el-tooltip`／`el-drawer` | **衍生值**：`--ink-2` 同色相／彩度，L +4.5pp |
| `--admin-bg-input` | `#070504` | 覆寫 `--el-fill-color-blank`（輸入框底） | `el-input`／`el-select`／`el-textarea` 等表單欄位，比 canvas 更暗做出「凹陷」感 | **衍生值**：`canvas` 再 −4.5pp |

（v2 的冷灰值 `#14161A`／`#1C1F24`／`#242830`／`#2A2E36`／`#101215` 已作廢，見 §13。）

### 7.3 文字階層（v3：暖化，理由與笛卡兒積驗算）

🔴 **設計問題：品牌黑當 `surface` 之後，v2 的冷灰文字（`#E8EAED`／`#ABB2BF`／`#9299A8`，色相約 215°–220°，
偏藍）疊在暖調棕黑底上會顯得偏冷、髒——這條必須處理，不是可調可不調。** 處理方式：**保留每一階文字原本
的相對亮度（WCAG relative luminance Y）不變，只把色相從冷藍（約 220°）換成與背景同色系的暖灰（`H=25°`，
介於 `--ink` 的 `13.85°` 與純中性之間，選 25° 是刻意不要暖到跟背景同色相、避免文字被背景「吃掉」；
飽和度壓低到 `S=7%`，比背景的 `22.81%` 低很多，維持「文字是文字、背景是背景」的區隔）**。保留相對亮度
的做法讓對比度數字盡量不因這次暖化本身而變差，實際數字的變動全部來自**背景**本身變了，不是文字调色
造成的：

| Token | 舊值（v2，冷灰） | 新值（v3，暖灰） | 對應 Element Plus 變數 |
|---|---|---|---|
| `--admin-text-primary` | `#E8EAED` | **`#EBE9E8`** | 覆寫 `--el-text-color-primary` |
| `--admin-text-secondary` | `#ABB2BF` | **`#B7B0AC`** | 覆寫 `--el-text-color-regular` |
| `--admin-text-tertiary` | `#9299A8` | **`#A39B95`** | 覆寫 `--el-text-color-secondary`／`--el-text-color-placeholder` |
| `--admin-text-disabled` | `#565C66` | **`#625A55`** | 覆寫 `--el-text-color-disabled`（豁免，不需過 AA） |

⚠️ **`tertiary` 沒有直接套「等相對亮度」算出來的值**：等亮度換算後 `tertiary` 對 `overlay`（四層最亮，
最嚴苛）只有 4.58:1，餘裕只有 0.08——比 v2 的 4.76（餘裕 0.26）更薄，直接沿用 `E-31` 抓到的教訓（不可以
「剛好過」就收工，要留捨入餘裕）。因此 `tertiary` 額外**以 `overlay` 為門檻反推**，固定抓 4.75 的目標值
往回解出 `L`，得到 `#A39B95`（比純等亮度版本 `#A09892` 再亮一點點），换回同樣約 0.25 的安全餘裕。

**完整笛卡兒積（每一階文字 × 每一層背景，五層全跑，以 WCAG 2.x 相對亮度公式實算）**：

| 文字 \\ 背景 | `canvas` `#150F0D` | `surface` `#231916` | `surface-2` `#31231F` | `overlay` `#3F2D28` | `input` `#070504` |
|---|---|---|---|---|---|
| `primary` `#EBE9E8` | 15.69 ✅ | 14.20 ✅ | 12.48 ✅ | 10.73 ✅ | 16.81 ✅ |
| `secondary` `#B7B0AC` | 8.88 ✅ | 8.03 ✅ | 7.06 ✅ | 6.07 ✅ | 9.51 ✅ |
| `tertiary` `#A39B95` | 6.94 ✅ | 6.28 ✅ | 5.52 ✅ | **4.75 ✅**（門檻反推，見上） | 7.44 ✅ |
| `disabled` `#625A55`（豁免） | 2.81 | 2.55 | 2.24 | 1.92 | 3.02 |

**27 組（不含 `disabled`）全數過 AA 4.5:1，最緊的一組是 `tertiary` on `overlay` 4.75:1，餘裕 0.25**，
與 v2 抓的安全邊界一致，不是踩線過關。

刻意不用純白 `#FFFFFF` 當主文字——深色底上的純白文字對比度過高（接近 17:1），長時間閱讀容易產生輕微的
「暈光」視覺疲勞感（這也是幾乎所有主流深色介面都用近白色而不是純白的原因），`#EBE9E8` 仍遠遠超過 AA
門檻，同時閱讀更舒適，這條 v2 的理由在暖化後依然成立。

### 7.4 邊框（v3：暖化，同色相家族）

| Token | 舊值（v2） | 新值（v3） | 用途 | 是否需要 3:1（UI 元件邊界） |
|---|---|---|---|---|
| `--admin-border` | `#333840` | **`#3C3733`** | 卡片、分隔線等純裝飾性邊界 | 不需要（不是唯一的邊界辨識手段，旁邊還有背景色階差異） |
| `--admin-border-input` | `#6B7280` | **`#8A7E75`** | 輸入框、下拉選單等表單元件的邊框 | **需要，五層全驗**：`canvas` **4.81 ✅**／`surface` **4.35 ✅**／`surface-2` **3.83 ✅**／`overlay` **3.29 ✅**／`input` **5.15 ✅**（最低 3.29，餘裕 0.29） |

`--admin-border` 的暖化做法與 §7.3 文字一致：**沿用舊值的相對亮度 Y，只把色相換成與背景同家族的
`H=25°`**，讓對比度的變動全部歸因於背景改變而非調色本身。

`--admin-border-input` **沒有沿用舊值的亮度**——它比等亮度的暖化值（`#7A6F68`）更亮，理由見下方修正記錄。
色相與飽和度仍是同一家族（`H=25°`／`S=8%`，比純中性的邊框多一點點彩度，讓它在暖底上仍讀得出「這是一條線」
而不是被暖底吃掉），只把明度推到 `L=50%`。

> 🔴 **修正記錄（2026-09-22，交付當日獨立複驗抓到）**：本節初稿寫的是 `#7A6F68`，並宣稱「邊框對 3:1 全過
> （最低 3.52）」。**那個 3.52 是對 `surface` 算的，沒有對五層背景全算。**實際跑完笛卡兒積，`#7A6F68` 對最亮的
> `overlay`（`#3F2D28`）只有 **2.66:1，過不了 WCAG 1.4.11 的 3:1**。
>
> **這不是理論上的組合**：`--admin-bg-input`（`#070504`）對 `overlay` 只有 **1.57:1**，所以在 `el-dialog`、
> `el-select` 這類以 `overlay` 為底的容器裡，**邊框是「這裡是一個可以打字的欄位」的唯一辨識線索**——欄位自己的
> 底色與容器底色幾乎分不出來。邊框一失效，欄位邊界就消失。
>
> ⚠️ **這與 [`18-work-errors.md`](18-work-errors.md) `E-31` 是同一個根因**（驗算範圍由產出者自己挑，沒進清單的
> 組合不會被發現），而且**漏的是同一層**（`overlay`）。E-31 那次漏的是 `--admin-text-tertiary × overlay`，
> 隔一輪換成 `--admin-border-input × overlay`。依 `CLAUDE.md` 第 13 條「同一類錯犯第二次不要再加一筆，
> 回頭把那筆升級成防呆」，處理方式**不是**在 `docs/18` 新增一筆，而是把 `E-31` 的防呆升級——
> 見 §15.2 對 `check-contrast.mjs` 的新要求。

### 7.5 操作主色（primary）（v3：由 Element Plus 預設藍改為品牌桃紅系）

🔴 **v3 核心變更**：`--admin-primary` 系不再是任何一種藍，改用 [`14-invariants.md`](14-invariants.md) 已
固化的品牌桃紅四階 `--brand`／`--brand-aa`／`--brand-bright`／`--brand-deep`（唯一來源
`reference/TCR_logo_CMYK.ai`）。**這四階不是為了 admin 新造的色，是既有品牌色票**——但深色底下哪一階
配哪個角色，跟白底完全不是同一套規則（見 §5.2），且與 v2 一樣，同一個色相無法同時滿足「文字要夠亮」與
「實心按鈕白字要夠暗的底」，所以延續 v2 的兩層拆分邏輯：

| Token | 值 | 用途 | 對比度 | 說明 |
|---|---|---|---|---|
| `--admin-primary` | **`--brand-bright` `#E85BA9`** | 文字、連結、icon、側欄選中態 accent bar、focus 外框 | against `surface` **5.32:1 ✅ AA**（完整五層見 §7.3 上方的 §7.7 用法限定） | 四階裡最亮，供文字用途 |
| `--admin-primary-fill` | **`--brand-aa` `#D61E83`** | 實心主要按鈕（`el-button--primary`）預設底，白字 | 白字 **4.80:1 ✅ AA** | `tcrfc.css` 原始註解就寫明這階是「白底小字，或承載白色小字的實心底」，語意直接吻合 |

**4.42:1**（過不了小字 AA，這也是 `tcrfc.css` 當初要另外定義 `--brand-aa` 的原因）；白字對 `--brand-bright`
`#E85BA9` 只有 **3.23:1**（更不夠）。四個既有品牌階裡，**只有 `--brand-aa` 與 `--brand-deep` 兩階能撐住
白字 AA**，這是 3 個按鈕互動態需要 3 個深淺點、但只有 2 個既有階可用的直接原因，所以 `active` 用了一個
明確標示為「衍生」的第 5 個值，不是隨意加色。

**primary 使用範圍的限定（誠實列出限制，不是全五層通用）**：`--admin-primary`（`#E85BA9`）對 `canvas`

AA**。規格上實際會用到 `--admin-primary` 當文字色的位置（頁面列連結、側欄 accent bar、表單 focus 外框）

對話框／下拉選單內用品牌色文字，必須另外驗證，不得逕自沿用這個 token。

已完整列於 §4.2、§4.3，這裡不重複，只重申一次來源：這組色票**是為深色底重新設計的，不是把 Element Plus
淺色預設值（`#F56C6C`／`#E6A23C`／`#67C23A`）原封不動搬過來**（見 §13 落差記錄）；v3 對危險色又做了一次

### 7.7 品牌色在深色後台的位置（v3 全面改寫，v2 的結論已被拍板推翻）

**v2 的結論是**：「後台不需要行銷識別，品牌色只做小範圍裝飾（站台切換器隊徽、登入頁角落），操作主色維持
中性」。**這條結論已被 2026-09-22 的拍板推翻**——操作主色本身現在就是品牌桃紅，不再是「小範圍裝飾」，
而是貫穿整個後台的操作語言（§7.5）。

**v2 那條理由現在還剩多少有效性？**——分開看，不是整條作廢：

- **「品牌色只做小範圍裝飾」這個具體做法：已經失效**，因為拍板直接要求品牌色成為操作主色，範圍從
  「兩三個角落」擴大成「所有按鈕、連結、focus、選中態」，這是拍板的明確目的，不是本檔可以自行縮小
  範圍的空間。
- **「後台不需要行銷識別」這個判斷背後的擔憂（品牌色大範圍使用可能造成視覺疲勞、對比度維護成本）：
  沒有失效，而是被正面處理掉了**——§7.5 的兩層拆分（文字用亮階、實心底用暗階）、§7.3 的暖灰文字階、
  §4.3 的危險色橘紅化，都是在「品牌色確實大範圍使用」的前提下逐一解決疲勞與對比度問題，不是假裝問題
  不存在。換句話說，v2 用「不大範圍使用」來迴避這些風險，v3 用「大範圍使用但逐一驗算」來正面處理，
  兩種路線都能得到可用的結果，這次拍板選了後者。
- **v2 沒有處理過、v3 才第一次出現的新問題**：操作主色帶磐石識別，對藍鯨維運人員的品牌歸屬感影響——
  這題 v2 從未回答過（因為 v2 主色是中性的，根本沒有這個問題），v3 的正面回答見 §5.1.1，結論是「疑慮
  成立但不夠格推翻拍板」，並提出緩解措施（隊徽圖示改真實圖像，見 §5.3）。

**v3 的品牌色使用範圍**：不再是「小範圍裝飾」，而是**操作主色本身**（§7.5 的四個 token）＋ 原本就有的
裝飾性位置（站台切換器隊徽——v3 起改用真實隊徽圖像而非色塊，見 §5.3；登入頁角落，做法不變）。

🔴 **v3 對「怎麼接品牌色」的正確做法（推翻 v2 的做法，但不是推翻成「隨便接」）**：v2 寫的是「不要把
`tcrfc.css` 的 `--brand` 變數直接接進 `--el-color-primary`」，這條在 v3 拍板「配色改品牌色」之後**字面上
確實過時了**，但拍板要的是「用品牌配色」，**不等於「把 `--brand` 這個特定 token 原封不動接進
`--el-color-primary`」**——`--brand` 正色本身對白字只有 4.42:1（§7.5 已算過），直接接會讓實心按鈕的白字
過不了 AA。**正確的接法**：

1. **`admin-theme.css` 不 `@import` 或引用 `tcrfc.css`**（兩個是不同的 Vue 專案，沒有共用 CSS 建置管線），
   而是把 `--brand-aa`／`--brand-bright`／`--brand-deep` 這三個**已經是 AA 安全版的既有品牌色**的十六進位
   值**逐字複製**進 `admin-theme.css`，並在註解標明「數值抄自 `site/src/assets/css/tcrfc.css`
   `--brand-*`，唯一來源仍是 `reference/TCR_logo_CMYK.ai`」——這與現行 `admin-theme.css` 檔頭「色值一律
   逐字抄自 `docs/21-admin-ui.md`」的既有紀律是同一套做法，只是這次文件裡的色票本身也是抄品牌色來的。
2. **`--el-color-primary` 接的是 `--admin-primary`（＝ `--brand-bright`），不是原始 `--brand`**——
   透過 §7.5 已經定義好的「文字用亮階、實心底用暗階」兩層拆分，`--el-color-primary` 只承擔 Element Plus
   內部用它做**非文字圖形**（如 checkbox／radio／switch 的選中色塊，這類是圖形不是文字，只需 3:1，
   `--brand-bright` 對白色勾勾圖示的對比度雖只有 3.23:1，但這是圖形門檻不是文字門檻，過關）的部分；
   **真正承載文字的按鈕標籤，一律走 `.el-button--primary` 的顯式覆寫（`--admin-primary-fill` 系）**，
   不依賴 `--el-color-primary` 本身——這個「文字用途另外覆寫，不依賴主變數」的架構本來就是現行
   `admin-theme.css` 已經在做的事（見第二階段檔案清單），v3 只是換值，不用改架構。
3. **危險／警告／成功三色與品牌桃紅是完全獨立的 token**（`--admin-danger-*`／`--admin-warning-*`／
   `--admin-success-*`），不透過 `--el-color-primary` 衍生，這條 v2 就是這樣做，v3 不變。

## 9. 圖片上傳元件

畫面元素、逐項規則（選檔即時預覽、解析度/檔案過大的錯誤文案、儲存中狀態、儲存失敗的處理、換圖/移除、
多圖排序、列表頁縮圖放大）**全部沿用 v1**，這些是功能行為層面的規則，與整體深色化無關。**這次新增的是
回應任務提出的疑慮**：深色底會不會影響編輯者對照片色調與去背邊緣的判斷。

### 9.1 中性看片台：圖片預覽框有自己固定的底色，不隨頁面主題變化

**決定**：所有圖片預覽區塊（上傳框選圖後的預覽、列表頁縮圖、編輯頁封面圖預覽、多圖排序的 `picture-card`）
底下鋪一塊**固定的中性參考面**，這塊參考面的顏色**不使用 §7 定義的任何背景色階**，是獨立於整體深色/淺色
主題之外的專用色，理由：

1. **這是色彩管理領域的標準做法，不是本檔發明的**：任何專業修圖／去背工具（Lightroom、Photoshop）都不會
   用應用程式介面本身的底色當作照片判色的參考面，而是在畫布外鋪一塊固定的中性灰，讓使用者不管當下用的是
   哪一套介面主題，看到的顏色參照基準永遠一致。
2. **這個解法直接回應 §7.0 提到的「深色是否影響照片判斷」疑慮，而且比切回淺色主題更有效**——一般網頁的
   純白底同樣不是中性參考面（純白會讓亮部看起來偏暗、偏冷），所以「做淺色模式」並不能真正解決這個疑慮，
   只有「圖片預覽框本身用中性色」才能解決，這也是 §7.0 判定「不需要為了這個理由做雙主題」的根據——而該判定已於 2026-09-21 由使用者拍板採納，所以**這塊中性看片台是深色唯一主題下處理判色問題的唯一手段**，不是備案。
3. **去背邊緣的判斷用棋盤格而不是純灰**：含透明通道的圖片（隊徽、去背後的贊助商標誌）如果背後只是純色
   平面，編輯者看不出透明區域跟「顏色剛好跟底色很像的不透明區域」的差別；棋盤格圖案（淺灰／深灰方格交錯）
   是業界標準的透明度可視化做法，讓透明邊緣清楚可辨。

具體分兩種底：

| 圖片類型 | 看片台底 | 說明 |
|---|---|---|
| 一般照片（封面圖、球員照、活動照片，預期不透明） | 中性灰 `#4A4D52`（固定值，不隨主題變化） | 中明度灰，避免像極暗或極亮的底色造成的同時對比錯覺 |
| 可能含透明通道的圖片（隊徽、去背標誌類） | 棋盤格（`#4A4D52` 與 `#5C5F65` 交錯，8px 方格） | 透明區域會透出棋盤格，不透明區域蓋住棋盤格，邊緣一目了然 |

這塊看片台色**與 §7 的四層背景色階脫鉤**，不隨 `html.dark`／未來若做淺色模式切換而改變，因為它存在的
目的就是提供一個恆定的判色基準。

🔴 **v3（2026-09-22）明文重申：中性看片台的兩個值（`#4A4D52`／`#5C5F65`）這次配色改版完全不動，也不得
跟著暖化。** §7.2／§7.3 這次把四層背景與文字全部從中性冷灰改成品牌黑推導的暖灰，**但看片台是判色的參考
面，正因為它「與主題脫鉤」才有意義**——如果看片台也跟著暖化，等於是把「介面主題色」重新混進「照片判色
基準」，正是 §9.1 一開始就要避免的事（見上面第 1、2 點理由）。**中性看片台必須維持嚴格意義上的中性灰，
不得沾染 `--ink` 的暖色相，這條規則本次沒有例外。**

### 9.2 一個刻意的用字取捨（沿用 v1）

規劃書規定畫面上不出現 `WebP`，但後端實際接受的格式清單包含 WebP；本檔的處理方式仍是「上傳提示文案完全
不列格式白名單細節」，`accept` 屬性仍可在背後接受 WebP。**這是代為做的文案判斷，列入 §12 待確認事項**。

## 10. 空狀態、載入中、錯誤狀態

v1 把空狀態與載入中放在 §2（列表頁）裡順帶一提，缺少統一規則，也完全沒有處理過「查詢失敗」這種錯誤狀態。
**這次獨立成一節、三種情境放在一起講，因為三者是同一組元件家族（都是「表格區域暫時沒有正常資料可顯示」）
共用的視覺骨架，只是觸發原因與文案不同。**

### 10.1 三種情境的共用骨架

```
┌────────────────────────────────────────────┐
│                                              │
│              （線稿圖示，見下表）              │
│              （主要說明文字）                  │
│              （可選：次要說明文字）             │
│              （可選：行動按鈕）                │
│                                              │
└────────────────────────────────────────────┘
```

圖示用 `--admin-text-tertiary`（v3 起＝ `#A39B95`，對 `surface` 6.28:1，仍過 AA，但這裡是裝飾性圖示不強制
要求），主要說明文字用 `--admin-text-secondary`（v3 起＝ `#B7B0AC`，對 `surface` 8.03:1），置於 `surface`
卡片內、`canvas` 底不直接鋪這個區塊。

| 情境 | 觸發時機 | 圖示 | 主要文字 | 次要文字 | 行動按鈕 |
|---|---|---|---|---|---|
| **空狀態（本來就沒有資料）** | 模組資料表目前一筆都沒有 | 線稿文件圖示 | 「目前還沒有任何{模組名稱}」 | — | 「+ 新增第一篇{資料單位}」（primary） |
| **空狀態（篩選查無結果）** | 有資料，但目前篩選/搜尋條件下沒有符合的 | 線稿放大鏡圖示 | 「找不到符合條件的資料」 | — | 「清除篩選條件」（一般按鈕，非 primary——因為這不是主要任務，只是排除當前篩選） |
| **載入中（首次進入，無快取資料）** | 列表頁第一次掛載、還沒有任何資料可先顯示 | `el-skeleton` 骨架卡片（比對表格列高與欄位排版產生的假輪廓） | — | — | — |
| **載入中（篩選／翻頁重新查詢，畫面上已有舊資料）** | 使用者已經看到上一輪查詢結果，正在等新一輪結果 | 沿用 v1：`el-table` 的 `v-loading`半透明遮罩＋轉圈，篩選列與工具列維持可視 | — | — | — |
| **錯誤（查詢失敗，如網路中斷、伺服器錯誤）** | API 回傳非預期錯誤（非「查無資料」，是「查詢這件事本身失敗了」） | 線稿警示三角圖示，顏色用 `--admin-text-tertiary`（**不用 danger 紅色**，見下） | 「資料載入失敗，請稍後再試」 | 若有錯誤代碼，附一行技術細節（`--admin-text-tertiary`，供回報問題時使用） | 「重新載入」（primary） |

### 10.2 為什麼首次載入與重新查詢用兩種不同的載入態（v1 沒區分過）

v1 只寫了一種「表格 `v-loading` 遮罩」的做法，理由是「篩選列與工具列維持可視，讓使用者知道操作被系統
收到了」——這條理由**只在畫面上已經有東西可以維持可視的前提下成立**。首次進入一個列表頁時，表格本來就
是空的，遮罩一塊空白區域轉圈，使用者看不到任何「這個頁面長什麼樣子」的線索，此時改用 `el-skeleton`
（依 §2.3 定義的行高與欄位排版生成骨架卡片）能讓使用者提前看到大致版面結構，减少「這頁是不是壞了」的
疑慮，也讓資料到位時的畫面跳動更小（骨架的高度與真實列一致）。這是本次新增的區分，不是重新設計骨架本身，
只是把「已經有資料在畫面上」與「畫面上什麼都沒有」這兩種載入情境的處理方式分開講清楚。

### 10.3 錯誤狀態為什麼不用 danger 紅色圖示

「查詢失敗」是系統性問題（網路、伺服器），不是使用者操作造成的後果，也不需要使用者做任何危險判斷
（不像刪除確認框那種「這個操作有後果」的警示）。用中性的 `--admin-text-tertiary` 而非 `--admin-danger`
色的警示三角，避免使用者誤以為「是我做錯了什麼」而慌張——這與 §4.3「危險色只用在需要使用者警覺後果的
操作」這條原則是一致的邏輯延伸。

### 10.4 儀表板等非列表頁的局部錯誤

儀表板（§11 建議第二階段做的四塊之一）的每個小工具（待辦提醒、流量概況……）各自獨立向後端取資料，
其中一塊失敗不該讓整個儀表板掛掉。局部錯誤沿用同一套骨架但縮小尺寸，塞進該小工具原本的卡片範圍內，
文案改為「這塊資料暫時載入不了」＋「重試」文字按鈕，不佔用整頁高度。

## 13. 與既有文件的落差／矛盾記錄

> 本節記錄**這次改版推翻了什麼、原本的理由為什麼失效**——不是把 v1 的決定悄悄刪掉當沒發生過。

### 13.1 配色：從「不碰 Element Plus 主色系統」全面改為「接官方深色模式並重新配色」

**v1 決定**：`--el-color-primary` 沿用 Element Plus 預設藍 `#409EFF`；`--el-color-danger`／`warning`／
`success` **維持 Element Plus 預設**（`#F56C6C`／`#E6A23C`／`#67C23A`）不因品牌一致性更動；品牌色只用在
站台切換器隊徽小圖示與登入頁角落。

**這次推翻的部分**：四態語意色的**具體數值**全部重新設計（§4.2、§4.3），不再是「維持 Element Plus 預設」。

**原本的理由為什麼失效**：v1「維持 Element Plus 預設不動」的理由是「紅黃綠是使用者已建立的通用心智模型，
不因品牌一致性而改動」——**這條理由本身沒有失效，這次也沒有改變紅＝危險、黃＝警告、綠＝成功的語意對映**，
但 v1 的前提是「Element Plus 預設值是設計給淺色底用的」，直接原封不動搬進深色底，白色系的淺色 tag 底
（Element Plus 淺色危險 tag 是接近白色的淺紅底配深紅字）放進深色頁面會變成突兀的高亮色塊，破壞整頁深色
調性，也不會有人特地為淺色設計的色票去驗證深色底下的對比度。**所以推翻的不是「紅黃綠語意」，是「數值
可以原封不動照搬」這個假設**——配色前提從白底換成黑底，數值本來就要重新算一次，這不是這次特有的新理由，
是配色的物理事實（同一組色相在不同底色上的可讀性天差地遠）。

**沒有推翻的部分**：品牌色只用在小範圍裝飾性位置（站台切換器隊徽、登入頁角落）這條原則**不變**，
只是深色底下要用哪個衍生色階（`--brand-bright` 而非 `--brand-aa`）重新算過，詳見 §5.2、§7.7。
「不用品牌色當 Element Plus 主色」的理由（後台不需要行銷識別、避免視覺疲勞、對比度持續維護成本）**在
深色底下依然全部成立**，甚至更成立（深色底上一大片高飽和品牌色的視覺疲勞問題只會更明顯不會更輕）。

### 13.2 陰影：從「1px 邊框 + 極淺陰影」改為「四層背景色階，不靠陰影」

**v1 決定**：卡片用 `1px` 邊框 + 極淺陰影區分層次，理由是「維持全站『平面、無材質』的調性一致」。

**這次推翻**：陰影不再是層次感的主要手段，改用 §7.2 的四層背景色階（tonal elevation）。

**原本的理由為什麼失效**：v1「平面、無材質」這個調性判斷本身沒有錯、也沒有被推翻——新設計仍然沒有漸層、
沒有玻璃感材質。失效的是「陰影在深色底下仍然能有效分層」這個**隱含假設**：v1 寫這條規則時預設的是淺色
底，淺色底上的深色陰影對比度足夠、人眼容易感知邊界；深色底上陰影本身也是深色（通常是黑色半透明），
疊在已經很暗的背景上，邊界幾乎無法辨識——這是 Material Design 深色主題規範明文指出、業界公認的深色 UI
設計限制，不是本專案特有的巧合。**配色前提換了，原本依賴淺色底才成立的手段自然要換掉**，詳見 §3.1。

### 13.3 站台切換器不整個換品牌色：重新論證後結論不變，但論證過程是新的

**v1 決定**：切換站台只換頂欄的隊徽圖示與名稱文字，不整個換品牌色。

**這次沒有推翻，但補了一段新論證**：任務明確要求檢驗「深色主題本身就是一次全站換色」與這條決定是否
矛盾——v1 寫下這條規則時完全沒討論過整站主題色（深/淺）這個維度，因為 v1 本身就是淺色主題，沒有「切換
主題」這件事可以拿來類比。這次深色化之後才第一次出現「原來後台真的可以整個變色」的先例，所以有必要重新
檢驗 v1 的論證在這個新事實下站不站得住——**結論是站得住**（詳見 §5.1：深色主題是系統層級、與俱樂部操作
範圍無關的設定；若切換站台換品牌色則是與俱樂部強相關、隨操作變動的效果，兩者性質不同），但這是**這次
新增的論證**，不是 v1 就有、直接沿用的舊理由，記在這裡避免下一位讀者以為這個問題 v1 就回答過。

### 13.4 已停用 tag 的具體樣式：從「比預設 danger 淺一階」改為「暗酒紅，深色底重新設計」

**v1 決定**：已停用用自訂樣式，淺紅底、紅字，「比 Element Plus 預設 `danger` 淺一階，避免跟操作型危險
按鈕搶視覺權重」。

**這次推翻**：改為 `#33202B` 底配 `#C98BA8` 字（暗酒紅系），不是「預設 danger 的淺一階」。

**原本的理由為什麼失效**：「已停用要跟操作型危險色區隔開」這個**語意判斷沒有變、也是這次延續的**（見
§4.2）。失效的是「淺一階」這個**具體手法**——v1 的「淺一階」是相對於淺色主題的 Element Plus danger
色（一種偏白的淺紅）往更淺的方向再調；深色主題下沒有「更淺」這個方向可調（背景本身已經是暗色），這次
改成調整色相本身（往酒紅、偏紫紅的方向），用色相區隔而不是用明度區隔，效果上同樣達到「跟操作型危險紅
分得開」的目的，但操作手法因為底色反轉而不能照搬。

### 13.5 模組數量「15」對不上實際「14」

見 §0，v1 已記錄，本次未變，不影響設計方向，純粹是數字核對，這裡不重複。

### 13.6 規劃書 §4.0 沒有明確講「站台切換器要不要整個換品牌色」／「要不要做深色」

這兩件事都是本次任務要求本檔回答的開放問題，不是矛盾——規劃書本來就不記視覺與版面的執行層決定
（前提已在檔頭寫明），這類問題交由本檔依既有原則推導或由使用者拍板，都是正常分工,不是文件之間打架。

### 13.8 v2 初稿的兩個對比度數字算錯（產出當日複驗抓到，已修正）

本檔 v2 的色票宣稱「全部用 WCAG 相對亮度公式實測」。產出後**逐組重跑驗算，27 組裡 25 組精確吻合，
2 組對不上**，兩筆都已在同一次交付內修掉：

| 位置 | 原本寫 | 實算 | 處理 |
|---|---|---|---|
| §4.3 警告按鈕「白字套 `#FFB84D`」的反例數字 | `4.06:1` | **`1.72:1`** | 改成 `1.72`。**結論不變**（白字本來就過不了 AA，深字 `10.54:1` 的決定是對的），錯的只是用來佐證的數字——但它錯了 2.4 倍，留著會讓後面的人以為「差一點就能過」而想去救白字方案 |
| §7.3 `--admin-text-tertiary` 對 `surface` | `4.88:1` | **`5.29:1`**（原色 `#8B92A0`） | 見下 |

**第二筆牽出一個真正的缺陷，不只是打錯字**：`--admin-text-tertiary` 同時覆寫
`--el-text-color-placeholder`，而 placeholder 會出現在**下拉選單的搜尋框、對話框與抽屜裡的表單欄位**
——這些容器的底色是四層裡最亮的 `overlay` `#2A2E36`。原色 `#8B92A0` 對 `overlay` 只有 **4.35:1，過不了
AA**，而 v2 初稿的色票表只驗了 `surface` 與 `surface-2` 兩層，**漏驗了最嚴苛的那一層**。

**修正**：`--admin-text-tertiary` 由 `#8B92A0` 改為 **`#9299A8`**（原色等比提亮 5%，色相不變），四層背景
全部過 AA：`canvas` 6.33／`surface` 5.78／`surface-2` 5.17／`overlay` **4.76**。不取剛好跨過門檻的
`#8E95A3`（`overlay` 4.52）是為了留捨入餘裕；也不再提亮，是為了與 `--admin-text-secondary` `#ABB2BF`
維持 1.97 的對比度差距，階層才分得出來。

**給後續的規則（這條比上面兩個數字重要）**：**每一階文字色都要對四層背景裡最亮的那一層驗過 AA，不是只驗
它「主要會出現」的那一層**。深色主題的陷阱正在這裡——淺色主題的容器越疊越暗、文字對比只會變好，深色主題
相反，容器越疊越亮、文字對比只會變差，所以最上層的 `overlay` 才是深色系統裡真正的門檻。

### 13.9 v3：四層背景色階從「與品牌無關的中性冷灰」改為「品牌黑推導」

**v2 決定**：四層背景（`canvas`／`surface`／`surface-2`／`overlay`／`input`）是純中性冷灰（色相約
215°–220°），與品牌色完全脫鉤，理由沒有明文寫過「為什麼要脫鉤」，只是延續「操作介面不需要品牌識別」
這條 v2 的整體立場（見 13.1、13.10）的自然結果。

**這次推翻**：改由品牌黑 `--ink`／`--ink-2` 推導，見 §7.2。

**原本的理由為什麼失效**：「操作介面不需要品牌識別」這條 v2 的整體立場**被拍板明確推翻**（見 13.10），
背景色階脫鉤只是這條立場眾多推論裡的一個，立場本身被推翻，這個推論自然也站不住，不是背景色階本身有
什麼獨立的問題。**技術上這次推導沒有增加風險**：品牌黑本身的明度分佈（`--ink` L=11.18%、`--ink-2`
L=15.69%）剛好落在深色 UI 需要的背景亮度區間，不需要為了塞進品牌色而扭曲整條色階的明度關係。

### 13.10 v3：「後台不需要行銷識別，品牌色只做小範圍裝飾」的結論被拍板推翻

**v2 決定**：品牌色只用在站台切換器隊徽、登入頁角落，操作主色維持中性（Element Plus 藍），理由是
「後台不需要行銷識別、避免大範圍品牌色造成視覺疲勞、對比度持續維護成本」。

**這次推翻**：操作主色改為品牌桃紅系，品牌色從「小範圍裝飾」升格為「貫穿全後台的操作語言」。

**原本的理由為什麼失效**：**沒有失效，是被使用者拍板直接覆蓋，且覆蓋的是判斷取捨，不是發現這條理由
本身有錯**。v2 提出的三個風險（視覺疲勞、對比度維護成本、行銷識別的必要性）**在 v3 底下依然是真實存在
的風險**，v3 沒有讓這些風險消失，而是選擇正面處理它們（§7.5 的兩層拆分因應對比度風險、§4.3 的橘紅化
因應辨識度風險），詳細說明見 §7.7。**這是本檔目前唯一一次「推翻的原因不是理由失效，而是使用者拍板直接
選擇承擔已知風險」**，記錄下來是為了讓下一位讀者知道：如果日後要評估「這個決定還要不要繼續」，該問的
不是「理由還成立嗎」（成立），而是「這些已知風險目前有沒有真的發生」（例如視覺疲勞的實際回饋、藍鯨
品牌歸屬感的實際回饋，見 13.11）。

### 13.11 v3：站台切換器隊徽從「純色色塊」改為「真實隊徽圖像」

**v2／v1 決定**：站台切換器的隊徽小圖示用 `--brand` 正色的純色圓點色塊。

**這次推翻**：改用兩隊各自的真實隊徽圖像（見 §5.3）。

**原本的理由為什麼失效**：v1／v2 定純色色塊時，操作主色是中性藍，色塊本身的桃紅／隊徽藍在畫面上是
**唯一的彩色元素**，辨識度不是問題。v3 操作主色本身也是桃紅系之後，**純色色塊會被同色系的按鈕、連結、
focus 外框稀釋掉「這是俱樂部標記」的獨立性**——這不是 v1／v2 的假設錯了，是配色前提換了，原本成立的
「色塊本身就夠顯眼」這件事不再成立，改用圖像找回辨識度。詳細論證見 §5.1.1、§5.3。

### 13.12 v3：危險色從「純紅（H≈0°）」改為「橘紅（H=14°）」

**v2 決定**：危險色（文字 `#FF9494`、按鈕底 `#B3453F`）色相落在純紅附近（H≈0°–3°）。

**這次調整**：色相統一推到 `H=14°`（橘紅），明度與飽和度不動。

**原本的理由為什麼沒有失效，是加碼**：v2 選純紅的理由（危險色要跟已停用的暗酒紅、跟成功綠、跟警告
琥珀都分得開）**在 v3 底下依然成立，且實測數字顯示 v2 的選色已經有基本的安全距離**（見 §4.3 的 ΔE76
與色相角實測，舊配色與品牌桃紅的色相距離 30.71°、色差 49.31，不算嚴重）。這次調整是因為**主色改成
桃紅之後，危險色與主色同屬「紅色系家族」的疑慮值得先發制人處理**，不是發現 v2 的選色有錯，而是操作
主色換了之後，值得把危險色的安全邊界再拉大一點，屬於**加碼保險**不是**修正錯誤**，這點在 §4.3 已經
明文交代，這裡不重複列數字，只記錄「這是加碼不是修錯」這個定性判斷。

### 13.13 v3：文字／邊框階從「中性冷灰」改為「暖灰」

**v2 決定**：文字階（`#E8EAED`／`#ABB2BF`／`#9299A8`）與裝飾邊框（`#333840`）色相落在約 215°–220°
（偏藍冷灰），與四層背景同一個冷灰家族。

**這次推翻**：色相改為 `H=25°` 的暖灰（§7.3、§7.4），與新背景色階（`H≈13.85°`）同一個暖色家族。

**原本的理由為什麼失效**：v2 的冷灰文字是配冷灰背景設計的，兩者同屬一個色相家族，視覺上協調。v3 背景
換成暖調的品牌黑之後，**如果文字色不動，冷暖色相在同一個畫面裡對撞，文字會顯得偏冷、發灰發髒**——這不是
v2 的選色本身有問題（配冷灰背景，冷灰文字完全正確），是背景的色相前提換了，文字必須跟著換才能維持
「同一個色彩家族」這個沒有明文寫出來、但一直隱含在配色決策裡的一致性要求。**相對亮度（WCAG Y 值）刻意
維持不變**，只換色相與飽和度，讓對比度數字的變動全部歸因於背景改變，不是文字調色本身引入的誤差
（見 §7.3）。

### 14.1 「這裡管理的是」補第三種變體：`app`（只產出到行動 App，網頁前台沒有對應頁面）

這些模組確實有產出，但產出的是行動 App 或「前台只送出、後台才是真正管理的地方」，不是可以開新分頁連過去
的網頁 URL。處理方式：新增第三種畫面行為 `app`——灰字顯示但不做成可點擊連結。程式碼在
`apps/admin/src/types/frontendUnit.ts`／`data/frontendUnits.ts`。

⚠️ 這份對照表逐字取自規劃書 §4.0：實作時發現「B2 → 新聞中心」這個舉例在規劃書裡實際寫的是
「07 新聞與故事（7.1–7.7）、首頁最新消息」，沒有「新聞中心」這個名稱，程式碼的對照表已改回規劃書原文。
本檔第 6 節（含本次改版）的例子文字是示意寫法，不是規劃書逐字規定。

**本次確認**：這條與配色、骨架種類完全無關，§6.3 直接沿用三種行為（`link`／`none`／`app`），無需修改。

### 14.2 側欄結構：14 個一級模組各自是「葉節點」或「手風琴子選單」，不是統一的兩層結構

有子模組代號的一級模組（`B C P E F G J K L M S`，比照 `docs/03-admin-spec.md` §1 的模組樹）渲染成
`el-sub-menu`（手風琴，`unique-opened`）；沒有子模組代號的（`A H I`）直接是可點擊的葉節點，不會有展開

**本次確認**：§1.3 已經把這條規則寫進正式規格（v1 只在這個補充小節提過，這次正式收進 §1.3 本文），
新的選中態視覺（accent bar）對葉節點與子選單項目一視同仁套用，不需要額外分支處理。

### 14.3 手機寬度下「這裡管理的是」文字要允許換行，不能整段強制單行

第一版用了 `white-space: nowrap`（因為桌面寬度下這一列理應在標題同一行、不換行），結果在 375px 寬度、
文字較長的情境超出螢幕寬度被裁切看不到後半段。已改為手機寬度下允許正常斷行。

**本次確認**：§6.2 已經從結構上解決這個問題——「這裡管理的是」不再與標題共用同一行，本來就是頁面列
獨立的第二行，任何寬度下都不需要跟標題搶版位，也就不需要再靠「桌面 nowrap、手機拔掉 nowrap」這種依
斷點切換的補丁規則。**這條 v1 的踩雷紀錄本身仍然值得留著**，讓下一位讀者理解「為什麼 §6 要這樣設計」
的背景，但實作面不再需要重複 v1 那個補丁做法。
