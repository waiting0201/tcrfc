## 0. 模組總數的一個落差（先說在前面）

派工說明寫「15 個模組」，但實際盤點 [`03-admin-spec.md`](03-admin-spec.md) 與規劃書 §4.0 的後台架構總覽，
本後台的一級模組是 **14 個**：`A B C P E F G H I J K L M S`。`N`（慈善捐款平台）雖然出現在同一份模組樹的
註記裡，但規劃書明文「**慈善捐款平台是獨立後台與獨立資料庫，不在本後台的模組之列**」，所以不計入本後台的
導覽結構。本檔以 14 個一級模組為準；`S` 是子模組最多的一個，`S1–S6` 共六個，與派工說明一致。這個數字落差
不影響設計方向，僅在此記錄避免下一位工程師對不上數字而懷疑自己算錯。

## 1. 版面骨架：左側欄 + 頂欄的混合結構

### 決定

**左側欄放模組導覽（可收合），頂欄放站台切換器與使用者操作，不做純頂欄式選單。**

### 為什麼

- 14 個一級模組、最深兩層（一級模組 → 子模組，`S` 有 6 個子模組），這個量放進頂欄的橫向選單或
  mega-menu 會過寬且必須換行或水平捲動，在滑鼠操作的桌面管理後台上，垂直清單（側欄）比水平清單更適合
  容納這種深度與數量——這是 Element Plus 官方後台範例（`el-menu` vertical + `el-sub-menu`）的標準用法，
  不需要自訂元件。
- 頂欄需要放**跨模組、全域性**的東西（站台切換器、使用者選單、通知），這些東西的性質跟「導覽到某個模組」
  不同層次，混進側欄選單裡會讓側欄承擔兩種不相干的職責。
- 兩者分工＝側欄回答「我要去哪個模組」，頂欄回答「我現在是誰、在哪個站台操作」。

### 側欄分組（視覺分組，不是重新切模組）

14 個模組攤平列出會讓人來回捲動找模組。以下用 `el-menu-item-group` 的視覺分隔把 14 個模組分成 6 組，
**分組只是導覽上的視覺輔助，模組本身仍依前台單元切分（規劃書 §4.0），沒有因為分組而合併或重新定義模組**：

```
總覽　　　　── 儀表板
內容與網站　── 內容管理／搜尋與 AI 能見度／網站設定／行事曆管理
球隊與活動　── 球隊管理／課程與活動
會員與商店　── 會員管理／商店
商業與社群　── 商業模組／文化模組／表單與詢問
App 與系統　── 行動 App／系統管理
```

分組依據：使用者在同一個工作階段裡通常是「編內容」「顧球隊」「顧會員與訂單」三種心智模式輪替，把常一起用
的模組放近，不是按資料表或技術邊界分（那正是規劃書 §4.0 明文禁止的切法）。

### 側欄寬度與收合行為

| 狀態 | 寬度 | 內容 |
|---|---|---|
| 展開 | `240px` | 圖示 + 完整中文模組名稱；有子模組的項目末端帶展開箭頭 |
| 收合 | `64px` | 只留圖示；hover 該圖示以 flyout（Element Plus `el-menu` collapse 內建行為）浮出該模組的子模組清單 |

- 240px 是實測值：最長的模組名稱「搜尋與 AI 能見度」（6 字）加圖示與內距後仍留白，不會被截斷成省略號。
- 子選單用**手風琴模式**（`unique-opened`）：同時間只展開一組子模組，避免 `S`（6 個子模組）展開後把其他
  13 個一級模組全部往下推出可視範圍。
- 收合鈕固定在側欄最底部，跨頁面保留使用者的收合偏好（存 `localStorage`，純前端便利設定，不必連後端）。

## 2. 列表頁標準型（14 個模組共用一套）

因為要通用給球隊、球員、訂單、會員、新聞……等性質差異很大的資料，標準型只規定**骨架與元件種類**，
每個模組決定要不要用其中某一列（例如「儀表板」無此頁、「系統管理｜稽核」可能沒有批次操作）。

### 骨架（由上到下）

```
┌────────────────────────────────────────────────────────────┐
│ 新聞與故事                        這裡管理的是：新聞中心 ↗    │ ← 頁首＋前台對照（第 6 節）
├────────────────────────────────────────────────────────────┤
│ [搜尋框.......] [分類 ▾] [狀態 ▾] [發布日期區間 📅]  篩選 清除 │ ← 篩選列
├────────────────────────────────────────────────────────────┤
│ 已選取 3 筆   [批次發布][批次下架][匯出][刪除]      + 新增文章 │ ← 工具列（批次操作僅選取後出現）
├────────────────────────────────────────────────────────────┤
│☐│封面 │標題              │分類 │狀態     │發布時間      │操作 │
│☐│[img]│球隊作客特倫欽...  │賽事 │● 已發布 │2026-05-20    │檢視 編輯 複製 更多▾│
│☐│[img]│U15 青訓營開放報名 │課程 │● 排程發布│2026-09-25 08:00│…│
│☐│[img]│(草稿) 週報草稿   │一般 │○ 草稿   │—            │…  │
├────────────────────────────────────────────────────────────┤
│                                     共 128 筆  每頁[20▾]  ‹1 2 3›│
└────────────────────────────────────────────────────────────┘
```

### 各元件規則

| 元件 | 規則與理由 |
|---|---|
| **搜尋框** | 單一自由文字搜尋，比對標題／內文摘要；放篩選列最左，是最高頻操作 |
| **篩選下拉** | 只放**該模組真的有的**維度（分類、狀態、日期區間、俱樂部歸屬——`club_id` 為空的共用內容顯示為篩選選項「共用內容」而不是顯示欄位名） |
| **批次操作** | **平常不出現**，勾選 ≥1 筆才顯示這一列工具列；操作項目依模組而定，但**永遠把「刪除」放最右且用危險色**，避免誤觸 |
| **新增按鈕** | 固定在工具列最右、`type="primary"`，全站位置一致，使用者不用每個模組重新找 |
| **表格圖片欄** | 若該模組有圖片欄位，一律顯示 **160px 方形縮圖**（規劃書 §4.0 圖片上傳通則），無圖時放灰底佔位圖示，**不留空白**（避免每列高度因為有無圖片而跳動） |
| **狀態欄** | 用 `el-tag`，規則見第 4 節，欄位標籤永遠是「狀態」不是「發布狀態」「上架狀態」等技術措辭的直譯 |
| **操作欄** | 常用動作（檢視／編輯）用文字按鈕平鋪；不常用或高風險動作（複製、刪除、下架）收進「更多 ▾」的 `el-dropdown`，理由：操作欄若把 5 個動作都平鋪，行距一亂使用者容易手滑點錯，尤其刪除這種不可逆動作 |
| **權限收斂的按鈕** | 使用者沒有該操作權限時，**按鈕整個不顯示**，不是顯示但 disabled。理由：disabled 按鈕會讓人以為系統壞了去問客服；完全不存在則不會引發疑問（例外見第 5 節「共用內容唯讀」，那種情況要解釋原因，因為使用者原本以為自己有權限） |
| **分頁** | `el-pagination`，固定放右下角，帶「每頁筆數」選擇器（10/20/50/100），預設 20 |

### 空狀態

```
┌────────────────────────────────────────────┐
│                                              │
│              🗎（線稿圖示）                  │
│         目前還沒有任何新聞與故事               │
│         [ + 新增第一篇文章 ]                  │
│                                              │
└────────────────────────────────────────────┘
```
搜尋／篩選後查無結果，用另一組文案：「找不到符合條件的資料，[清除篩選條件]」，避免使用者誤以為模組本身是空的。

### 載入中

表格用 `el-table` 的 `v-loading`（半透明遮罩 + 轉圈），**不用整頁 spinner**——篩選列與工具列維持可視，
讓使用者知道自己剛才的操作被系統收到了，只是資料還在載入，而不是整頁閃白重繪。

## 3. 編輯頁標準型

### 決定：欄位少（≤ 8 個、無雙語長文字）用 `el-dialog`／`el-drawer`；欄位多或含雙語內容用整頁

理由：FAQ 一則、行事曆分類這種輕量資料，開整頁對「插入一則資料」這個動作來說是過度的頁面跳轉；
但新聞、球員、商品這種有雙語內容、圖片、SEO 欄位的資料，塞進 Dialog 會讓 Dialog 高度失控、還要在小視窗裡
切換分頁，不如給一個完整頁面呼吸。**分界點：只要出現雙語長文字欄位（內文、簡介）或圖片上傳，一律用整頁。**

### 整頁編輯的骨架

```
┌──────────────────────────────────────────────────────────────┐
│ ← 返回列表    編輯文章                    這裡管理的是：新聞中心 ↗ │
│               狀態：● 已發布（2026-05-20 09:00 發布）             │
├──────────────────────────────────────────────────────────────┤
│ ┌ 基本資訊 ──────────────────────────────────────────────┐    │
│ │ 分類 *          [賽事 ▾]                                 │    │
│ │ 標題（中文）*    [___________________]                    │    │
│ │ 標題（英文）     [___________________]  尚未翻譯 🏷        │    │
│ │ 網址名稱 *       [tcrfc-vs-trencin____]                   │    │
│ └──────────────────────────────────────────────────────┘    │
│ ┌ 內容 ───────────────────────────────────────────────┐     │
│ │ [中文內容] [英文內容（尚未翻譯）]  ← el-tabs             │     │
│ │ ┌────────────────────────────────────────────┐    │     │
│ │ │           （富文本編輯器）                     │    │     │
│ │ └────────────────────────────────────────────┘    │     │
│ └──────────────────────────────────────────────────────┘     │
│ ┌ 封面圖片 ───────────────────────────────────────────┐      │
│ │ [ 縮圖預覽 / 拖曳上傳框 ]  圖片說明文字（中文）*[___]        │      │
│ │                          圖片說明文字（英文，選填）[___]     │      │
│ └──────────────────────────────────────────────────────┘     │
│ ┌ 發布設定 ───────────────────────────────────────────┐      │
│ │ 不讓搜尋引擎收錄  [開關]     正規網址（選填）[________]      │      │
│ └──────────────────────────────────────────────────────┘     │
├──────────────────────────────────────────────────────────────┤
│                                    [ 預覽 ]  [ 儲存草稿 ] [ 發布 ▾ ]│ ← 固定在內容區底部

```

### 欄位分組（`el-card` 分段，每段一個標題）

固定分段順序：**基本資訊 → 內容（雙語）→ 圖片 → （視模組而定的專屬欄位，如球員的球衣背號、商品的規格）→
發布設定（SEO／排程）**。全站順序一致，使用者換模組時肌肉記憶還能用。

### 必填標示

`el-form-item` 的 `required` 屬性（Element Plus 預設在 label 前加紅色 `*`），**必填規則統一放 label 前方**，
不用「(必填)」文字或顏色標籤等其他寫法混用。

### 雙語欄位（`zh` / `en`，英文可空但欄位必須存在）

**短欄位並排、長欄位用分頁**，兩種都要用，理由分別如下：

| 欄位型態 | 呈現方式 | 為什麼 |
|---|---|---|
| 短欄位（標題、副標、按鈕文字、Alt 文字） | **並排雙欄**（中文在左、英文在右，同一個 `el-form-item` 群組裡兩個等寬 `el-input`） | 短欄位並排時使用者能一眼比對「這句中文跟英文是不是對得起來」，這是校對雙語內容最常見的動作；並排不會佔用太多垂直空間 |
| 長欄位（內文、摘要、SEO 描述、富文本） | **`el-tabs`「中文內容」／「英文內容」切換** | 富文本編輯器並排會讓兩欄各自窄到不能正常編輯；改分頁後每欄都能用滿版面寬度 |

英文分頁標籤上加一個小灰點或「尚未翻譯」`el-tag`（`type="info"`，畫面文字：**「尚未翻譯」**），對應儀表板
本來就要統計的「未翻譯內容數」——編輯頁能一眼看出這篇還缺英文版，不用點進分頁才發現是空的。

### 儲存／發布／預覽的按鈕邏輯

固定在內容區底部（不是整個視窗底部，側欄不受影響），由左到右：

1. **預覽**（次要按鈕）：開新分頁看前台這筆資料的實際頁面。**尚未發布過的資料**，預覽連結需要一組簽章
   預覽網址讓編輯者在正式發布前也能看草稿；**這一段的預覽機制屬於後端功能，本檔不代為決定**，第一階段
   若後端還沒做草稿預覽，此按鈕先以 `disabled` + tooltip「尚未發布，暫不提供預覽」呈現。
2. **儲存草稿**（一般按鈕）：只存值，不改變發布狀態。
3. **發布 ▾**（主要按鈕，`el-dropdown` 分裂按鈕）：主按鈕文字依目前狀態變化——
   草稿狀態顯示「**發布**」；已發布狀態顯示「**儲存變更**」；下拉選單裡永遠有「**排程發布**」選項
   （點開帶出日期時間選擇器）。**用同一顆按鈕承載狀態相依的文字**，比同時擺「儲存」「發布」「排程」
   三顆固定按鈕更不容易讓使用者對著已發布的文章按到「發布」而困惑「這樣算重新發布嗎」。

### 離開未儲存的提醒

路由離開（`onBeforeRouteLeave`）與瀏覽器分頁關閉（`beforeunload`）兩處都要攔，跳出確認對話框，
畫面文字：**「這頁還有未儲存的變更，確定要離開嗎？」**，兩個按鈕「繼續編輯」「捨棄變更並離開」——
「捨棄」而不是「離開」，讓使用者清楚代價是什麼。這條是功能行為要求，實作在第二階段的 Vue 路由層。

## 4. 狀態呈現

### 四態模型（有這個語意的模組才套用全部四態，不是每個模組都有四態）

| 狀態 | 畫面文字 | `el-tag` 樣式 | 使用情境 |
|---|---|---|---|
| 草稿 | **草稿** | `type="info"`（灰） | 尚未對外顯示，內容可能不完整 |
| 排程發布 | **排程發布**（hover 顯示「將於 2026-09-25 08:00 發布」） | `type="warning"`（橘） | 已通過審核、等到時間自動轉為已發布 |
| 已發布 | **已發布** | `type="success"`（綠） | 前台看得到 |
| 已停用 | **已停用** | 自訂樣式：淺紅底、紅字（比 Element Plus 預設 `danger` 淺一階，避免跟「操作型」危險按鈕搶視覺权重） | 曾經發布過、現在主動下架，語意上跟「還沒發布過的草稿」不同，不能共用灰色 tag |

理由：草稿與已停用如果共用同一個灰色 tag，使用者無法從列表一眼分辨「這篇本來就沒發布過」跟「這篇本來
有、現在被下架了」——這在新聞這類需要交代「什麼時候下架的」的場景是重要區別，所以刻意給已停用一個獨立顏色
而不是沿用草稿的灰色。

**不是每個模組都有全部四態**：例如 Banner／贊助方案只有「上架／下架」二態（用「已發布」「已停用」兩個
既有 tag 就夠，不需要草稿與排程）；商店訂單（`S3`）走自己的狀態機（待付款／已付款／備貨中／已出貨／
已完成／退款中……），**不套用本節的四態 tag，但沿用「用 `el-tag` 顏色語意化狀態」這個视觉語言**——
綠色=完成/成功、橘色=進行中/待處理、紅色=異常/退款、灰色=結束但非成功（已取消）。

### 編輯頁的狀態呈現

放在頁首標題正下方（見第 3 節 wireframe），比列表頁多帶一行細節文字：已發布的顯示「於 2026-05-20 09:00
發布」；排程的顯示「將於 2026-09-25 08:00 發布」；已停用的顯示「於 2026-06-01 由王小明 下架」
（如果稽核紀錄有記錄操作者，順手顯示，沒有就只顯示時間）。

## 5. 站台切換器

### 放哪、長怎樣

放在**頂欄左側**（見第 1 節 wireframe），緊接在側欄收合鈕之後。外觀是一個中性樣式的 `el-dropdown`
觸發器：俱樂部隊徽小圖示（16px）＋ 俱樂部中文名稱（「台中磐石」／「台中藍鯨」）＋ 下拉箭頭，
**用一般文字色與邊框，不用品牌色填底**——原因見下方「不整個換色」。

```
[🔴台中磐石 ▾]     ← 頂欄左側，平時樣子（🔴代表小隊徽圖示，非強調色塊）
```

點開下拉，只列出**該帳號已授權且未到期**的俱樂部（規劃書 §4.0，v3.0）：

```
┌──────────────┐
│ ✓ 台中磐石     │
│   台中藍鯨     │
└──────────────┘
```

**只授權一個俱樂部的帳號不顯示下拉箭頭**，改成純文字標籤（不可點擊），理由是規劃書明文
「只授權一個俱樂部者不顯示切換器」——用不可互動的靜態標籤而不是隱藏整塊區域，是為了讓使用者仍然
隨時看得到「我現在在哪個站台底下」，只是少了切換的必要性。

### 切換後：只換一個徽章標記，不整個換品牌色

**決定：後台操作介面本身維持一套中性色（見第 7 節），切換站台只換頂欄的隊徽圖示＋名稱文字，
不把 Element Plus 的主色換成該俱樂部的品牌色（磐石桃紅 / 藍鯨藍）。**

理由（直接對應規劃書那句「⚠️ 切換器是介面便利，不是安全邊界」）：

1. **視覺上的權限暗示風險**：如果切換站台會讓整個後台變成粉紅色或藍色主題，使用者容易產生「顏色 = 我現在
   的權限範圍」的錯覺——但實際的資料範圍限制是在資料存取層（`AdminUserClub`、`club_id` 過濾）強制的，
   跟畫面顏色無關。規劃書特別強調這條界線，設計上就不該做出容易被誤讀成安全機制的效果。
2. **一致的操作介面比討喜的品牌介面更重要**：後台是天天使用的工具，頻繁切色會增加視覺疲勞與誤讀成本
   （尤其磐石桃紅對白只有 4.42:1，大量套用在操作型 UI 上會逼著到處切換 AA 版本，詳見第 7 節）。
3. 仍然需要「看得出現在是哪一站」的**主動提醒**，作法是：
   - 頂欄的隊徽圖示與名稱**永久顯示**（不是切換瞬間才閃一下），這是最低成本、隨時可見的視覺確認。
   - 切換當下跳一個 `el-message`（success 樣式）：**畫面文字「已切換至台中藍鯨的管理畫面」**，並重新載入
     目前模組、以新俱樂部的範圍重新查詢列表。
   - 進入**列表頁與編輯頁**時，若該筆資料屬於「共用內容」（`club_id` 為空）且目前帳號的範圍受限（唯讀），
     用一個顯眼但非警告色的 `el-tag`（`type="info"`，畫面文字：**「共用內容（唯讀）」**）標在標題旁，
     編輯頁的儲存／發布按鈕改為 `disabled` 並加 tooltip：**畫面文字「這是兩隊共用的內容，你的帳號僅能檢視」**。
     這裡**刻意違反**第 2 節「沒權限的按鈕直接不顯示」的通則——因為使用者原本预期自己能編輯（畫面看起來
     跟平常的編輯頁一樣），如果按鈕直接消失，會被誤以為系統故障；唯讀是「看得到但不能動」的特例，需要
     解釋，跟「本來就不該看到這個功能」不同。

## 6. 每個模組頁首的「產出前台哪裡」＋預覽連結

規劃書 §4.0 這條是硬性規定（「對不上的模組就是切錯了」），設計上把它做成**每個列表頁與編輯頁都固定
出現、位置一致**的一小列，不是藏在說明文件或 tooltip 裡才看得到。

### 列表頁（模組層級）

放在頁首標題同一行的右側（見第 2 節 wireframe）：

```
新聞與故事                                    這裡管理的是：新聞中心 ↗
```

- 「這裡管理的是：{前台單元中文名稱}」是固定句式，`{前台單元中文名稱}` 取規劃書「前後台對照表」
  裡對應的前台名稱（例：內容管理 B2 → 「新聞中心」；商店 S1 → 「站內商店的商品頁」）。
- `↗` 是外部連結圖示，點擊在新分頁開啟前台**該單元的首頁或列表頁**（不是單筆資料）。
- **無前台產出的模組**（儀表板、系統管理）不放假連結，改成灰色小字：
  **畫面文字「本頁僅供後台管理使用，沒有對應的前台頁面」**。
- 一個後台模組對應多個前台頁面時（如頁面管理對應一整批靜態頁），文字改為「這裡管理的是：多個靜態頁面」，
  連結改成到前台的網站地圖或該類頁面的入口頁，而不是硬選一個。

### 編輯頁（單筆資料層級）

同樣位置，但連結要指到**這一筆資料**的實際前台網址，而不是模組首頁：

```
編輯文章                                  這裡管理的是：新聞中心 ↗（在新分頁開啟這篇文章）
```

尚未發布的資料沒有正式網址可連，見第 3 節「預覽」按鈕的處理方式（草稿預覽是後端待做功能，第一階段先
`disabled` + tooltip）。

## 7. 配色與 design tokens

### 決定：後台自建一套操作型 tokens，不直接沿用 `tcrfc.css` 的品牌桃紅當 Element Plus 主色

品牌色的唯一來源仍是 `reference/TCR_logo_CMYK.ai`（[`14-invariants.md`](14-invariants.md)），
本節**沒有另外定義新的品牌色**，只決定「後台的操作用色要不要等於品牌色」，答案是不等於，理由：

1. **對比度**：`--brand`（`#E0218A`）對白底只有 4.42:1，只過大字 AA，過不了小字 4.5:1 的門檔。Element Plus
   的操作型元件（表格文字、按鈕、標籤）大量是 14px 以下的小字，若把它設成 `--el-color-primary`，開發時
   會不斷撞到「這個小字要不要換成 `--brand-aa`」的判斷，**是持續性的維護負擔，不是一次性的事**。
   藍鯨的品牌藍更嚴重（對白僅 3.29:1）。品牌色留在它原本設計要出現的地方（行銷型的前台大標題、色塊）
   反而更安全。
2. **後台不需要行銷識別，需要的是操作一致性**：這是天天使用的內部工具，不是對外的品牌接觸點。同業常見
   做法（如多數 SaaS 後台）也是後台配色中性、只在品牌識別點（登入頁、頂欄小標記）點綴品牌色。
3. **呼應第 5 節「切換器不是安全邊界」的決定**：如果後台主色直接套用品牌色，等於又製造一次「換站台=
   換一大片顏色」的暗示，兩節決定要互相一致。

### 具體對應表

| Element Plus token | 值／來源 | 理由 |
|---|---|---|
| `--el-color-primary` | 沿用 Element Plus 預設藍 `#409EFF`（或後續由 `frontend-architect` 微調的一個中性藍灰） | 操作型主色，避開磐石桃紅／藍鯨藍的對比度問題；藍色也是使用者對「可點擊、主要動作」最無歧義的既有心智模型 |
| `--el-color-danger` / `warning` / `success` | **維持 Element Plus 預設**（`#F56C6C` / `#E6A23C` / `#67C23A`） | 紅黃綠是使用者對「危險／警告／成功」已建立的通用心智模型，不因品牌一致性而改動——改了反而增加誤讀（比如把危險色換成偏品牌桃紅，容易被誤認成「強調」而非「危險」） |
| 品牌色出現的位置 | 只用在：頂欄站台切換器的隊徽小圖示、登入頁的俱樂部標誌角落 | 小範圍、裝飾性使用，符合「品牌色的唯一來源」不變量，但不讓它承擔操作語意 |
| 中文字體 | 延續 `tcrfc.css` 的 `"Noto Sans TC", -apple-system, "PingFang TC"` | 後台大量中文標籤，沿用同一套字體堆疊維持系統一致的中文顯示品質；但**不沿用** `Montserrat`（英文行銷字體）與前台的 `clamp()` 流體大字級——那是給行銷頁大標題用的尺度系統，後台字級走 12–14px 的操作介面常規尺度 |
| 圓角 | 表格、卡片維持 Element Plus 預設小圓角（`4px`）；主要按鈕與強調卡片可縮到 `2px` | 前台美學是「硬邊直角、零漸層」（`06-conventions.md` §2），後台若整套改成 0 圓角要覆寫大量 Element Plus 內建樣式，維護成本高且沒有對應的功能收益；用「主要按鈕改極小圓角」做一個弱連結向前台語彙致意即可，不需要照搬 |
| 陰影／材質 | 不用漸層、不用高光玻璃感（呼應前台零漸層調性），卡片用 1px 邊框 + 極淺陰影區分層次 | 維持全站「平面、無材質」的調性一致，這點前後台可以共用不衝突 |

**給 `frontend-architect` 的實作方式**：用 Element Plus 官方的 CSS variable 覆寫（`--el-color-primary` 等）
或 SCSS `@use "element-plus/theme-chalk/src/common/var.scss" with (...)`，**不要**把 `tcrfc.css` 的
`--brand` 變數接進 `--el-color-primary`。

## 8. 響應式：完整響應式後台（使用者拍板）

### 決定

🔴 **後台做完整響應式，14 個模組每一頁都要在手機上可用**（使用者 2026-09-21 拍板）。
不是只做「現場拍照上傳」這類關鍵流程——**寬表格類模組（商店訂單、會員名單、權限矩陣）也要有
手機版的資訊層級設計**，不得只靠橫向捲動交差。

### 為什麼

規劃書沒有明文規定後台要不要支援手機，這是使用者的範圍決定。本檔原先提的是「只做關鍵流程」
（理由是資料密集的管理介面在手機上難維持資訊密度），**使用者選擇了範圍更大的那個**。

> ⚠️ **這個決定的成本不在第二階段，在之後每一個模組。** 手機版寬表格不是把 `el-table` 塞窄，
> 而是要為每個模組各自決定「這張表在手機上要先看到哪 3–4 個欄位、哪些操作要收進次選單」。
> 第二階段只驗證外殼與兩種標準頁型的響應式行為；`S3` 訂單、`K1` 會員名單、`J2` 權限矩陣這類
> 寬表格的手機版資訊層級，要在做到那個模組時逐一設計，**排工作量時要算進去**。

> 🔵 **原本的取捨仍然有效的部分**：手機上的操作重心仍是「新增／編輯單筆資料 ＋ 拍照」。
> 「完整響應式」的意思是**每一頁都可用、不是每一頁都為手機最佳化到同等程度**——
> 重度批次比對操作在手機上可用即可，不需要為它另做一套互動。

### 斷點與行為

| 斷點 | 側欄 | 表格 | 表單 |
|---|---|---|---|
| 桌面 `≥ 1024px` | 常駐，可收合 | `el-table` 正常橫向欄位 | 第 3 節標準型（並排雙語欄位） |
| 手機 `< 768px` | 預設收起，變成 `el-drawer` 遮罩式抽屜，點頂欄 hamburger 開關 | 改用**卡片式列表**：每筆資料一張 `el-card`，只顯示 3–4 個關鍵欄位＋狀態 tag＋操作按鈕（不是把 table 硬擠進小螢幕橫向捲動） | 單欄堆疊（`el-form label-position="top"`）；雙語欄位**一律改用分頁**（並排在手機寬度下擠不下兩個可用的 input） |
| 中間 `768–1024px` | 視同桌面的收合態（強制收合，可展開） | 維持 `el-table`，但隱藏次要欄位（可用 `el-table-column` 的 `v-if` 依斷點藏欄） | 同桌面 |

### 圖片上傳在手機的特別處理

- 上傳按鈕的 `<input type="file">` 加 `accept="image/*" capture`，讓使用者可以直接呼叫相機拍照，不必先
  存到相簿再選檔。
- iPhone 相機直出常是 HEIC：瀏覽器對 HEIC 的預覽支援不穩定，**前端預覽這一步**可能需要額外的用戶端轉檔
  函式庫（如 `heic2any`）先轉成可預覽的格式，**但這不影響「儲存才真的上傳、伺服器端統一重新編碼」的規則**
  ——用戶端轉檔只是為了讓使用者在按下「儲存」之前看得到預覽，送出時仍是原始檔案交給伺服器統一處理。
  這一段是功能行為要求，實際函式庫選型留給第二階段的 `frontend-architect` 決定。
- 手機情境的操作重心是「新增/編輯單筆資料 + 拍照」，**不建議**在手機上開放 `S3` 訂單出貨掃描、
  批次操作這類需要同時看多筆資料比對的重度操作——這些仍導向「請用電腦操作」（可以只是不特別優化，
  不必刻意用 `el-message` 擋下，桌面版表格在手機上雖然難用但仍可捲動使用，不阻斷）。

## 9. 圖片上傳元件

### 畫面元素

```
┌───────────────────────────────┐
│                                │
│         📷（線稿圖示）           │
│    點擊或拖曳圖片到這裡上傳         │
│                                │
└───────────────────────────────┘
支援常見的照片格式，檔案大小上限 10 MB。
系統會自動把圖片縮成適合網頁的大小，並清除照片內的位置資訊。
```

選了檔案之後（尚未按儲存）：

```
┌───────────────────────────────┐
│ [縮圖預覽]                  ✕  │  ← 右上角小叉叉＝移除
│                                │
└───────────────────────────────┘
player-09.jpg・2.3 MB          [更換圖片]
圖片說明文字（中文）* [___________________]
圖片說明文字（英文，選填） [___________________]
```

### 逐項規則

| 情境 | 畫面行為 |
|---|---|
| 選檔（尚未儲存） | 瀏覽器端立即產生預覽縮圖；**不送出、不寫入**，只存在瀏覽器記憶體 |
| 解析度不足 | 前端讀取圖片實際像素，低於版位下限時擋下並顯示紅字：**「圖片解析度太低（至少需要 1600×900），請換一張品質較好的圖片」**，不允許帶著這張圖進入待儲存狀態 |
| 檔案過大 | **「圖片檔案太大（上限 10 MB），請換一張或先壓縮」**（規劃書 §4.0 原文案，沿用） |
| 按下「儲存」 | 圖片跟表單其他欄位一起送出；儲存按鈕文字變成「儲存中…」並 `loading`，圖片框疊一層半透明遮罩＋轉圈；**沒有獨立於表單之外的圖片上傳進度條**，因為圖片是跟著整個表單一起送出的，不是獨立非同步上傳 |
| 儲存失敗（伺服器端二次驗證不通過） | 圖片框變紅框，框下顯示：**「這張圖片無法使用：{原因}，請重新選擇」**，其餘欄位保留使用者輸入，不清空重填 |
| 換圖 / 移除 | 縮圖右上角 `✕`（移除，恢復成空上傳框）；「更換圖片」按鈕重新開啟選檔。**新圖寫入成功後才刪舊物件**（後端行為，前端只需在使用者體感上維持一致：換圖前舊圖仍在，直到整個表單成功儲存） |
| 多圖情境（商品圖等子表） | `el-upload` 的 `list-type="picture-card"` 呈現一排縮圖，可拖曳調整排序（需搭配拖曳排序函式庫），每張縮圖右下角一顆小星形圖示「設為主圖」 |
| 列表頁縮圖 | 160px 方形縮圖直接放在 `el-table` 對應欄，點擊用 `el-image` 內建的 `preview-src-list` 放大檢視 |

### 一個刻意的用字取捨

規劃書規定畫面上**不出現 `WebP`**，但後端實際接受的格式清單裡包含 WebP。本檔的處理方式是：
**上傳提示文案完全不列格式白名單的細節**（寫「支援常見的照片格式」而不是「支援 JPG、PNG、WebP、HEIC」），
`accept` 屬性仍可在背後接受 WebP，只是不把格式清單寫進畫面文字——這樣既遵守「畫面不出現 WebP」的硬性規定，
也不需要為了迴避一個詞而假裝系統不支援 WebP。**這是我代為做的文案判斷，不是規劃書逐字規定，值得請使用者
過目確認可接受。**

## 10. 第二階段建議實作頁面

### 建議組合

**外殼（頂欄＋側欄＋站台切換器＋使用者選單）＋ 儀表板（A）＋ 新聞與故事列表頁（B2）＋ 新聞與故事編輯頁（B2）**

### 為什麼是這四塊、為什麼具體挑 B2

- **外殼**是所有頁面的容器，且本檔第 1、5 節的決定（側欄分組、收合、站台切換器不換色）全部要在外殼裡
  驗證是否好用，不做外殼就沒有東西可以裝列表頁跟編輯頁。
- **儀表板**沒有前台產出、也不是列表/編輯的標準型，但它是登入後的第一頁，值得優先做出來檢查「無前台
  產出模組」的頁首寫法（第 6 節）與整體資訊密度是否恰當。
- **列表頁與編輯頁**沒有選一個最複雜或最簡單的模組，而是選 `B2` 新聞與故事，因為它**同時具備**本檔
  九條規範裡最多的驗證點：
  - 雙語欄位（標題並排、內文分頁）——驗證第 3 節兩種雙語呈現方式是否都好用；
  - 完整四態（草稿／排程發布／已發布／已停用）——驗證第 4 節狀態模型；
  - 圖片欄位（封面圖）——驗證第 9 節上傳元件；
  - SEO 欄位（網址名稱、正規網址、不讓搜尋引擎收錄）——驗證「技術概念要翻譯」這條規則在真實表單裡好不好用；
  - 明確對應到單一前台頁面（新聞中心）——驗證第 6 節的預覽連結機制。

  相對地，`S`（商店）或 `K`（會員）雖然功能上更貼近核心商業邏輯，但它們的複雜度來自**業務規則**
  （庫存扣減、訂單狀態機、會籍到期計算），如果第一階段就挑這兩個，會讓「先把標準型與元件庫定下來」
  這個目標被業務邏輯淹沒，之後其餘 13 個模組要重用這套標準型時反而缺乏一個「純粹展示版面規則」的參考範例。
  `B2` 做完之後，其餘模組的列表頁／編輯頁基本上是這個標準型的參數化重用（少雙語、少圖片、多幾個
  專屬欄位），複雜的業務規則（訂單狀態機、庫存）留給實作那些模組時再另外設計狀態機本身，不影響版面骨架。

- 若第二階段還有餘裕，**次優先建議加做 `J2` 角色與權限頁**——它是驗證「代號不進介面、權限碼一律譯成中文
  描述」這條規則最容易踩雷的地方（規劃書 §6 權限矩陣直接用 `shop.order.export` 這類代號描述，介面上必須
  translate 成「匯出訂單名單」），值得早點做出來對一次。

## 13. 第二階段實作補充（S0-12，`frontend-architect` 建立可點 mockup 時發現）

以下是把本檔規格做成真的 Vue 專案時，發現本檔沒講清楚或講得不夠而需要補的地方。**規格本身沒有變**，
是補完第 6 節「這裡管理的是」在少數情境下的第三種行為，以及把第 1 節的側欄結構講得更精確。

### 13.1 「這裡管理的是」補第三種變體：`app`（只產出到行動 App，網頁前台沒有對應頁面）

第 6 節原本只講了兩種行為：`none`（無前台產出，灰字說明）與 `link`／`multi`（有網頁前台頁面，可點擊
連結）。但實際查規劃書 §4.0 的**前後台對照表**（真實來源，逐字核對過，見下）後發現有第三種情況：
`M`（行動 App）全部五個子模組、`E4–E6`（廣告主與版位／投放檔期／成效報表）、`P3`／`P4`（報名／試訓，
「資料進後台，前台只負責送出」）、`G1`／`G2`（表單設計／收件匣）——這些模組**確實有產出**，但產出的
是行動 App 或「前台只送出、後台才是真正管理的地方」，不是一個可以開新分頁連過去的網頁 URL。

處理方式：新增第三種畫面行為 `app`——灰字顯示「這裡管理的是：{名稱}」但不做成可點擊連結（因為沒有
URL 可連，硬做成連結會連到 404）。與 `none` 的差別是文字仍然講清楚「管理的是什麼」，不是「沒有產出」；
與 `link` 的差別是不可點擊。程式碼在 `apps/admin/src/types/frontendUnit.ts`／`data/frontendUnits.ts`。

⚠️ **這份對照表逐字取自規劃書 §4.0，不是本檔或實作階段編的**——實作時發現 `docs/21` 原本舉的例子
「B2 → 新聞中心」在規劃書裡實際寫的是「07 新聞與故事（7.1–7.7）、首頁最新消息」，**沒有「新聞中心」
這個名稱**。已在程式碼的對照表改回規劃書原文「新聞與故事」，本檔第 6 節原本的例子文字是示意寫法，
不是規劃書逐字規定，這裡一併記錄避免下一位工程師照著例子的措辭去核對規劃書時對不上。

### 13.2 側欄結構：14 個一級模組各自是「葉節點」或「手風琴子選單」，不是統一的兩層結構

第 1 節的 wireframe 只示範了「內容管理」展開後的樣子，`儀表板`／`搜尋與 AI 能見度`／`網站設定` 前面
畫的箭頭符號並不一致（儀表板前也畫了箭頭，但儀表板沒有子模組）。實作時採用的規則是：**有子模組代號
的一級模組（`B C P E F G J K L M S`，比照 `docs/03-admin-spec.md` §1 的模組樹）渲染成
`el-sub-menu`（手風琴，`unique-opened`）；沒有子模組代號的（`A H I`）直接是可點擊的葉節點**，不會有
展開箭頭。這個規則跟 `docs/03` 的模組代號分配完全對得上，只是第 1 節的 wireframe 手繪示意沒有畫出這
個差異，這裡補記讓下一位讀者不必自己重新判斷。

### 13.3 手機寬度下「這裡管理的是」文字要允許換行，不能整段強制單行

第 6 節與第 9 節都沒有特別提到這一列在窄螢幕的換行行為。實作時第一版用了 `white-space: nowrap`
（因為桌面寬度下這一列理應在標題同一行、不換行），結果在 375px 寬度、文字較長的情境（例如編輯頁的
「這筆資料尚未發布，沒有正式網址可預覽」附加說明）超出螢幕寬度被裁切看不到後半段，雖然沒有造成整頁
橫向捲動（外層 flex 容器有 `flex-wrap: wrap` 讓這一列自己換到標題下一行），但那一行本身內部仍不換行
導致文字被裁掉。已改為手機寬度下允許正常斷行（移除 `nowrap`），桌面寬度因為文字通常較短還是维持
同一行。之後其他模組的頁首如果也照抄「同一行右側」的寫法，記得比照這個處理，不要重複 nowrap 的坑。
