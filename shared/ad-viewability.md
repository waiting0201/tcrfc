# 廣告可見度量測：雙平台共同行為規格

> 🔵 **執行層產物，不是規格。** 規則來自 App 規劃書 §7.5（曝光與點擊的定義）、§2.4（離線硬規則）與 [`docs/19`](../docs/19-app-tech-stack.md) §6.1；本檔只把它們寫成**兩端都能照著實作的判定流程**，不新增規則。與規劃書衝突時以規劃書為準。
> **兩端不得各自解釋這份文件**——歧義就回頭問，不要自己選一種（Android 實作時發現講不清楚的地方，就是規格真的沒寫清楚，見 docs/19 §11 緩解 5）。
> 測資是 [`ad-viewability-cases.json`](ad-viewability-cases.json)，兩端單元測試**逐案**比對事件數；[`scripts/check-shared.py`](scripts/check-shared.py) 內有一份參考實作，用來驗證測資本身與本文一致。

## 1. 分工：哪些可以不同，哪些必須相同

| 層 | 內容 | 兩端是否可以不同 |
|---|---|---|
| 取得 `visibleRatio` | iOS：UIKit `AdSlotView`＋`CADisplayLink`；Android：Compose `onLayoutRectChanged` 或 `onGloballyPositioned`＋200ms 迴圈（docs/19 §6.2、§6.3） | **可以不同**（UI 框架不同） |
| **判定**：拿到取樣序列之後，何時算一次有效曝光 | 本檔 §3 | **必須相同**，由測資驗證 |
| 事件佇列與上報 | docs/19 §6.4 | 必須相同（欄位、批次、逾時、丟棄） |

## 2. 常數

| 名稱 | 值 | 來源 |
|---|---|---|
| 取樣間隔 | 200ms（5Hz） | docs/19 §6.1 |
| 最低可見比例 | `visibleRatio ≥ 0.5`（含 0.5） | 規劃書 §7.5「≥50%」 |
| 最短連續時長 | `≥ 1000ms`（含 1000） | 規劃書 §7.5「≥1 秒」 |
| 點擊去重窗口 | 5000ms | 規劃書 §7.5 |

`visibleRatio` ＝ 版位矩形 ∩ 有效可見區 的面積比。有效可見區 ＝ 視窗 ∩ 所有會裁切的祖先容器 ∩ 扣除已知固定遮擋（底部分頁列、彈窗）。

## 3. 曝光判定（純函式，無 UI 相依）

**輸入**：依時間排序的取樣序列。每筆取樣是 `(tMs, visibleRatio, appState, presentationId)`：

- `tMs`：**單調時鐘**毫秒（iOS `CLOCK_MONOTONIC`／Android `SystemClock.elapsedRealtime()`），不是牆鐘；
- `appState`：`active`／`inactive`／`background`（`inactive` 含來電橫幅、控制中心）；
- `presentationId`：每次素材裝載進版位產生一個 UUID（規劃書 §7.5；輪播每則各自一個）。

每個 `presentationId` 另有兩個屬性：`isFallback`（是否備援素材）、`imageDecodedAtMs`（圖片解碼成功的單調時間，尚未成功為 `null`）。

**規則**（逐筆取樣、依序處理）：

1. **備援素材**：`isFallback` 為真 → 這個 presentation 的量測器根本不啟動，永不發曝光。
2. **圖片未解碼**：`imageDecodedAtMs` 為 `null`，或 `tMs < imageDecodedAtMs` → 這筆取樣不計（量測器在圖片解碼成功之後才啟動）。
3. **App 不在前景**：`appState != active` → **所有** presentation 的連續計時**立即歸零**，這筆取樣不計。
4. **切換素材**：這筆取樣的 `presentationId` 與上一筆不同 → 上一個 presentation 的連續計時歸零（輪播切走即離開版位）。
5. **已發過**：這個 `presentationId` 已經成立過 → 不再處理（**每個 presentationId 只發一次曝光**）。
6. **可見判定**：
   - `visibleRatio ≥ 0.5`：若沒有進行中的連續區間，則以這筆的 `tMs` 為**起點**；若 `tMs − 起點 ≥ 1000` → **成立**，發出一次曝光，事件 `atMs = tMs`，並標記這個 presentation 已成立。
   - `visibleRatio < 0.5`：連續區間**歸零**（下次再可見時重新起算）。

🔴 **用單調時鐘計算「連續滿足的時長」，不是數取樣次數**：掉幀時取樣會變稀，數次數會低估（測資 `monotonic_duration_not_sample_count`）。相鄰兩筆取樣之間，視為維持前一筆的狀態。

## 4. 點擊去重（裝置端）

- 同一裝置對**同一素材**，**距離上一次「實際送出」的點擊小於 5000ms** → 丟棄；`≥ 5000ms` → 送出。
- 窗口以「上一次**送出**的點擊」為錨，不是滑動窗口（測資 `click_anchor_is_last_sent`）。
- 不同素材各自去重。
- **伺服器端同時去重**（兩層都要，裝置時鐘可被改）：伺服器以「同裝置同素材、前後各 5 秒（開區間）內已有點擊」判重，邊界一致（剛好相隔 5000ms 不算重複）。

## 5. 其他共同規則（不在純函式內，但兩端必須一致）

| 項目 | 規則 | 來源 |
|---|---|---|
| 離線 | 離線時不得計算曝光；事件可暫存，但**必須帶原始發生時間**，伺服器拒收超過 24 小時者 | 規劃書 §2.4 硬規則 1 |
| 時鐘校正 | 啟動時由設定端點回應的 `Date` 標頭算 `server_skew`；事件 `occurred_at` ＝ 單調時鐘推算 ＋ skew | docs/19 §6.1 |
| 不計曝光 | 顯示備援素材時、App 在背景時、廣告載入失敗時 | 規劃書 §7.5 |
| 隱私 | 事件不得帶 `member_id`、完整 IP、座標、廣告識別碼——在 App 端就不放進 payload | docs/19 §6.4、規劃書 §7.8 |
| 揭露 | 回應的 `disclosureLabel`（「廣告」／「Ad」）必須顯示 | docs/19 §11b |

## 6. 已知誤差與待決

- **登記為已知誤差**：Android 10 分割畫面下兩個 App 可能同時 `RESUMED`，可能高估（docs/19 §6.3）。
- 【待決】連續區間的**起點**用「第一筆達標取樣的 `tMs`」。若某端 UI 框架在版位進入畫面與第一次取樣之間有延遲，會比實際略晚起算（偏保守，不會高估）。規劃書未規定更精確的起點，若廣告主對帳需要，先改規劃書。
- 【待決】裝置重啟後單調時鐘重置：本檔的曝光判定只在單次 App 行程內使用單調時鐘，不跨重啟；事件佇列內已存的 `occurred_at_utc` 是換算後的 UTC，不受影響。會員卡 7 天提醒跨重啟的處理見 `shared/README.md` 待決清單。
